## 1. Профили лежат в файлах

Профиль — файл `api/profiles/<имя>.json`, например `vms.camera/1` лежит в `vms.camera.json`. Таблицу `<имя>.md` собирает `tools/build_api.py`, руками её не правят. Раздел `profiles` в `api/fixtures/demo.json` теперь собирается из этих файлов. Копия w2c раздела `kinds` из `demo.json` работает как раньше: виды и их поля не менялись.

Нужно от w2c: ничего менять не нужно. Если бэкенд берёт описания профилей из `demo.json`, он может брать их и из файлов.

## 2. `GET /kinds`: `version` и `uses`

В разделе `profiles` у каждого профиля есть два новых необязательных поля.

- `version` — младшая версия профиля, которую сделал бэкенд, вместе со старшей: `1.0`. Старшая версия равна номеру в `id`.
- `uses` — список `{id, version}`: от каких профилей и каких версий зависит профиль. Значение берётся из файла профиля этой версии.

Клиент, который не знает этих полей, их игнорирует. Если бэкенд не прислал `version`, консоль считает версию `M.0`, где `M` — старшая версия из `id`.

Нужно от w2c: отдавать `version` и `uses` в `GET /kinds` для профилей, которые бэкенд объявил. Эти значения бэкенд берёт из файла профиля, а не придумывает сам.

## 5. Клиент и незнакомая версия

Консоль читает версию профиля, которую прислал сервер, тремя способами (подробности — в [`api/profiles/README.md`](../profiles/README.md), раздел «Версии»).

1. Младшая версия выше известной (`1.7` при известной `1.5`): особый экран работает, новые поля консоль показывает в «Все параметры».
2. Младшая версия ниже известной (`1.4` при известной `1.5`): особый экран не показывает поля, которых в `1.4` нет.
3. Незнакомая старшая версия (`vms.camera/2` без `vms.camera/1`): консоль пропускает профиль и открывает объект формой по схеме.

Нужно от w2c: бэкенд отдаёт `version` из файла профиля и сам версию не меняет. Новое поле — запрос к owner профиля (mockup): он поднимает младшую версию в файле. Переименованное поле или смену типа owner оформляет новым профилем `<имя>/<N+1>` рядом со старым.
