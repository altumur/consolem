## Почему по группам

Почти все пункты — подробности камер, детекторов, архивов и действий. Механизм для них в контракте уже есть: схема вида, `allOf`, `actions`, `events`, форма по схеме. Нужны только данные вида. Владелец не проверяет такие подробности по одному полю. Ядро контракта и описания подсистем владелец хочет разделить (`docs/2026-11-16-kontrakt-i-podsistemy-predlozhenie.md`). Поэтому:

- с этого ответа **данные существующего вида**, которые не трогают `api/openapi.json`, уведомления владельцу не требуют. Это правило записано в скилле `api-contract`, п. 5, и в `CLAUDE.md`;
- уведомление по-прежнему нужно, если правка добавляет новый вид, новый профиль, новое расширение `x-*`, меняет `api/openapi.json`, что-то ломает или **вводит новое поведение сервера**: новую проверку или отказ, команду, которая что-то делает, перенос, замену, резервирование, репликацию. Если сервер только хранит и отдаёт новое значение, уведомление не нужно.

## 2. Пороги D6 и D7 — число вместо строки

Принято. Параметры событий `load.high` (`percent`) и `device.lost` (`thresholdSec`) лежат в описании событий вида в `demo.json`, а не в `api/openapi.json`. Поэтому это тоже данные вида. Клиентов у контракта нет, поэтому:

- тип меняется на число (`integer` с `minimum` и `maximum`: D6 — 0–100 %, D7 — 0–3600 с), без старого поля с `deprecated`;
- у `device.restored` появляется свой порог (D7);
- сохранённые правила в наборах переводятся на числа;
- в `api/README.md` — строка «Ломающие изменения в X.Y.Z»: что стало числом.

Уведомление не нужно.

## 3. Пункты ядра — приняты, с уведомлением

Это правила и права, они общие для всех подсистем.

- **D4. Сравнение диапазоном в условии правила.** Параметр события в `match` может быть числом или объектом `{min, max}`, у которого любая граница необязательна. Сервер сравнивает диапазон только у числовых параметров. Диапазон у нечислового параметра — `422 VALIDATION_FAILED`. Нужен для возраста, температуры, живости, порогов D6 и D7. Выбор конкретного списка (`listId`) — это данные события, его делаете вместе с C17.
- **DX1. Справочник переменных шаблона.** В `reference` — список переменных для текстов действий: имя, подпись и события или виды, у которых переменная есть. Пять переменных из описания `RuleAction.text` переходят в справочник, около 25 новых добавляются. Описание `RuleAction.text` ссылается на справочник.
- **D23. Блокировка пользователя.**
  - `AccessUser.lockedUntil` (`date-time` или `null`): `null` — пользователь не заблокирован. Если срок блокировки 0, блокировку снимает только администратор. Форма записи на ваш выбор, назовите её в уведомлении.
  - Команда снятия блокировки, например `POST /access/users/{id}/unlock`. Снятие — запись в журнале аудита.
- **D24. Требования к имени пользователя.** Они живут там же, где политика паролей. Где именно, решает ответ на [запрос об опциях домена](2026-11-06-135941Z-mockup-domain-options-fields-response.md), п. 1.3. Нарушение — новый отказ при создании пользователя. У пользователя из каталога отказа нет: консоль его имя не выбирает. Вместо отказа ставится признак, как предложено для имени RTSP в [вопросе о входе за потоком](2026-11-16-203335Z-owner-stream-access-keys-request.md).
