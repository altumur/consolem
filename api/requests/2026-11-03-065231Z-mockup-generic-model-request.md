## Краткий итог

- **Ответ: да, но частично.** Для расширяемых VMS универсальная модель обязательна. Объекты psim-плагина появляются уже после выпуска WebUI, и без описаний видов с сервера WebUI их просто не настроит. Универсальной модель должна быть для **конфигурирования объекта**: дерево, карточка, мастер добавления, групповая правка, команды, события в правилах, права. Живое видео, PTZ, разговор, архив и шкала времени, матрица прав и редактор правил остаются предметными API: это не формы.
- **Что предлагаем:** гибрид — вариант 3 из шага 3. Гипотезу «`Unit` в стиле Kubernetes CRD» принимаем как основу, с пятью поправками:
  1. описания видов — отдельный ресурс `GET /kinds` с ETag и событием `kinds.changed`, а не часть `/reference`;
  2. ссылки на объекты — это свойства (`x-ref`), а не отдельный API связей;
  3. проекции «кодом плагина» отвергаем, вместо них — **профили** (`implements: ["vms.camera/1"]`). Профиль — опубликованный набор свойств с известным смыслом, ручные экраны привязываются к нему, а не к виду;
  4. универсальные действия — только `instant` и `longRunning`. `session` и `media` — предметные API, доступность которых объявляет профиль;
  5. одно поле `state` делим на заданное (`properties`) и наблюдаемое (`status`: связь, условия, `observedVersion`).
- **Главный выигрыш:** новый вид объекта сейчас — это контракт, `server.js`, `index.html`, тесты и набор. Ближайший аналог `security_controller` — единицы СКУД с контроллером и командами, коммит `953777e`: 16 файлов, 957 строк. С универсальной моделью — ноль правок WebUI и контракта: только описание вида в системе. За пять дней контракт менялся в 73 коммитах. По запросам w2c — 38 коммитов, 496 изменений файлов, около 40 тыс. добавленных строк. Из 116 пунктов этих запросов 42 (36 %) — «добавьте поле, значение, вид или настройку вида»; в новой модели это данные.
- **Цена:**
  - контракт: около 12 новых операций вместо около 35 операций CRUD по видам, договорённости об описании вида, профилях, ошибках с путём к полю и о `status`;
  - WebUI: построитель формы по схеме, дерево и мастер по описаниям, перевод ручных экранов на профили;
  - адаптеры: w2c — манифест в `UnitKind`; NGP — `UnitDescriptor` и `factory` в `UnitKind`; psim — `plugin.json` в `UnitKind`;
  - доработка систем: строгая проверка версии при записи (сейчас её нет ни в NGP, ни в psim), команды и события у видов NGP, Plugin V2 в NGP (ADR-009 в статусе «предложено», в коде NGP его ещё нет).
- **Что теряет UX:** формы по схеме у незнакомых видов беднее ручных — нет связанных подсказок, сводок и «умных» вкладок. Смягчаем подсказками `x-ui-*` (группы, вкладки, порядок, единицы, виджеты), ручными экранами по профилям у известных видов и необязательной страницей плагина в iframe.
- **Прецеденты:**
  - Kubernetes CRD — способ, которым сторонний модуль добавляет в Kubernetes новый вид объекта со схемой полей, после чего общие клиенты сразу его показывают и правят;
  - Nx Meta: модель настроек плагина, по которой клиент сам строит форму, и свои виды событий;
  - Home Assistant (формы по схеме и типизированные «домены» сущностей), openHAB (описания настроек с контекстом для виджета).
  - Общий урок: везде универсальное ядро **плюс** ручные экраны или плагины UI для важных видов (Rancher, Headlamp, Milestone). Чисто универсального интерфейса без исключений не нашли.

## 1. Что такое Kubernetes CRD — простыми словами

Раздел нужен, чтобы читать разбор гипотезы (раздел 2): гипотеза построена «в стиле CRD».

**Kubernetes** — система, которая запускает программы на группе серверов. Всё, чем она управляет (программа, её адрес в сети, её диск), — **ресурс**: запись, в которой человек пишет, *каким* это должно быть, а не *что сделать*. Записи хранит и проверяет **API-сервер**; отдельные программы-**контроллеры** смотрят на записи и приводят систему к описанному.

**CRD (Custom Resource Definition)** — описание нового вида ресурса, которое сторонний модуль кладёт в работающую систему, не меняя сам Kubernetes. В описании: имя вида, его версии, **схема полей** (OpenAPI v3, то есть JSON Schema: типы, обязательность, диапазоны, перечисления) и разделение на `spec` — что задано, и `status` — что получилось ([Kubernetes: Extend the API with CRDs](https://kubernetes.io/docs/tasks/access-kubernetes-api/extend-api-custom-resource-definitions/), [Custom Resources](https://kubernetes.io/docs/concepts/extend-kubernetes/api-extension/custom-resources/)). После этого объекты нового вида — **custom resources** — создаются, читаются, правятся и удаляются теми же общими запросами, что и встроенные.

**Кто что делает.** API-сервер хранит объекты и проверяет их по схеме (в том числе правилами на языке CEL: «поле нельзя менять после создания», «min ≤ max» — [CEL in Kubernetes](https://kubernetes.io/docs/reference/using-api/cel/)). Поведение реализует контроллер (оператор) модуля: он читает `spec`, что-то делает и пишет итог в `status` через отдельный подресурс `/status`, чтобы запись человека и запись контроллера не мешали друг другу ([API conventions, копия](https://github.com/tscherf/kubernetes/blob/master/docs/api-conventions.md)).

**Почему общие клиенты справляются без доработки.** `kubectl`, Lens, Headlamp читают список видов и их схемы у API-сервера; объект любого вида для них — дерево полей, которое можно показать списком и править как YAML. Headlamp показывает CRD автоматически, а для «богатого» вида нужен плагин ([Kubernetes blog: Headlamp plugin for Kubeflow](https://kubernetes.io/blog/2026/07/13/introducing-headlamp-plugin-for-kubeflow/)). У Rancher без своего экрана — список и правка YAML, свой экран регистрирует расширение ([Rancher extensions: resources](https://extensions.rancher.io/internal/code-base-works/customising-how-k8s-resources-are-presented)).

**Пример.** Описание вида «датчик» и объект этого вида:

```yaml
# Описание вида (CRD): кладёт модуль
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata: {name: sensors.security.example.com}
spec:
  group: security.example.com
  names: {kind: Sensor, plural: sensors}       # имя вида
  scope: Namespaced
  versions:
    - name: v1
      served: true
      storage: true
      subresources: {status: {}}               # status пишет контроллер отдельно
      schema:
        openAPIV3Schema:                        # схема полей
          type: object
          properties:
            spec:                               # что задано
              type: object
              required: [zone]
              properties:
                zone: {type: string}
                mode: {type: string, enum: [auto, manual, test], default: auto}
            status:                             # что получилось
              type: object
              properties:
                online: {type: boolean}
---
# Объект этого вида (custom resource): создаёт пользователь
apiVersion: security.example.com/v1
kind: Sensor
metadata: {name: door-1}
spec: {zone: "Вход А", mode: auto}
```

**Соответствие нашим понятиям**

| Kubernetes | У нас |
|---|---|
| CRD | описание вида объекта `UnitKind` (`GET /kinds`) |
| custom resource | объект `Unit` |
| API-сервер | бэкенд конфигуратора с адаптером системы |
| контроллер (оператор) | плагин psim, подсистема w2c, конфигуратор NativeBL в NGP |
| `spec` / `status` | `properties` (задано) / `status` (наблюдаемое: связь, условия, `observedVersion`) |
| `kubectl`, Lens, Headlamp | наш WebUI |
| плагин Headlamp, расширение Rancher | ручной экран WebUI по профилю или страница плагина `setup_ui` |

**Чего в CRD нет и что придумываем сами:**
- подсказок для формы — групп, вкладок, подписей вариантов, виджетов. У Kubernetes есть только `additionalPrinterColumns` для колонок списка ([CRD v1](https://kubernetes.io/docs/reference/kubernetes-api/apiextensions/custom-resource-definition-v1/)); берём `x-ui-*`, как в JSON Forms и openHAB;
- команд у объекта. У Kubernetes «действие» — смена `spec`; у нас ARM/DISARM — команда (`actions`);
- событий для правил автоматизации. В Kubernetes нет; у нас `events` в описании вида, как у psim и Nx;
- прав «по-человечески»: Kubernetes RBAC — глаголы над видом. Берём то же, плюс право на каждое действие;
- групповых операций с частичным успехом — у нас уже есть `/operations`.

Где Kubernetes решает иначе: проверка «сложных» условий — вебхуки (отдельная программа модуля отвечает «можно / нельзя»). Нам это подходит как `CanCreateChild` psim и проверка в адаптере. Преобразование версий схемы — вебхуки конверсии ([KEP-598](https://www.kubernetes.dev/resources/keps/598/)); нам это пока не нужно: описание вида у нас одно на версию плагина, старое не хранится.

## 2. Разбор гипотезы

### 2.1. Решение по элементам

| Элемент | Решение | Почему (доказательство — в приложении Б) |
|---|---|---|
| Один ресурс `Unit`: `uid`, `kind`, `parent`, `version`, `properties`, `relations`, `state` | **с поправкой** | Ложится на три системы: w2c `unit:<sub>/<id>` и строка манифеста; NGP `UnitDescriptor` (`ConfigurationService.proto:27`); psim `Unit{object, parent, params}` (`common.proto:37`). Поправки: `relations` убрать в свойства-ссылки; `state` разделить на `properties` и `status`; добавить `name`, `domainId`, `folders`, `capabilities` (что можно с этим объектом), `secrets` (какие секреты заданы) |
| `GET /reference` как справочник видов | **с поправкой** | Отдельный ресурс `GET /kinds`, `GET /kinds/{kind}` с ETag и событием потока `kinds.changed`. `/reference` остаётся для того, что не вид (часовые пояса, модели устройств) |
| Четыре метода записи и чтения | **принимаем**, плюс `GET /units` (отбор по виду, родителю, ссылке) и `POST /units/{uid}/move` | `PATCH` — JSON Merge Patch (RFC 7396) по `properties`: так же устроен `UpdateObject` psim (`platform_service.proto:291`); w2c пишет строку целиком — адаптер читает, сливает и пишет с `revision` |
| `If-Match` по `config_etag` | **с поправкой: сейчас только видимость** | NGP: `ChangeConfigRequest` ожидаемой версии не принимает (`ConfigurationService.proto:199`), реализация `config_etag` не сверяет, а сам `config_etag` общий на пакет и его детей (`ConfiguratorUtils.h:186-195`, `FillConfigInfoDFT`). psim: версии у объекта нет вовсе (`common.proto:37`, `UpdateObjectRequest`). w2c: строгая проверка `revision` есть (`07-console-module.norms.md:80`, `:102`). Нужны доработки NGP (N-01 из `configurator-backend/notes/08` §10.1) и psim |
| Действия `POST /units/{uid}/actions/{action}`, `kind: instant \| longRunning \| session \| media` | **с поправкой** | `instant` и `longRunning` — да. `longRunning` отвечает операцией из `/operations`. `session` и `media` — нет: живое видео, разговор, PTZ, воспроизведение — WHEP, аренды и шкала, у них своя форма запросов и ответов. Они остаются предметными API, их наличие объявляет профиль |
| Связи `GET/POST/DELETE /units/{uid}/relations/{type}` | **отвергаем как отдельный API** | Во всех трёх системах ссылка — значение свойства: psim `source: platform_objects` (`plugin.schema.json:42`), NGP `ReferencePropertyAttribute` (`PropertyAttribute.proto:82`), w2c `about` (`rec.subsystem.yaml:60`). Делаем свойство с `x-ref: {kinds, scope}`, обратный поиск — `GET /units?ref=<uid>`. Членство в папке — общее поле `folders` |
| Топология `GET /tree/children`, `GET /tree/paths` | **принимаем**, `TreeNode.kind` — открытая строка | Плюс `GET /units/{uid}/creatable` — что можно создать здесь и форма для создания. Это `factory` NGP (`ConfigurationService.proto:61`, `BatchGetFactories`) и `CanCreateChild` psim (`plugin_service.proto:51`) |
| Проекции `?projection=<name>`, «реализует код плагина» | **отвергаем, заменяем профилями** | Кода «проекции» нет ни в одной из трёх систем. Клиенту всё равно нужно знать, как рисовать `Device`, то есть типизация вернулась бы в клиент. Профиль `vms.camera/1` — опубликованная схема-фрагмент: вид объявляет `implements`, ручной экран WebUI привязан к профилю |
| Остаётся типизированным: `/operations`, `/stream`, `/access/apply`, `/test/*` | **принимаем и расширяем** | Плюс живое видео, разговор, PTZ, шкала и воспроизведение, удержания и отметки, правила и расписания, режимы, сценарии, матрица прав, настройки, журнал, ассистент |

### 2.2. Девять пунктов проверки

1. **Ложится ли один `Unit` на три системы и что теряется.** Ложится:
   - w2c: `kind = <sub>` (одна коллекция `rows` на подсистему, `cam.subsystem.yaml:36`), `uid = unit:<sub>/<id>`;
   - NGP: `kind = UnitDescriptor.type`, `uid` с родителями (`ConfigurationService.proto:30,103`);
   - psim: `kind = <plugin_id>/<type>`, `uid` — `type`+`id` (`common.proto:17-33`).

   Теряется:
   - у w2c — таблицы (записываются целиком, `cam.subsystem.yaml:246`), общие настройки домена с наследованием (`cam.subsystem.yaml:201`, `:402`), размещение и метрики. Таблицы и общее на домен — особые виды (п. 5.10), размещение — `status`;
   - у NGP — схема на объект, а не на вид: свойства с ограничениями приходят в каждом `UnitDescriptor` (`:46`), зависят от значений (`EnumerationConstraintsItem.properties`, `PropertyDescriptor.proto:147`) и бывают динамическими (`DynamicParametersService.proto:54`). Нужна схема объекта поверх схемы вида (п. 5.1). Ещё теряются шаблоны (`assigned_templates`, `:89`) и `reset_operations` (`:56`) — их делаем действиями;
   - у psim — ничего, кроме версии, которой нет.
2. **`If-Match` по `config_etag`.** Строгой проверки нет — только видимость (см. таблицу). Предлагаем: контракт требует строгой проверки; пока системы её не дали, адаптер сверяет «прочитал — сравнил — записал» с окном гонки, а система объявляет это в возможностях. Это открытый вопрос В-1 в приложении Ж.
3. **`GET /reference` и реестр видов.** Отдельный `GET /kinds`: список описаний и его общий ETag; `If-None-Match` → `304`. Установка, обновление или выключение плагина и смена манифеста w2c → `kinds.changed` с перечнем видов, клиент перечитывает их. Размер: у psim вид — десятки строк JSON; у NGP видов около сотни, схема по видам укладывается в сотни КБ. Схемы на объект (NGP) — отдельно, `GET /units/{uid}/schema`, только у видов с `schemaPerUnit: true`.
4. **`properties` против `relations`.** Граница: значение, которое задаёт оператор в форме объекта, — свойство, даже если это ссылка (камеры контроллера psim, `security_controller/manifest/plugin.json:41-74`). Связь с собственными атрибутами (камера ↔ хранилище с режимом и сроком) — либо дочерний объект (запись в хранилище как `Unit` вида `recording`), либо свойство-массив объектов со ссылкой. Отдельного API связей не нужно.
5. **Где исполняется «проекция».** Нигде: ни в NGP, ни в w2c, ни в psim такой точки нет. Проекции возвращают типизацию в клиент, поэтому заменяем их профилями — данными, а не кодом.
6. **`session` и `media`.** Одним универсальным методом не выражаются: WHEP (`/devices/{id}/live`), аренда PTZ, шкала и куски записи — разные протоколы. Оставляем предметные API, адресуем их по `uid`, а доступность объявляем профилем (`vms.live/1`, `vms.ptz/1`, `vms.talk/1`, `vms.archive/1`).
7. **Чего в ядре гипотезы нет, а в контракте есть** — сохраняем:
   - групповые операции с частичным успехом и `idempotencyKey` (`/operations`, `POST /objects/delete`) — шаги `set`, `action`, `delete` по `uid`;
   - откат («Отменить»);
   - права на объект и на вид (п. 5.7);
   - правила по событиям и действиям из описаний видов (п. 5.7);
   - поиск и фильтры дерева — по `kind`, профилю и свойствам с `x-ui-filter`;
   - наблюдаемое состояние и «почему не применилось» — `status.conditions`.
8. **Желаемое и наблюдаемое.** Одного `state` мало. `properties` — задано. `status` — `link` (связь), `conditions[]` (`Applied`, `Ready`… с `reason`, как условия Kubernetes), `observedVersion` («применилась ли моя правка»), `observed` (значения, которые система назначила сама, например `serverId` камеры w2c — п. 8 запроса `2026-11-01-182545Z-w2c-domain-startup-archives-rollback`).
9. **Хватит ли описания вида на `security_controller` без кода под вид.** Хватит на карточку, мастер, команды, события и права (сценарий 1, приложение Е). Не хватает в самом манифесте psim: обязательности полей (в схеме манифеста нет `required` у параметра, `plugin.schema.json:8-80`), групп и вкладок, описания параметров команд (`parameters` — произвольный объект, `:246`) и данных событий, нескольких допустимых родителей (`parent` — одна строка, `:198`). Без этого форма работает, но хуже. Это пункты к команде psim-sdk, не к нам.

### 2.3. Наброски трудных частей

Схемы OpenAPI 3.1 целиком — приложение Д. Здесь — суть и выбор.

**`ActionDescriptor`**

```yaml
ActionDescriptor:
  id: ARM                         # = Command.id psim, requests.action w2c
  label: {key: command.arm, text: "Поставить на охрану"}
  execution: instant              # instant | longRunning
  params: {JSON Schema 2020-12}   # пусто — без параметров
  result: {JSON Schema}           # для instant: что вернётся (psim SendCommandResponse.result)
  confirm: {typeCount: false, text: …}   # нужно ли подтверждение
  group: true                     # можно в групповой операции
  ruleAction: true                # можно как действие правила
  right: action:ARM               # право, которое нужно
```

Альтернативы: (а) действие как смена свойства (`armed: true`) — так в Kubernetes, но ARM у psim — команда, а не состояние; (б) типизированные пути на каждую команду — новый контракт на каждый плагин. Рекомендуем дескриптор: он ложится на psim `commands` (`plugin.schema.json:230`), на w2c `requests.schema` (`cam.subsystem.yaml:332`) и на нынешние `UnitOption.operations`.

**Ссылка на объект (вместо связей)**

```yaml
cameras:
  type: array
  items: {type: string}           # uid
  x-ref: {kinds: ["*"], implements: ["vms.camera/1"], scope: domain}
```

Выбор камер строится запросом `GET /units?implements=vms.camera/1&domainId=…`. Альтернатива — отдельный API связей (гипотеза) — дублирует свойство и требует второго пути записи.

**Профиль (вместо проекции)**

```yaml
Profile vms.camera/1:             # публикует контракт, а не плагин
  properties: [ip, port, vendor, model, archiveId, recordMode, …]   # имена и смысл фиксированы
  status: [recordState]
  apis: [live, timeline]          # какие предметные API у объекта есть
```

Вид объявляет `implements: ["vms.camera/1"]`. Ручной экран камеры WebUI работает с любым видом, который это объявил: с камерой NGP, w2c и psim (`camera` из `psim_plugins/cmd/camera`). Свойства сверх профиля показываются формой по схеме на вкладке «Дополнительно». Профили версионируются; незнакомый профиль клиент пропускает и рисует форму.

**Полнота ограничений.** Берём подмножество JSON Schema 2020-12: `type`, `enum` (+ `x-enum-labels`), `minimum`/`maximum`, `minLength`/`maxLength`/`pattern`, `items`, `minItems`/`maxItems`, `required`, `default`, `readOnly`, `writeOnly` (секрет), `if/then` и `dependentSchemas` (зависимые поля NGP). К ним — расширения:
- `x-immutable` (w2c `fixed`, CEL `oldSelf` у Kubernetes);
- `x-inherit` (w2c `inherit`/`merge`);
- `x-unique` (w2c `unique`);
- `x-ref`;
- `x-ui-*`: `group`, `tab`, `order`, `unit`, `widget` (`polygon`, `line`, `mask`, `point` — геометрия NGP, `PropertyDescriptor.proto:45-66`; так же у Nx: `PolygonFigure`, `LineFigure`), `filter`, `advanced`.

Что JSON Schema не выразит (уникальность среди объектов, «можно ли здесь», лимиты лицензии), проверяет только бэкенд и отвечает ошибкой с путём к полю.

**Миграция.** Подробно — раздел 5.12 и приложение Д. Кратко: ядро вводится рядом с нынешними путями, разделы переводятся по одному, затем старые CRUD-пути «Оборудования» и «Хранилищ» удаляются.

**Цена и что теряем:**
- **Адаптеры.** w2c — перевод манифеста (раздел 6, вопрос 1). NGP — перевод `UnitDescriptor` и `factory` в описание вида и схему объекта, команды из других сервисов NativeBL. psim — почти один к одному, но к NGP Plugin V2 ещё не подключён.
- **Формы по схеме против ручных.** У незнакомых видов карточка — группы полей и вкладки по `x-ui-*`, без «умных» сводок; ручные экраны остаются только у профилей.
- **Проверки в двух местах.** Клиент проверяет по схеме для подсказки, решает бэкенд; расходиться им нечем: схема одна.
- **Производительность.** Дерево не меняется (`/tree/children` уже универсально). Описания видов кэшируются по ETag. Групповая правка 200 объектов разных видов — та же операция, шаг `set` по `uid`.
- **Отладка.** Ошибка «поле не прошло» вместо «поле `codec` устройства» — смягчаем указателем на поле (`/properties/mode`) и именем вида в ответе.

**Баланс.** Для расширяемых VMS вопрос не «окупится ли», а «можно ли без этого». Объекты psim-плагинов без описаний видов WebUI не настроит вообще, поэтому ядро нужно уже для первого плагина. Для известных видов переход окупается раньше всего на потоке правок: 42 пункта из 116 в запросах w2c за пять дней — ровно те правки, что исчезнут. Если не переходить, каждый плагин и каждая подсистема — запрос, правка контракта, сервера, WebUI и тестов, по образцу `953777e`, а новые плагины у заказчика без выпуска WebUI невозможны.

**Вывод.** Для расширяемых систем преобладает приём «схема вида с сервера + общий клиент + необязательный свой UI для важных видов». Наше предложение отличается от Kubernetes подсказками формы, командами, событиями и правами (в CRD их нет), а от Milestone — тем, что код UI на вид не нужен. Документированного «возврата от универсальной модели к типизированной» в VMS не нашли. Найдены предупреждения: антипаттерн «внутренней платформы» ([Inner-platform effect](https://en.wikipedia.org/wiki/Inner-platform_effect)) и то, что Rancher и Headlamp всё равно добавляют экраны для своих видов поверх общего. Отсюда профили и ручные экраны.

## 5. Пункты запроса

Каждый пункт: что изменить в контракте, зачем, что сломается у тех, кто уже работает по контракту. Наброски схем — приложение Д.

1. **Описание вида `UnitKind` и `GET /kinds`.** `GET /kinds` (список, ETag, `If-None-Match`), `GET /kinds/{kind}`, событие потока `kinds.changed {kinds[]}`. Поля описания:
   - `kind` и происхождение `origin {system, subsystem?, plugin?, pluginVersion?}`;
   - `label`, `labelPlural`, `icon`;
   - `parents[]` (виды-родители; `null` — корень), `children[]`, `dynamicCreate` (спрашивать `creatable`);
   - `capabilities[]` (`rename`, `enable`, `delete`, `move`, `folders`, `bulkSet`);
   - `implements[]` (профили);
   - `schema` — JSON Schema 2020-12 с `x-*`; `schemaPerUnit` (схема зависит от объекта);
   - `actions[]` (`ActionDescriptor`), `events[]` (`id`, `label`, `severity`, `params` — схема данных события), `accessLevels[]`;
   - `setupUi?` (п. 5.11).

   Источники: манифест w2c, `UnitDescriptor`/`factory` NGP, `plugin.json` psim — по полю в приложении В. **Зачем:** новый вид без правки WebUI. **Сломается:** ничего, пока старые пути живы. После перехода — `Reference.deviceKinds`, `deviceParams`, `capabilities.deviceTypes`, `foundDeviceTypes`, `unitTypes`, `writableFields`, `UnitOption`, `UnitProperty` (их заменяет `UnitKind`).
2. **Объект `Unit`:** `uid`, `kind`, `parentId`, `name`, `domainId`, `folders[]`, `version`, `properties` (по схеме вида), `secrets {имя: true}` (какие секреты заданы), `status {link, conditions[], observedVersion, observed}`, `capabilities[]` (что можно с этим объектом сейчас, с учётом прав и состояния). **Зачем:** общие поля отдельно от настроек и от наблюдаемого. **Сломается:** клиенты, читающие `Device`, `Server`, `Archive`, `Volume`, `Folder`, `Domain`. До перехода их отдаём как сейчас.
3. **Операции над объектами:**
   - `GET /units?kind=&parentId=&domainId=&implements=&ref=&q=&cursor=`;
   - `POST /units` (с `idempotencyKey`, вложенные дети — как сейчас у `POST /devices`);
   - `GET /units/{uid}`, `PATCH /units/{uid}` (JSON Merge Patch по `properties` и общим полям, `If-Match`), `DELETE /units/{uid}`;
   - `POST /units/{uid}/move {parentId}`;
   - `POST /units/{uid}/actions/{action}` — `instant` отвечает `result`, `longRunning` — `202` с операцией;
   - `GET /units/{uid}/creatable` — виды и, у NGP, форма создания из `factory`;
   - `GET /units/{uid}/schema` — схема объекта при `schemaPerUnit`;
   - `POST /units/validate` — проверка без записи, «что будет, если».

   Групповые: шаги `/operations` — `set {uid, patch}`, `action {uid, action, params}`, `delete {uid}`; `POST /objects/delete` — по `uid`. **Зачем:** около 12 операций вместо около 35 по видам. **Сломается:** после перехода — `/domains`, `/servers`, `/devices`, `/folders`, `/archives`, `/volumes`, `/devices/{id}/streams` (CRUD). Предметные остаются (п. 5.9).
4. **Ошибки с путём к полю.** `Problem.field` — JSON Pointer (RFC 6901) в теле запроса (`/properties/mode`), плюс `Problem.errors[] {code, field, params}` для нескольких полей сразу. Коды проверки схемы — общие (`VALIDATION_FAILED` с `params.keyword`: `required`, `enum`, `maximum`…). Коды вида — строкой `kind:<код>` с подписью из описания вида. **Зачем:** форма подсвечивает поле незнакомого вида. **Сломается:** клиенты, сравнивающие `field` с простым именем (`field: "parentId"` станет `"/parentId"`). Можно оставить простое имя для полей верхнего уровня.
5. **Топология с сервера.**
   - `TreeNode.kind` — открытая строка, у узла `icon`, `implements[]`;
   - мастер добавления строится по `GET /kinds` (`parents`) и `GET /units/{uid}/creatable`; перенос — по `parents` и `capabilities.move`;
   - `CanCreateChild` psim и `factory` NGP отвечают в `creatable` (с причиной отказа: лимит, лицензия, родитель не готов — `plugin_service.proto:138-180`).

   **Сломается:** `TreeNode.kind` enum, `needsParent`/`parentOpts` в WebUI, `parentFits` в сервере.
6. **Возможности вместо видов.** Кнопка или вкладка видна, потому что она есть в `Unit.capabilities`, в профиле или в `UnitKind.actions`, а не потому что объект — «камера». `Capabilities.deviceTypes` и `writableFields` уходят в описания видов. **Сломается:** `ui-profile.js` и набор `one-domain`: отбор переносится с видов на возможности.
7. **Права и автоматизация для новых видов.**
   - **Права:** у вида — `accessLevels` (по умолчанию `view`, `edit`, `delete`, `create`) и право на каждое действие `action:<id>`. Роль получает уровень на объект (`objectAccess` по `uid`) и на вид (`kindAccess {kind: уровень}`) — для объектов, которых ещё нет. Права psim (ACL объекта в `meta.conf`, ADR-010) и NGP ложатся на `objectAccess`.
   - **Автоматизация:** событие правила `{source: "unit", kind, event, match}` из `UnitKind.events`, действие `{type: "unitAction", kind, action, params}` из `UnitKind.actions` с `ruleAction: true`. Форма параметров — по схеме. `Reference.ruleTriggers`/`ruleActions` остаются для своего (расписание, режимы).

   **Сломается:** `Role`, `RoleGlobal` (коды `dCam`, `dTel`… — часть уходит в `kindAccess`), `RuleTrigger.source` и `RuleAction` получают новые варианты; старые продолжают работать.
8. **Подписи и переводы.** Описания видов отдают `label: {key, text}`: ключ и текст на языке из `Accept-Language`. Бэкенд переводит по `langs/` psim (ADR-006), NGP уже локализует сам по `accept-language` (`ConfigurationService.proto:400-409`), у w2c тексты в `display` манифеста. **Меняется договорённость** «сервер отдаёт коды, подписи — в интерфейсе» (`api/README.md`, «Тексты») — для видов из систем подписи приходят с сервера. Открытый вопрос В-2.
9. **Что остаётся, что уходит, что становится частным случаем.** Таблица по каждой схеме и операции — приложение Д.3. Кратко:
   - **остаются:** `/operations`, `/stream`, `/access*`, `/rules*`, `/schedules`, `/day-groups`, `/modes`, `/maintenance-windows`, `/domains/{id}/scenarios*`, `/settings`, `/licenses`, `/journal`, `/assist`, `/test/*`, а также живое видео, разговор, PTZ, шкала, воспроизведение, удержания, отметки, `archive-fetch`, `archive-watches`, `archive-scans`, поиск в сети — **с адресом по `uid` и доступностью по профилю**;
   - **частный случай ядра:** домены, серверы, устройства, папки, хранилища, тома, потоки камеры, единицы СКУД, `POST /devices/probe` и `/volumes/{id}/format` (действия), `/servers/assign` (групповой `move`);
   - **уходят:** `DeviceType`, `TreeNode.kind` enum, плоский `Device`.
10. **Не-единицы.**
    - **Таблицы** w2c — вид с `shape: document`: один объект, `properties` — документ целиком, запись `PUT`/`PATCH` целиком с `If-Match`.
    - **Общие настройки домена** — свойства с `x-inherit`; в ответе `inherited {имя: {from: uid}}`.
    - **Параметры уровня плагина** (psim `Configure`) — объект вида `plugin:<id>` (в NGP это и есть юнит `PluginV2.<id>`, ADR-009 §2) с `schema` из `parameters` манифеста.
11. **Страница настройки плагина (`setup_ui`) — необязательно.**
    - **Описание:** `UnitKind.setupUi {url, kinds[], mode: "iframe"}`.
    - **По умолчанию** WebUI показывает форму по схеме. Переключатель «Страница плагина» открывает iframe: `sandbox="allow-scripts allow-forms"` (без `allow-same-origin`), отдельный источник, параметры `?uid=&kind=&lang=` — как у эмулятора psim (`psim_platform_emulator/webui/webui.html:628-705`).
    - **Запись:** страница пишет через API своего плагина. Конфигуратор видит итог событием `entity.changed` и не доверяет данным из iframe.
    - **Обмен сообщениями** `postMessage` — только `ready`, `height`, `dirty`, `saved`.

    **Зачем:** автор плагина может сделать свой экран, но без него вид всё равно настраивается. **Сломается:** ничего. Нужно, чтобы CSP консоли w2c разрешала `frame-src` источника плагина — вопрос 8 раздела 6.
12. **План перехода и сосуществование.**
    1. Ядро (`/kinds`, `/units`, `creatable`, `actions`, `kinds.changed`) рядом с нынешними путями. Объекты — те же записи, `uid` = нынешний `id`. Набор `demo.json` получает описания видов и вид psim `security_controller`, плюс «незнакомый» вид `test.unknown` для приёмки.
    2. WebUI: форма по схеме и мастер по описаниям для видов без ручного экрана; затем ручные экраны переводятся на профили.
    3. Права и автоматизация — `kindAccess`, события и действия из описаний.
    4. Удаление CRUD-путей по видам, `DeviceType`, плоского `Device`.

    Тесты `tests/api-*.js` — общие сценарии ядра плюс проверка описаний. `tools/check_api.py` проверяет описания видов набора по мета-схеме. У команды w2c ломаются отвеченные пункты о полях `Device` (раздел 6, вопрос 4). Ломающую правку владелец разрешил; порядок — на усмотрение altumur.
