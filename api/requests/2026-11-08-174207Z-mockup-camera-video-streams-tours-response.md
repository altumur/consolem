## Кто что делает

- **Данные вида** (свойства, события и команды существующего вида, значения `reference`) mockup добавляет сам, без уведомления. Так решил владелец 2026-11-16 в [ответе о пробелах против Axxon One](2026-11-12-104207Z-mockup-axxon-one-gaps-contract-response.md), раздел 1.
- **Добавочную правку механизма** (новое поле общей схемы, новое поведение сервера, расширение `x-*`) mockup может внести сам. Порядок — скилл `api-contract`, раздел «Правка контракта без владельца». После правки mockup пишет владельцу уведомление `…-done-request.md`.
- **Ломающую правку** делает только владелец.

## 1. Режим потоков камеры

Принято.

- Флажок `streamsMode` (`device`, `console`; умолчание — `device`) — свойство вида `camera` в `api/fixtures/demo.json`.
- В режиме `device` сервер объявляет поля с `x-dev` только для чтения. Для этого схема камеры получает часть `allOf`: `if` по `streamsMode: device`, `then` — `readOnly` у полей `x-dev`. Камера отдаёт решённую схему в `GET /units/{uid}/schema` (`schemaPerUnit`). Сейчас встроенный сервер проверяет правку объекта только по схеме вида (`kinds.validate` в `api/kinds.js`), а не по решённой схеме объекта. Проверку правки по решённой схеме объекта (`unitSchema`) нужно ввести для всех видов со `schemaPerUnit`. Это общий механизм, его делает владелец в той же правке, что лицензии и файлы. Флажок `streamsMode` и части `allOf` камеры mockup делает с уведомлением.
- Новый отказ 409 не нужен. Правку поля только для чтения сервер уже отклоняет общим `422`.
- В `api/README.md`, в строке `x-dev` таблицы «Расширения описаний», mockup называет `streamsMode` как флажок, о котором там сказано.

Кто делает: mockup, с уведомлением владельцу. Правка меняет поведение сервера: поле становится только для чтения по значению другого поля.

Сначала нужно сделать п. 6 [ответа о параметрах драйвера камеры](2026-11-09-182805Z-mockup-camera-driver-params-response.md): `schemaPerUnit: true` у вида `camera`. Сейчас его в наборе нет.

## 2. Параметры потока

Данные вида. Их делает mockup, без уведомления.

- `codec`, `codecProfile`, `bitrateMode`, `bitrateKbps`, `quality`, `gopFrames`, `liveUse` — свойства вида `stream`.
- Набор и пределы зависят от драйвера. Поэтому mockup задаёт их частями `allOf` по драйверу, как параметры драйвера камеры. Если виду `stream` нужна своя схема у каждого потока, mockup ставит ему `schemaPerUnit: true`.
- Параметры, которые консоль записывает в камеру, получают `x-dev`. Тогда п. 1 сам закрывает их правку в режиме `device`.
- `codec` перестаёт быть только для чтения. Это расширение, а не ломающая правка: старый клиент поле читает, как раньше.

## 3. Переход в пресет из консоли

Ждёт отдельного API видео. Живое управление PTZ — работа оператора, а не настройка. Владелец предложил вынести его из общего контракта: `docs/2026-11-16-kontrakt-i-podsistemy-predlozhenie.md`, п. 7. Команда `preset` остаётся `ruleOnly`.

## 4. Туры PTZ

Решение делится на две части.

- **Модель тура — данные вида.** Её делает mockup, без уведомления. Туры — свойство камеры `tours`: `id`, `name`, `steps` (`preset`, `dwellSec`, `speed`), `order`, `pauseSec`, повтор, `onManual` (`pause`, `stop`), `resumeSec`, `resumeFrom`, `idleStartSec`. Пределы от камеры (число туров, число точек, пределы времени и скорости) — свойства камеры только для чтения, как `presetMax`. Команда правила `ptz.tour` называет тур по `id` из `tours`.
- **Пуск, пауза, состояние тура и событие о смене состояния** ждут отдельного API видео (п. 3).

Где идёт тур, в камере или на сервере, решает бэкенд. Форме нужно правило `onManual` из настроек тура, и оно действует одинаково в обоих случаях.

Данные вида. Их делает mockup, без уведомления: свойство камеры только для чтения, например `ptzAxes`, рядом с `ptz`.
