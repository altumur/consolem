# Запрос от команды mockup: уровень журнала сервера и очистка журналов

2026-11-16 · коммит контракта `f080e13` (0.12.0) · от команды mockup, для владельца контракта

Кому: владелец контракта

**Статус: новый**

## Что мы делаем

Мы закрываем пробел A22 против Axxon One (`docs/axxon-one-gaps.html`): администратор меняет уровень журнала сервера и очищает журналы сервера из карточки сервера. В Axxon One объект «Сервер» даёт блок **Server logging management** (документ lexiro 568876): **Server logging level** — TRACE, DEBUG, INFO (по умолчанию), WARN, ERROR — и кнопку **Clear** у **Clearing server logs**. Уровень действует только до перезапуска сервера. После перезапуска сервер берёт уровень из утилиты управления журналами на самом сервере.

Сейчас в контракте этого нет: у вида `server` нет ни уровня журнала, ни команды очистки, а в опциях домена есть только срок хранения системного журнала. Прототип 68 (`index_68_uroven-zhurnala.html`) рисует блок «Журнал сервера» на вкладке «Общие» карточки сервера на заглушке: значения живут в браузере.

## Источники

Axxon One 3.0, документ lexiro 568876 («Server», раздел «Manage server logging»). Живого сервера Axxon мы не проверяли.

## Что нужно

Имена полей и команд — наше предложение. Владелец контракта может выбрать другие.

1. **Уровень журнала сейчас.** Поле вида `server` `logLevel`: `TRACE`, `DEBUG`, `INFO`, `WARN`, `ERROR`. Сервер принимает новое значение сразу, без перезапуска. Это значение действует до перезапуска сервера, поэтому его удобнее менять командой `POST /units/{uid}/actions/setLogLevel` с параметром `level`, а не правкой настроек объекта: правка настроек в черновике «Сохранить» обещала бы, что значение останется.
2. **Уровень после перезапуска.** Поле вида `server` `logLevelBase`, только для чтения: уровень из утилиты управления журналами на сервере. Зачем: консоль говорит «после перезапуска сервер вернётся к уровню INFO» и даёт кнопку «Вернуть INFO». Без поля консоль знает только умолчание Axxon One (INFO).
3. **Размер журналов.** Поля вида `server`, только для чтения: `logFiles` (число файлов журнала), `logBytes` (размер), `logOldestAt` (время самой старой записи). Зачем: администратор видит, сколько места занимает журнал, особенно на уровнях TRACE и DEBUG. Окно очистки просит ввести число файлов (правило макета «Удаление — с вводом числа»).
4. **Очистка журналов.** Команда `POST /units/{uid}/actions/clearLogs`: сервер удаляет все свои файлы журнала. Уровень журнала не меняется. Ответ — новые `logFiles`, `logBytes`, `logOldestAt`. Если очистка занимает время — `longRunning` с операцией.
5. **Событие в потоке.** Изменение `logLevel` (также после перезапуска сервера) и очистка — событие с новой версией объекта. Тогда карточка обновляется сама, и второй администратор видит новый уровень.
6. **Возможность.** Признак в `capabilities` (например, `features.serverLogLevel`): не каждый бэкенд умеет менять уровень журнала. Без признака консоль прячет блок.

## Что сломается

Ничего. Поля новые, необязательные; поля пп. 2 и 3 только для чтения. Команды новые и необязательные: признак п. 6 говорит клиенту, есть ли они. Клиент, который их не знает, пропускает поля по правилу контракта о незнакомых полях.
