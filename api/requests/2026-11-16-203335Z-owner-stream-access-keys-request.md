## Суть

Обе команды согласны, что учётку потока нужно убрать. Учётка потока — отдельная сущность со своим именем, паролем и **своим списком камер** (`Access.streamGrants`). Её недостаток — второй набор прав рядом с ролями.

w2c просит сохранить у пользователя два свойства учётки:
- «только поток»: с этим паролем нельзя войти в консоль и в API;
- пароль придумывает сервер и показывает один раз.

w2c предлагает `AccessUser.streamOnly` и пароль от сервера.

Владелец контракта предлагает вместо этого **ключи доступа у пользователя**, как пароли приложений и токены в других системах:
- у пользователя может быть несколько именованных ключей;
- каждый ключ годится только для потока;
- своих прав у ключа нет: он видит те же камеры, что и пользователь;
- каждый ключ отзывается отдельно.

Ниже — что нужно, как это делают другие, пять вариантов с плюсами и минусами, рекомендация и вопросы к обеим командам.

## 1. Что нужно

Внешний клиент — не человек, а программа или устройство:
- видеостена;
- сторонняя VMS или регистратор, который забирает потоки;
- облачный приёмник;
- программа аналитики.

Из этого следуют требования. Номера (Т1…Т9) используются в сравнении ниже.

| № | Требование | Почему |
|---|---|---|
| Т1 | Одна модель прав: камеры, которые программа видит, задают роли, уровни и папки в `Access` | Иначе администратор следит за двумя местами. Это довод запроса mockup |
| Т2 | Утечка секрета из чужой программы не даёт войти в консоль и в API | Секрет лежит в настройках чужой программы, часто открытым текстом. Мы не управляем тем, как его хранят |
| Т3 | Одну программу можно отключить, и остальные при этом работают | Утечка у одной стены не должна гасить все стены |
| Т4 | Секрет можно сменить без простоя | Плановая смена, увольнение подрядчика |
| Т5 | Видно, какая программа и когда брала поток | Расследование, журнал аудита (`actor`) |
| Т6 | Секрет не придумывает человек | Человек повторяет свои пароли |
| Т7 | Работает с любой программой, которая умеет RTSP | RTSP знает только имя и пароль (Basic или Digest, RFC 2326 и RFC 7826). Заголовков с токеном там нет |
| Т8 | Работает на любом бэкенде | Например, если бэкенд отдаёт RTSP прямо из Axxon One, без своего шлюза |
| Т9 | Просто для администратора | Меньше новых понятий и экранов |

## 2. Как это делают в индустрии

### 2.1. Пароли приложений

Сервис выпускает отдельный пароль для программы, которая умеет только «имя и пароль». Пароль показывается один раз, у него есть имя, и его отзывают отдельно.

- **Google, пароли приложений.** Пароль из 16 символов для почтовых и календарных программ, которые не умеют OAuth. Пользователь видит список паролей и отзывает любой из них.
- **Apple, пароли для приложений** (app-specific passwords). Для сторонних клиентов почты, календаря и контактов. Пароль выдаётся на программу, его отзывают по одному.
- **Microsoft 365, пароли приложений** при многофакторном входе. Для старых клиентов, которые умеют только пароль.

Общее у всех трёх:
- секрет придумывает сервер (Т6);
- секрет передают вместо пароля (Т7);
- одну программу отключают, не трогая остальные (Т3).

Слабое место: такой пароль обычно даёт доступ ко всему, что умеет протокол. Поэтому область действия должна быть узкой: у нас — только поток.

### 2.2. Токен вместо пароля

- **GitHub.** С августа 2021 года `git` по HTTPS не принимает пароль от аккаунта, только персональный токен (personal access token), переданный в поле пароля. У токенов fine-grained есть:
  - область: какие репозитории и какие действия;
  - срок действия;
  - отметка о последнем использовании.

  Это ближе всего к нашему случаю: протокол знает только имя и пароль, а секрет — токен с узкой областью.
- **GitLab:** personal access tokens и deploy tokens. Deploy token — это токен только на чтение репозитория или реестра, для серверов сборки.
- **Atlassian (Jira, Confluence):** API-токен вместо пароля при Basic-входе в REST API.

### 2.3. Сервисная учётная запись и ключи

Для программ заводят отдельную учётную запись. Права выдают ей как обычному пользователю, а программа получает ключ этой записи.

- **AWS IAM.** Пользователь или роль и ключи доступа (access keys). У одного пользователя может быть до двух ключей одновременно. Это сделано для смены без простоя: выпустить новый, перевести программы, отозвать старый (Т4). AWS советует для программ роли с временными ключами, а долгоживущие ключи — только там, где иначе нельзя.
- **Google Cloud.** Сервисные аккаунты (service accounts) и их ключи. Права — у аккаунта, ключей может быть несколько, у каждого видна дата создания.
- **Kubernetes.** ServiceAccount и токен. Права задают через RBAC, как у пользователя, а токен — только способ входа.

Общее у всех трёх: права живут у учётной записи (Т1), а ключ — только способ войти. Это прямо отвечает доводу mockup про одну модель прав.

### 2.4. Видеонаблюдение

- **Axxon One** (документация 3.0, «Configuring the RTSP server», lexiro 291998). RTSP-сервер принимает имя и пароль пользователя Axxon One. Отдельных учёток и ключей нет. Это вариант А ниже.
- **ONVIF** (Device Management, `CreateUsers`). У устройства есть пользователи с уровнями `Administrator`, `Operator`, `User`. RTSP-поток берут под этими пользователями, обычно с Digest. Отдельных ключей стандарт не задаёт.
- **Регистраторы и камеры массового рынка** (например, Hikvision). RTSP — под пользователем устройства, а у пользователя есть права на просмотр по каналам. Это тоже вариант А, с правами у пользователя.

Вывод: в видеонаблюдении обычно берут поток под пользователем системы, с его правами. Ключи для потока — практика облачных и ИТ-систем, в VMS их делают реже. Значит, вариант А должен работать всегда, а ключи — дополнение для систем, где перед RTSP стоит свой шлюз.

### 2.5. Подписанные ссылки и временные токены

- **Amazon S3 presigned URL, CloudFront signed URL, Wowza SecureToken.** Ссылка на поток с подписью и сроком в несколько минут. Сервер проверяет подпись, а пароля в ссылке нет.

Это хорошо подходит **своему** веб-плееру: он сам получает свежую ссылку. Чужая видеостена или регистратор так не умеют. Им нужен адрес, который работает неделями, а продлевать ссылку они не будут. Поэтому для внешних программ этот способ не подходит. Мы его упоминаем, чтобы было видно, что его рассмотрели.

### 2.6. Клиентские сертификаты (mTLS)

Программа входит по своему сертификату, а не по паролю. Это самый надёжный способ, но RTSPS с клиентскими сертификатами поддерживают немногие RTSP-клиенты и видеостены. К тому же нужна выдача и отзыв сертификатов. Для нашего случая сейчас это слишком дорого. Упоминаем по той же причине.

## 3. Варианты

### А. Пароль пользователя консоли (как в Axxon One)

Программа входит под именем и паролем обычного пользователя и видит его камеры.

Плюсы:
- ничего нового: ни путей, ни экранов (Т9);
- работает на любом бэкенде, в том числе прямо на RTSP Axxon One (Т8);
- одна модель прав (Т1).

Минусы:
- пароль от консоли лежит в чужой программе. Утёк — по нему можно войти в консоль и в API и всё настроить (нет Т2);
- сменил пароль — встали все программы этого пользователя (нет Т3, Т4);
- в журнале видно только пользователя, но не программу (Т5 частично);
- пароль придумывает человек (нет Т6).

Как смягчить: завести для программ отдельного пользователя с ролью «только просмотр», по одному на программу. Это помогает с Т3 и Т5, но утечка всё равно даёт вход в консоль с этой ролью.

### Б. `streamOnly` у пользователя и пароль от сервера (предложение w2c)

Особый пользователь, который может только брать поток. Пароль ему придумывает сервер и показывает один раз.

Плюсы:
- утечка не даёт войти в консоль (Т2);
- пароль придумывает сервер (Т6);
- одна модель прав (Т1);
- одно поле и одна команда.

Минусы:
- один пароль на пользователя. Для десяти стен — либо десять пользователей, либо одна общая утечка (Т3 только через много пользователей);
- смена без простоя невозможна: новый пароль сразу отменяет старый (нет Т4);
- появляется особый вид пользователя. В списке пользователей смешаны люди и программы, и администратору надо понимать разницу (Т9 частично);
- на RTSP Axxon One признак «только поток» сам не работает: у пользователя Axxon One нет такого ограничения. Бэкенду нужен свой шлюз или своя проверка (Т8 частично).

### В. Ключи доступа у пользователя (предложение владельца контракта)

У любого пользователя может быть несколько ключей. Каждый ключ:
- годится только для потока;
- имеет имя;
- выпускается сервером и показывается один раз;
- отзывается отдельно;
- хранит дату последнего использования.

Права у ключа — пользователя. Ключ передаётся вместо пароля: `rtsp://videowall:<ключ>@сервер/…`.

Плюсы:
- одна модель прав (Т1): своих камер у ключа нет;
- утечка не даёт войти в консоль и в API (Т2);
- одну программу отключают, остальные работают (Т3);
- смена без простоя: выпустить новый ключ, перевести программу, отозвать старый (Т4), как у AWS;
- в журнале видны пользователь и имя ключа (Т5);
- секрет придумывает сервер (Т6);
- работает с любым RTSP-клиентом (Т7);
- особого вида пользователя нет: ограничение «только поток» задаёт ключ, а не пользователь;
- так делают GitHub, Google, Apple, AWS, Google Cloud (раздел 2). Администратору с ИТ-опытом схема знакома.

Минусы:
- ключ должен проверять тот, кто стоит перед RTSP. Встроенный RTSP Axxon One ключей не знает. У w2c есть шлюз потоков, а у другого бэкенда его может не быть (Т8 только с шлюзом);
- три новых пути и экран ключей в карточке пользователя (Т9 частично);
- если отключить человека, перестают работать и его ключи. Для программ лучше заводить служебного пользователя, и это надо объяснить в документации.

### Г. Учётки потоков (то, что есть сейчас)

Плюсы: Т2, Т3, Т6, Т7.

Минусы:
- вторые права рядом с ролями (нет Т1). Это причина запроса mockup;
- у учётки нет пользователя, поэтому журнал не связывает её с людьми и ролями (Т5 частично);
- новое понятие, которого нет в Axxon One (Т9).

### Д. Подписанные ссылки

Подходят только своему плееру, а не чужим программам (раздел 2.5). Как способ для внешних клиентов не рассматриваем.

## 4. Что предлагает владелец контракта

1. **Снять учётки потоков сразу,** без шага `deprecated` (п. 1 запроса mockup). У w2c их нет в поставке, других клиентов нет.
2. **Вариант А — правило по умолчанию для любого бэкенда** (п. 2 запроса mockup). Внешний клиент входит под именем и паролем пользователя. Живое видео он получает по праву смотреть камеру, архив — по праву смотреть архив. Права — из `Access`.
3. **Вариант В — возможность.** Бэкенд объявляет её, если умеет проверять ключи (`capabilities.operations`). Консоль показывает ключи только тогда. Б не делаем: В закрывает всё, что даёт Б, и ещё Т3, Т4, Т5.
4. **Имя, которое не годится для RTSP** (п. 3 запроса mockup), — признак в ответе, без нового отказа. Например, `AccessUser.streamLoginInvalid: true`. Пользователя из каталога консоль не называет сама, поэтому отказ отрезал бы его от консоли целиком.
5. **В документации** — совет: для программ заводить служебного пользователя с ролью на нужные камеры и выпускать ключи ему, а не человеку.

Набросок контракта для В (имена обсуждаемы):

- `GET /access/users/{id}/keys` — список: `id`, `name`, `createdAt`, `lastUsedAt`, `expiresAt` (если решим про срок);
- `POST /access/users/{id}/keys` `{name, expiresAt?}` → `{id, name, secret}`. `secret` приходит один раз, сервер хранит только проверочное значение;
- `DELETE /access/users/{id}/keys/{keyId}` — отозвать;
- ключи — команды, а не часть черновика прав (`/access/apply`): секрет не попадает в черновик, в историю и в план;
- в журнале аудита — `actor` пользователя и имя ключа. Выпуск и отзыв ключа — записи журнала.

### Тонкости, о которых нужно договориться

- **Basic или Digest.** При Digest сервер должен знать пароль или его хеш, привязанный к realm (HA1 = MD5(имя:realm:пароль)). Значит, ключ нельзя хранить только стойким хешем. Возможные ответы:
  - Basic только поверх RTSPS (TLS), тогда ключ хранится стойким хешем;
  - Digest, тогда шлюз хранит HA1, а сам ключ не хранит.

  То же касается и варианта А.
- **Имя в RTSP-адресе.** Логин пользователя или отдельный идентификатор ключа? Если логин, шлюз проверяет ключ среди ключей этого пользователя. Логин из каталога может не годиться для RTSP (п. 4 выше). Тогда помогает имя-идентификатор ключа, например `key-3f2a`.
- **Отключили пользователя** (`enabled: false`) — его ключи перестают работать сразу. Включили снова — ключи работают снова, если их не отозвали.
- **Срок ключа.** GitHub его требует или настоятельно советует, AWS — нет, Google — по политике организации.
- **Число ключей.** У AWS ограничение 2 на пользователя, у Apple — 25. Нам, вероятно, хватит ограничения в `reference`.
