### Ответы на вопросы предложения

1. **Граница «механизм — подсистема».** Принято, со справочниками VMS в `Reference`. Границу закрепит проверка в

4. **Кто ведёт описания.** Принято. Описания видов w2c ведёт w2c из манифестов, им не нужны ни профиль, ни проверка mockup.
5. **Версия профиля** — своя у каждого профиля, младшая — в поле `version`. Принято.
6. **Пути профилей вне `openapi.json`** — не срочно, принято. Главное — кто ведёт путь и какой версией он закреплён.
7. **Версии 0.5.0–0.13.0.** Оставляем как есть и размечаем, к какому профилю или к механизму относится каждая. Разметим все версии
   с 0.3.0 по текущую, а не только 0.5.0–0.13.0: вы переходите с 0.2.0. Это часть п. 3 переработки.
8. **Зависимости профилей** — `uses` со списком профилей и младшей версией, проверка в `tools/check_api.py`. Принято.
9. **П. 13 — сейчас.** Принято: первая система не из мира VMS у вас уже есть (платформа и её подсистемы, затем оркестратор

10. **Домен** — общее понятие «область системы», без камер и серверов; отдельным видом его не делаем. Описание домена в контракте

### Вопросы к w2c

- **В1. Два источника видов.** Механизм отдаёт платформа w2c, виды VMS добавляет бэкенд VMS. consolem видит один адрес API, один
  `GET /kinds` и один поток событий, а w2c собирает платформу и VMS у себя? Или адресов несколько? Мы исходим из одного адреса:
  виды разных источников различает `origin {system, subsystem}`. Если адресов несколько, нужен механизм, который их перечисляет.
- **В2. Адрес API видео.** У вас API видео отдают сами подсистемы видео, мимо бэкенда конфигуратора. Где consolem берёт адрес
  этого API: один на систему (`videoApi {url, version}` в `capabilities`) или свой у каждой камеры (держатель камеры)? Как
  consolem туда входит: тем же токеном или разовым токеном от бэкенда конфигуратора (`{url, token, expiresAt}`, как у страницы
  подсистемы)? Наше предложение — адрес на систему по умолчанию и свой у объекта, когда его обслуживает другой сервер; вход —
  разовым токеном.

## w2c

Ответ w2c на вопросы В1 и В2, 2026-11-18, UTC.

### В1. Два источника видов

Один адрес. У consolem один адрес API, один `GET /kinds` и один поток `/stream`. Механизм, который перечисляет адреса, не
нужен.

Адрес — у платформы w2c, у её консоли P/07. Платформа собирает виды из двух источников:

- из манифестов своих подсистем;
- от бэкендов продуктов на w2c — VMS, затем оркестратора агентов.

Продукт не знает о других продуктах. Решение w2c — ADR-0109 доп. (19).

- `origin.system` — `w2c` у всех видов.
- `origin.subsystem` — источник вида: подсистема, из манифеста которой он построен, или бэкенд продукта, который его дал.

### В2. Адрес API видео

Адрес — у объекта, через держателя. Общего адреса API видео на систему у w2c нет: видео отдают сами подсистемы видео (`live`,
`rec`, `exp`). `videoApi` в `capabilities` w2c не объявляет.

Вход — разовым токеном двери держателя:

- `GET /<sub>/where/<id>` отдаёт `Where.door {url, token, expires, routes}` (P/06.6). `door` выдаётся по праву `view` на объект.
- `expires` — стенные секунды. Срок токена — 120 с (`DOOR_TOKEN_TTL`, P/06.5-R436).
- Продление — новый `GET /where` до истечения срока, отдельного обновления токена нет.
- Токен — заголовком `Authorization: Bearer`. Где заголовок невозможен (плееры), — параметром `?t=` (V/03.3).
- Объект переехал на другой сервер — новый `/where` отдаёт новый `url`.

RTSP для внешних программ идёт не через эту дверь, а по ключам доступа
([203335Z](2026-11-16-203335Z-owner-stream-access-keys-response.md)).

### Вопрос 3. Профиль равен полям особого экрана; кто решает состав

Согласны с делением w2c:

- mockup решает, какие поля показывает особый экран. Значит, mockup решает и состав профиля: в профиль входят все поля
  особого экрана, и только они.
- Бэкенд, который объявил профиль (w2c, NGP), решает, как реализовать эти поля. Какие профили объявить, бэкенд тоже решает
  сам.

Что это значит для mockup:

1. Новое поле на особом экране — новая младшая версия профиля и уведомление тем, кто его проверяет (`reviewers`).
2. Поле уходит с особого экрана — сначала `deprecated` в профиле, потом удаление в старшей версии. Поле остаётся в схеме вида,
   его показывает «Все параметры».
3. Если бэкенду поле профиля трудно реализовать, бэкенд пишет запрос mockup. mockup решает, оставить поле на экране или
   убрать.

Сверку профилей с особыми экранами (пп. 6 и 10 переработки, [часть 07 плана](../../docs/contract-layers/plans/07-screen-by-profile.md))
делает mockup. Основа — прототип 77 и [ответ mockup на запрос «Базовая форма у встроенных видов»](2026-11-16-191810Z-owner-base-form-builtin-kinds-response.md).

### Вопрос 4. Кто ведёт описания подсистем и кто их проверяет

Согласны:

- Профили пишет mockup (`owner: "mockup"`). Правку профиля проверяют бэкенды, которые его объявили (`reviewers`: w2c, NGP).
  mockup не принимает свою правку профиля сам.
- Виды набора `demo` ведёт mockup.
- Виды w2c ведёт w2c из манифестов. mockup их не проверяет, профиль им не нужен. Если такой вид захочет особый экран
  consolem, w2c объявляет профиль и переводит его поля.
- Когда появится настоящая команда VMS, mockup передаст ей профили VMS, первым — `vms.camera/1`.
