### Вопрос 1. Ключ у пользователя вместо учётки потока

Устраивает. Своих камер у ключа нет: он видит то, что видит пользователь. Это и было доводом нашего запроса [«Снять учётки потоков»](2026-11-12-094349Z-mockup-drop-stream-accounts-request.md). Учётки потоков снимайте сразу, без шага `deprecated`: консоль показывает раздел «Учётки потоков» только при `listStreamAccounts`. Когда учёток не станет, раздел пропадёт сам. Код раздела mockup уберёт в той же версии контракта.

### Вопрос 2. Где консоль показывает ключи

В двух местах:
1. **Вкладка «Ключи доступа» в карточке пользователя** («Права» → пользователь). Здесь администратор выпускает и отзывает ключи. В списке видно имя, дату выпуска, срок и последний вход. Секрет консоль показывает один раз, сразу после выпуска, вместе с готовым адресом RTSP для копирования.
2. **Раздел «Ключи доступа» в «Правах»** — на месте раздела «Учётки потоков». Он показывает все ключи системы: владельца, имя, последний вход, срок. Раздел нужен при утечке и при аудите: какие программы берут видео, какие ключи давно не входили, у каких ключей кончается срок. Здесь ключ тоже можно отозвать, но выпуск — только из карточки пользователя.

Для раздела нужен путь со списком всех ключей. В наброске его нет, есть только ключи одного пользователя. Предлагаем `GET /access/keys` с отбором по пользователю и страницами, как у других списков: `id`, `userId`, `name`, `createdAt`, `lastUsedAt`, `expiresAt`.

Обе части консоль показывает только при возможности в `capabilities.operations` (п. 3 раздела 4).

### Вопрос 3. А — правило, В — возможность

Согласны. А работает на любом бэкенде, в том числе на RTSP Axxon One без своего шлюза. Без возможности ключей консоль ничего о ключах не показывает. Карточка RTSP-сервера тогда говорит, что программа входит под пользователем консоли, и советует завести для неё служебного пользователя с ролью «только просмотр».

### Вопрос 8 (обеим командам). Срок действия

По желанию. При выпуске есть поле «Действует до», пустое поле — без срока. Обязательный срок не подходит: видеостена и регистратор работают годами, и ключ, который кончился, остановит их без предупреждения. Консоль сама предупреждает: в списках ключ с близким концом срока отмечен, а за 14 дней до конца срока консоль показывает его в сводке «Прав». Нужен ли сигнал и в журнале (событие «срок ключа скоро кончится»), решает владелец контракта.

### Вопрос 9 (обеим командам). Ограничение числа ключей

Нужно, и число задаёт бэкенд в `reference`, например `limits.accessKeysPerUser` (имя — на ваше усмотрение). Консоль показывает «Ключей: N из M» и выключает «Выпустить ключ» на пределе, с причиной. Сервер на пределе отвечает `422` с машинным кодом, например `LIMIT_REACHED`.

### Вопрос 10 (обеим командам). Требования, которых нет в разделе 1

1. **Т10. Кто выпускает ключи.** Выпуск и отзыв — отдельное право, как управление пользователями. Иначе любой, кто может править пользователя, выпустит себе ключ с его камерами. Сам пользователь выпускает ключи себе только с этим правом. Консоль проверяет право, как у других действий (`can(...)`).
2. **Т11. Имя в адресе RTSP — идентификатор ключа, а не логин.** Так проще всем:
   - имя из каталога, которое не годится для RTSP (п. 4 раздела 4), не мешает;
   - шлюз находит ключ сразу, без перебора ключей пользователя;
   - в журнале шлюза сразу видно, какой ключ входил;
   - логин пользователя не попадает в настройки чужой программы.
   Пример — `rtsp://key-3f2a:<секрет>@сервер/…`. Окончательно решает w2c (вопрос 5), консоли подойдёт любой вариант: адрес она строит по ответу `POST …/keys`.
3. **Т12. Пользователь из каталога (LDAP, AD).** Каталог отключил пользователя — его ключи перестают работать сразу, как при `enabled: false`. Иначе уволенный сотрудник сохранит доступ к видео через ключ. Для программ это ещё один довод за служебного пользователя консоли, а не из каталога.

Других вариантов, кроме А–Д, не видим.
