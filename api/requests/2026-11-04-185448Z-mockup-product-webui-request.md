# Макет как основа продукта: условия и план перевода

- Дата: 2026-11-04
- Команда: `mockup`
- Коммит контракта: `1a1c1fe`
- Статус: новый

Предложение: макет (`index.html`) становится основой продуктового WebUI консоли VMS, отдельной команды, которая пишет свой интерфейс по образцу, нет. Мы оценили подход и считаем его верным: нет второй реализации, которая расходится с образцом; контракт, критерии приёмки, сценарии интерфейса и сборка под CSP уже есть; не нужна передача знаний.

Но подход работает, только если вместе с ним меняются правила работы. Сейчас макет уже уходит в продукт (`tools/build_webui.py` → w2c, `/backend/`), а код и процесс устроены как у макета:

| Что | Сейчас |
|---|---|
| Код интерфейса | один встроенный скрипт в `index.html`, около 25 тыс. строк, глобальные функции и состояние |
| Разметка | строками через `innerHTML` (`paintMain`), экранирование вручную (`escHtml`, около 1200 вызовов) |
| Проверки | контракт, тесты API, около 8 тыс. строк сценариев `tests/ui-*.js`, `api/ACCEPTANCE.md` |
| Процесс | все пушат в `main` без PR; с 1 октября около 570 коммитов от 5–6 авторов, включая агентов |
| Договорённость с фронтендом | `api/FRONTEND.md`: «ни целиком, ни частями в продукт его не переносят» |

Если оставить всё как есть и просто отдавать сборку в продукт, проблемы безопасности и поддержки будут копиться, и через год переписывать станет дороже, чем сейчас. Ниже — что нужно решить. Пункты 1–5 недорогие и нужны до первой установки у заказчика; 6–7 — перевод кода, это месяцы.

## 1. Записать решение: макет — основа продукта

**Что нужно.** Переписать вводную часть `api/FRONTEND.md` («Для чего этот прототип», «Чем он не является»): `index.html` — код продукта, а не только эталон. При необходимости — строка об этом в `api/README.md`.

**Зачем.** Сейчас документ прямо запрещает то, что предлагается. Командам VMS и новым людям должно быть понятно, что `index.html` и есть WebUI.

**Что сломается.** Ничего в контракте. Команды, которые читали `FRONTEND.md` как «интерфейс пишем сами», должны узнать о смене.

## 2. Релизы отдельно от экспериментов

**Что нужно.** Сборку для w2c делать из помеченной версии (тег `webui-ГГГГ-ММ-ДД` или ветка релиза), а не из текущего `main`. Прототипы попадают в продукт только переносом в `index.html`.

**Зачем.** Сейчас любая правка в `main`, в том числе незаконченная, оказывается в следующей сборке.

**Что сломается.** w2c должна брать сборку по тегу. Решить, кто ставит тег и по какой проверке.

## 3. Ревью продуктового кода

**Что нужно.** Изменения `index.html`, `api/` и `tests/` — через PR с обязательными проверками (`check_api.py`, `check_ui.py`, `check_webui.py` в GitHub Actions) и одним человеком, который смотрит изменения. Прототипы можно оставить без PR.

**Зачем.** Код, который ставят заказчикам, не должен попадать в продукт без проверки и без того, кто его видел.

**Что сломается.** Правило «все в `main`, без PR» в `CLAUDE.md` меняется для этих файлов. Правки идут медленнее.

## 4. Ответственный за фронтенд

**Что нужно.** Назвать одного человека, не команду: он решает вопросы устройства кода интерфейса и разбирается в нём без агента.

**Зачем.** Сейчас код пишут в основном агенты, а люди смотрят на результат в браузере. У продукта должен быть хозяин.

**Что сломается.** Ничего; это часть времени одного человека.

## 5. Аудит безопасности

**Что нужно.** До первой установки у заказчика проверить экранирование всего, что приходит от сервера и устройств. Пример пропуска: `index.html:4810` — имя домена попадает в `<option>` без `escHtml`.

**Зачем.** CSP консоли не даст выполнить вставленный скрипт, но подменить разметку можно. Имена устройств и объектов задают люди и сами устройства.

**Что сломается.** Ничего; правки точечные.

## 6. Сценарии интерфейса — через DOM

**Что нужно.** Согласие на то, что мы постепенно, по одному файлу, переписываем `tests/ui-*.js`: вместо вызова внутренних функций (`pick`, `setGroup`, `renderTree`) и чтения состояния (`treeBr`, `devicePool`) — действия пользователя (клик, ввод) и проверка видимого текста и запросов к серверу. `tests/api-*.js` не трогаем.

**Зачем.** Сейчас сценарии привязаны к устройству кода. Через DOM они становятся эталоном для перевода (п. 7): новый код готов, когда проходит те же сценарии. Полезно и без перевода.

**Что сломается.** Ничего: сценарии переписываются по одному, проверки остаются зелёными. Начать можем сразу, не дожидаясь п. 7.

## 7. Перевод кода: React + TypeScript по разделам

**Что нужно.** Решение о стеке и порядке. Предлагаем:

1. Догнать основной: перенести прототип 27 и остальные висящие, пока `index.html` в старом виде.
2. Инфраструктура: Vite + TypeScript, типы из `api/openapi.json`. Сборка заменяет `tools/build_webui.py` и выдаёт тот же `MANIFEST.json` под тот же CSP. Pages собирается через GitHub Actions.
   - Встроенный сервер остаётся. `api/server.js`, `client.js`, наборы — обычный JS, от фреймворка интерфейса они не зависят. Две сборки из одного кода: демо (Pages, прототипы, тесты) — со встроенным сервером и наборами, макет работает без бэкенда, как сейчас; для w2c — без них, с бэкендом консоли, как делает `build_webui.py` сейчас. Контракт и сервер по-прежнему правит altumur.
3. Вынести в модули клиент API, кэш и поток событий.
4. Переводить раздел за разделом левого меню («Права», «Хранилища», …); непереведённые рисует старый код. Каждый раздел проверяется своими сценариями из п. 6. Правила интерфейса (моргание, удаление с вводом числа, плавные фильтры) становятся общими компонентами.

**Зачем.** Файл на 25 тыс. строк с глобальными функциями трудно менять вшестером, и с каждым месяцем труднее. React-компоненты экранируют данные по умолчанию (п. 5 перестаёт держаться на внимательности), состояние перестаёт быть глобальным, перерисовка не теряет фокус и прокрутку, а людей на этот стек проще найти.

**Что сломается.**

- Порядок работы с прототипами: копия одного HTML-файла больше не работает, прототипы станут ветками или флагами с превью на Pages. Правила в `CLAUDE.md` переписываются.
- Открытие макета двойным кликом — если не собирать отдельную демо-версию без модулей.
- На время перевода — двойная работа: нужно правило, где делать запросы команд VMS (предлагаем: в переведённый раздел — только на React).
- Контракт и бэкенды команд VMS не затрагиваются.

## 8. Требования, которые макет не проверяет

**Что нужно.** Записать, что требуется от продукта: поддерживаемые браузеры, доступность, поведение при ошибках сети и долгой работе, журналирование, обновление версий у заказчика. Решить, какие из них проверять тестами.

**Зачем.** У макета этих требований не было, у продукта они есть, но нигде не записаны.

**Что сломается.** Ничего.

## 9. Прототипы — тоже на React

**Что нужно.** Решить, переходят ли на React и прототипы, а не только основной. Предлагаем: да, по мере перевода разделов — прототип раздела делается на том стеке, на котором этот раздел в основном.

**Плюсы.**

- Один стек от идеи до продукта: перенос прототипа в основной — слияние ветки, а не переписывание по `git diff` двух огромных файлов.
- Прототип собирается из тех же компонентов, что продукт (дерево, фильтр `.bk-scope`, подтверждение удаления), и сразу соблюдает правила интерфейса.
- Агентам проще (подробнее ниже): прототип — это несколько небольших файлов, а не копия файла на 29 тыс. строк, как `index_generic.html`.

**Минусы.**

- Прототип — ветка или флаг, а не файл `index_NN_….html`. Превью на Pages надо собирать через GitHub Actions (каждая ветка прототипа — в свою папку), порядок в `CLAUDE.md` и `protos.html` переписывается.
- Сборка на каждый прототип: быстрый набросок «на час» дороже, чем копия HTML.
- Открыть прототип двойным кликом из папки нельзя (если не собирать демо без модулей).
- Пока перевод не закончен, есть оба вида прототипов: для непереведённых разделов — по-старому.

**Правда ли, что ИИ проще работать с React.** Частично.

- Верно, что React — самый частый фреймворк в обучающих данных, и инструменты генерации интерфейсов (v0, Lovable, Bolt) по умолчанию выдают React + TypeScript + Tailwind ([обзор](https://dev.to/aierastack/choosing-a-frontend-framework-in-2026-when-ai-becomes-your-invisible-teammate-5b8g), [ещё](https://codewithbre.substack.com/p/ai-vs-frontend-developers-vibe-coding-a-react-tailwindcss-monoculture-757eabfeda83)). Но это популярность, а не измеренная эффективность; источники — блоги.
- Среди фреймворков React у моделей действительно лучший: в Web-Bench у Claude 3.7 Pass@2 по React 65 против 30 у Vue, 40 у Angular, 25 у Svelte ([Web-Bench](https://arxiv.org/html/2505.07473v1), приложение A.1.1).
- По сравнению с чистым HTML/JS — не лучше: в DesignBench модели заметно слабее на фреймворках, чем на чистом HTML/CSS, особенно в правке и исправлении (у Claude 3.7 оценка правки 8,2 на React против 9,2 на чистом) ([DesignBench](https://arxiv.org/html/2506.06251v3)). Оговорка: чистые примеры там переведены из React-примеров моделью, и это задачи «по картинке», на небольших страницах.
- Для нас важнее другое: исследования меряют небольшие задачи, а наша трудность — размер и связность. В одном файле на 25 тыс. строк с глобальным состоянием агент тратит контекст на поиск, а правка в одном месте ломает далёкое. Компоненты с типами дают маленькие независимые файлы, и компилятор ловит ошибки до запуска тестов. Это выигрыш от модулей и TypeScript; React к нему добавляет экранирование по умолчанию и знакомый моделям способ собирать интерфейс.

Вывод: «ИИ проще с React» само по себе не довод — измерений, что React лучше чистого JS, нет. Довод — что код в модулях с типами агентам и людям менять проще, чем один большой файл; React — самый распространённый и самый знакомый моделям способ к этому прийти.

**Что сломается.** Порядок работы с прототипами (см. минусы). Контракт не затрагивается.
