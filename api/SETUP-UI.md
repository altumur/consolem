# Своя страница подсистемы: протокол `setup/1`

Этот документ описывает, как своя страница подсистемы работает внутри карточки consolem. Страницу объявляет вид: `UnitKind.setupUi` с `mode: iframe` ([openapi.json](openapi.json)). Страница и consolem обмениваются сообщениями `postMessage`. Точный вид каждого сообщения задаёт JSON Schema [`setup-ui.schema.json`](setup-ui.schema.json), а `python3 tools/check_api.py` сверяет схему с этим документом. Документ описывает шаг 1: страница показывает поля и отдаёт правку, а consolem записывает её. Шаг 2 (страница просит consolem) — часть 06 переработки. Описание решения — [`docs/contract-layers/2026-11-18-setup-ui-iframe-design.md`](../docs/contract-layers/2026-11-18-setup-ui-iframe-design.md).

## Зачем и какой экран главнее

Подсистема лучше знает свой объект, поэтому она может дать свою страницу настроек. Тогда consolem не нужен ручной экран под каждый вид.

Какой экран видит человек, consolem решает по виду объекта, в три ступени:

1. У вида есть своя страница: `setupUi.mode: iframe`, версия `setupUi.protocol` знакома consolem (нет поля — `setup/1`), вид есть в `setupUi.kinds` (нет поля — только этот вид). Тогда consolem показывает страницу.
2. Страницы нет, но есть ручной экран consolem по профилю. Тогда consolem показывает ручной экран.
3. Нет ни страницы, ни ручного экрана. Тогда consolem показывает форму по схеме вида из `/kinds`.

Незнакомую версию протокола (`setup/9`) consolem не встраивает и показывает ступень 2 или 3. У `mode: tab` страница открывается ссылкой в новой вкладке и пишет сама, а в карточке consolem показывает ступень 2 или 3.

Страница заменяет только вкладки вида: те вкладки, которые ручной экран рисует под этот вид. Свои вкладки страница рисует внутри себя. Общее для любого объекта остаётся у consolem (вариант А описания решения):

- шапка карточки: имя, путь, состояние и меню «Ещё» (переименовать, перенести, удалить, папки, «Все параметры»);
- вкладки механизма, например «Доступ»;
- кнопки «Показать план» и «Применить» под страницей.

Ступень 1 не меняет тип объекта в consolem. Поэтому у вида с ручным экраном и страницей вкладки механизма остаются.

## Адрес и рамка

**Адрес.** У `mode: iframe` consolem всегда берёт адрес из `POST /units/{uid}/setup-ui`, даже если у вида есть `setupUi.url`. Бэкенд дописывает к адресу объект, язык и разовый ключ. Ключ бэкенд кладёт в запрос (`?t=`) или в путь адреса. consolem открывает адрес как есть и ничего к нему не дописывает. Относительный адрес consolem разрешает от адреса своей страницы. Когда consolem загружает рамку заново (после смены языка или по кнопке «Повторить»), consolem берёт новый адрес.

**Происхождение.** consolem принимает сообщения только от `iframe.contentWindow` и только с происхождения страницы. Отвечает consolem только на это происхождение и никогда на `"*"`. Происхождение страницы consolem берёт из `SetupUiLink.origin`. Если этого поля нет, consolem берёт `setupUi.origin`, а если нет и его, то происхождение выданного адреса. Поле `origin` нужно, когда дверь и прокси перенаправляют страницу на другое происхождение. Дверью этот документ называет шлюз системы, через который браузер получает страницу подсистемы и отправляет её запросы.

Страница проверяет, что сообщение пришло от `window.parent` и с происхождения consolem. Происхождение consolem страница берёт из `location.ancestorOrigins[0]`, а если его нет, из `document.referrer`. Страница обращается только к своему происхождению, относительными адресами.

**Правило: настоящая страница приходит с другого происхождения, чем consolem.** Бэкенд не отдаёт страницу подсистемы с происхождения consolem. Только так страница не получает доступа к consolem, хотя у рамки есть `allow-same-origin`. Правило не действует только на стенде (ниже, «Правило стенда — не протокол»).

**Рамка.** consolem создаёт рамку так:

```html
<iframe sandbox="allow-scripts allow-forms allow-same-origin" src="…"></iframe>
```

- `allow-same-origin` нужен, потому что без него страница не может обратиться к своей двери с кукой. Доступа к consolem страница с другого происхождения при этом не получает.
- `allow-top-navigation` и `allow-popups` consolem не даёт. Страница не уводит consolem со страницы и не открывает окна.

**Что настраивает система, а не consolem:**

- дверь отдаёт страницу с заголовком `Content-Security-Policy: frame-ancestors <происхождение consolem>`, поэтому чужой сайт не может встроить страницу. Этот заголовок и защищает страницу. Проверка происхождения в сообщениях не мешает чужому сайту встроить страницу и показать её человеку;
- политика CSP consolem разрешает `frame-src` для происхождений дверей;
- кука двери приходит в рамку, только если дверь на том же сайте, что consolem. Для двери на другом домене нужен `SameSite=None; Secure; Partitioned` или другой способ входа.

**Правило стенда — не протокол.** Встроенный сервер отдаёт тестовую страницу на том же происхождении, что consolem, или с диска (`file:`). Рамку стенд создаёт так:

- consolem открыт по `http` или `https`, и адрес страницы на том же происхождении. Тогда consolem создаёт рамку без `allow-same-origin`. У страницы непрозрачное происхождение, поэтому страница не получает доступа к consolem;
- consolem и страница открыты с диска. Тогда consolem создаёт рамку с `allow-same-origin`. Без него Chrome не загружает скрипты страницы с диска. Chrome даёт каждому файлу своё непрозрачное происхождение, поэтому страница всё равно не получает доступа к consolem;
- ключ Chrome `--allow-file-access-from-files` открывает файлам доступ друг к другу. Этот ключ ставит `tools/check_ui.py`. Под этим ключом страница с диска получает доступ к consolem. Поэтому стенд с диска нужен только для проверок, и чужую страницу с диска открывать нельзя.

В обоих случаях стенд работает так:

- consolem отправляет сообщения с `"*"` и принимает их с происхождения `"null"`. Chrome называет происхождение рамки с диска `"null"`, даже если у рамки есть `allow-same-origin`;
- страница принимает сообщения consolem с происхождения `"null"` или `"file://"`. Chrome для страницы с диска называет происхождение родителя `"file://"`, а не `"null"`. Так бывает, когда consolem открыт с диска, например под `tools/check_ui.py`;
- проверку `source === window.parent` страница не снимает;
- правило стенда действует, только когда страница сама открыта с диска (`location.protocol` — `file:`) или её своё происхождение непрозрачно (`"null"`). Если настоящая страница не знает происхождения consolem (в Firefox нет `ancestorOrigins`, а `Referrer-Policy: no-referrer` убирает `referrer`), страница не переходит на правило стенда: автор передаёт происхождение явно, иначе страница не подключается и пишет причину в консоль.

Это правило нужно только стенду. Настоящая страница приходит с другого происхождения (правило выше), поэтому правило стенда к ней не относится.

## Сообщения

Каждое сообщение — объект `{proto: "setup/1", type, …}`. Получатель пропускает сообщение с незнакомым `type` и незнакомое поле. Другую версию `proto` получатель тоже пропускает. Схема описывает, что отправляет сторона шага 1, поэтому в ней у каждого сообщения `additionalProperties: false`.

Указатель поля — JSON Pointer в `Unit`, как `Problem.errors[].field`: `/properties/<имя>`. Правка — JSON Merge Patch (RFC 7396) к `unit.properties`. Сторона всегда отправляет весь черновик, а не последнее изменение. `null` снимает значение, `{}` значит «изменений нет».

### consolem → страница

| `type` | Когда | Поля |
|---|---|---|
| `init` | consolem получил `ready` | `uid`, `kind`, `lang` (`ru`, `en`…), `theme`, `readOnly`, `unit {uid, kind, name, version, properties, status?}`, `draft` (черновик, `{}` — нет), `host {proto, apply}` |
| `draft` | черновик изменили вне страницы, например в «Все параметры» | `patch` — черновик целиком |
| `applied` | своё «Применить» прошло | `unit` — новый объект; черновик пуст |
| `errors` | бэкенд отверг правку в `POST /units/validate` | `problem` — `Problem` как есть: `code`, `message`, `field?`, `params?`, `current?`, `errors[]?` с указателем `field` |
| `revert` | объект у бэкенда изменился или черновик опустел по действию consolem | `unit`; черновик пуст |
| `theme` | тема consolem изменилась | `theme` |
| `flush` | consolem собирается применить правку | `seq` — целое число от 1 |

### Страница → consolem

| `type` | Когда | Поля |
|---|---|---|
| `ready` | страница загрузилась | `fields?` — указатели полей, которые показывает страница |
| `change` | человек изменил поле на странице | `patch` — черновик целиком |
| `invalid` | страница нашла ошибку ввода | `fields` — указатели полей с ошибкой (пустой список снимает запрет), `message?` |
| `height` | высота содержимого изменилась | `px` — целое число от 0 |
| `flushed` | ответ на `flush` | `seq` — номер из `flush` |

**Тема.** `theme = {mode: "dark" | "light", tokens: {"--one-…": "<значение CSS>"}}`. consolem передаёт токены оформления: `--one-canvas`, `--one-surface`, `--one-surface-muted`, `--one-fg`, `--one-fg-muted`, `--one-border`, `--one-border-strong`, `--one-accent`, `--one-accent-on`, `--one-danger`, `--one-focus-ring`, `--one-control-bg`, `--one-control-hover`, `--one-radius-control`. Страница ставит их своими переменными CSS.

**Язык.** Смена языка consolem перезагружает рамку с новым адресом и новым `lang`.

**Высота.** До первого `height` consolem даёт рамке 320 px. Значение `px` consolem ограничивает от 80 до 20 000 px. Это правило consolem, а не протокола.

## Как идёт «Применить»

1. Страница на каждую правку отправляет `change` с черновиком целиком. consolem кладёт черновик в свой черновик карточки, тот же, что у «Все параметры».
2. consolem отбрасывает ключи правки вне схемы вида, поля `readOnly` и поля `x-transient`. О каждом таком ключе consolem один раз пишет предупреждение в консоль браузера.
3. Пока страница сообщает `invalid` с непустым списком, consolem не даёт нажать «Показать план». Пустой список `invalid` снимает запрет.
4. consolem пишет правку своим обычным путём карточки: «Показать план», проверка `POST /units/validate`, план, «Применить», `POST /operations` с `expectedVersions`. Журнал, уведомление с отсчётом и «Отменить», конфликт версий — общие для всех правок consolem. Это и есть «`PATCH` с `If-Match`» описания решения.
5. Перед записью consolem отправляет `flush {seq}` и ждёт `flushed` с тем же `seq` не дольше 2 секунд. Страница сначала отправляет `change` с вводом, который ещё не отправила, затем `flushed`. Если страница не ответила, consolem применяет то, что есть, и пишет об этом в уведомлении.
6. Если запись прошла, consolem отправляет `applied {unit}`. Только своё удачное «Применить» даёт `applied`.
7. Если бэкенд отверг правку в `POST /units/validate` (`422`), consolem отправляет `errors {problem}`. Страница подсвечивает свои поля. Поля, которых на странице нет, consolem показывает списком под рамкой со ссылкой «Все параметры». Конфликт версий (`412`) consolem показывает как у любой правки. Отказ `POST /operations` при «Применить» странице не приходит как `errors`: consolem показывает его, как у любой правки, и отправляет `revert` (п. 8).
8. consolem отправляет `revert {unit}`, когда объект у бэкенда изменился или черновик опустел по действию consolem: «Сбросить», «Отменить» после записи, чужая правка при пустом черновике, неудачное «Применить». При непустом черновике consolem не передаёт странице чужую правку: её найдёт конфликт версий при «Применить».

На шаге 1 consolem не проверяет черновик на ходу. Бэкенд проверяет правку один раз, по «Показать план».

## Режим `apply`

consolem называет режим применения в `init.host.apply`:

- `button` — человек нажимает «Применить» в consolem. Макет работает в этом режиме;
- `leave` — consolem применяет правку, когда человек уходит с карточки. Протокол для него готов (`flush` и `flushed`), но макет этот режим пока не делает.

Ни в одном режиме страница не рисует своих кнопок сохранения. Подсказку о режиме страница показать может.

## Страница не загрузилась

consolem ждёт `ready` 10 секунд. Если бэкенд не выдал адрес, дверь не ответила или `ready` не пришёл вовремя, consolem пишет, что страница подсистемы недоступна, и называет причину. Ниже consolem показывает форму по схеме вида, поэтому объект можно настроить и без страницы. Кнопка «Повторить» берёт новый адрес и загружает страницу снова.

## Только просмотр

Страница `mode: iframe` ничего не пишет сама, поэтому бэкенд выдаёт её адрес по праву `view`. Бэкенд ставит `SetupUiLink.readOnly: true`, когда у человека право `view` без `edit`. Тогда consolem:

- отправляет странице `init` с `readOnly: true`;
- не показывает «Применить»;
- не принимает `change`.

Страница при `readOnly: true` делает поля неактивными. Человек с правом `view` видит ту же страницу, а не другой экран.

## Чего страница не делает

- Страница не пишет настройки объекта ни через consolem, ни через свою дверь. Всё, что меняет `properties`, идёт через `change` и «Применить» consolem.
- Страница не обращается к `/api/*` consolem и не получает куки и токен consolem.
- Страница не уводит consolem на другой адрес и не открывает окна.
- Страница не рисует кнопки «Сохранить» и «Отменить».

## Библиотека `setup-bridge.js`

Автор страницы может взять готовую библиотеку [`setup-bridge.js`](setup-bridge.js). Она отправляет `ready`, принимает `init`, проверяет `source` и происхождение, хранит черновик, отвечает на `flush` и сообщает высоту. Сообщения библиотеки точно повторяют схему: `python3 tools/check_api.py` прогоняет библиотеку в Node (`tools/check_setup_bridge.js`) и сверяет каждое её сообщение с `setup-ui.schema.json`.

**Как подключить.** Положить файл рядом со страницей и подключить обычным тегом, без сборки и зависимостей:

```html
<script src="setup-bridge.js"></script>
<script src="page.js"></script>
```

```js
SetupBridge.connect({
  fields: ["/properties/code_length", "/properties/beep"],
  onRevert: (unit) => show(unit.properties),
  onApplied: (unit) => show(unit.properties),
  onDraft: (patch) => show(SetupBridge.merge(session.unit.properties, patch)),
  onErrors: (problem) => mark(problem.errors || []),
  onTheme: (theme) => paintTheme(theme),
}).then((s) => {
  session = s;
  paintTheme(s.theme);
  show(SetupBridge.merge(s.unit.properties, s.draft));
});
// на каждый ввод — весь черновик
input.onchange = () => session.change(SetupBridge.diff(session.unit.properties, readForm()));
```

**`SetupBridge.connect(opts)` → `Promise<Session>`.** Библиотека сразу отправляет `ready` (с `opts.fields`, если они есть). Обещание сбывается, когда приходит `init`. Страница вызывает `connect` один раз: каждый вызов отправляет свой `ready` и добавляет свой обработчик сообщений. Поля `opts`, все необязательные:

- `fields` — указатели полей, которые показывает страница;
- `origin` — происхождение consolem, если автор знает его заранее. Оно главнее `ancestorOrigins` и `referrer`. Библиотека берёт от значения только происхождение (`new URL(origin).origin`), поэтому путь в адресе не мешает. Значение `"*"`, непрозрачное происхождение и не адрес библиотека не принимает: `connect` отказывает;
- `onDraft(patch)`, `onApplied(unit)`, `onErrors(problem)`, `onRevert(unit)`, `onTheme(theme)` — сообщения `draft`, `applied`, `errors`, `revert`, `theme`;
- `onFlush()` — consolem собирается применить правку. Страница отдаёт неотправленный ввод синхронно: вызывает `session.change(…)` или возвращает черновик. Если возвращённый черновик отличается от отправленного, библиотека отправляет `change`. Затем библиотека отправляет `flushed` с тем же `seq`, даже если `onFlush` бросил исключение: исключение библиотека пишет в консоль. Если `seq` не целое число от 1, библиотека пропускает `flush`;
- `autoHeight` — по умолчанию `true`: `ResizeObserver` на `document.body` отправляет `height` с высотой содержимого: низ `body` плюс его нижнее поле. Значение `documentElement.scrollHeight` не меньше высоты рамки, поэтому библиотека его не берёт: иначе рамка не становится ниже. Одно значение два раза подряд библиотека не отправляет. Если странице задать `body {height: 100%}`, низ `body` всегда равен высоте рамки, и рамка никогда не становится ниже. Поэтому высоту `body` страница не задаёт.

**`Session`** — объект после `init`:

- `init` — сообщение `init` целиком; `host`, `readOnly`, `theme` — его поля; `unit` — последний объект из `init`, `applied` или `revert`;
- `draft` — последний черновик, который страница отправила или получила. После `applied` и `revert` черновик становится `{}`, после `draft` черновик становится `patch`;
- `change(patch)` отправляет `change` с черновиком целиком и возвращает `true`. При `readOnly` библиотека ничего не отправляет и возвращает `false`;
- `invalid(fields, message?)` отправляет `invalid`. Пустой список снимает запрет;
- `height(px)` отправляет `height`: целое число от 0.

**`SetupBridge.merge(base, patch)`** применяет JSON Merge Patch (RFC 7396) и возвращает новый объект: `null` снимает ключ, вложенный объект сливается, массив заменяется целиком. `base` не меняется. **`SetupBridge.diff(base, next)`** даёт правку от `base` к `next`: снятый ключ — `null`, вложенные объекты — рекурсивно, массивы — целиком. Если в `next` нет значений `null`, `merge(base, diff(base, next))` равно `next`. Значение `null` в правке снимает ключ, поэтому `null` из `next` после `merge` пропадает. Обе функции смотрят только на свои ключи объекта и пропускают ключ `__proto__`.

**Происхождение consolem** библиотека берёт из `opts.origin`, иначе из `location.ancestorOrigins[0]`, иначе из `document.referrer`. Библиотека принимает только сообщения от `window.parent` с `proto: "setup/1"`. Незнакомый `type` библиотека пропускает. Если происхождение известно, библиотека отправляет сообщения только на него и принимает только с него. Если происхождение непрозрачное (`"null"`, `"file://"`) или неизвестное, библиотека поступает так:

- если страница открыта с диска или её своё происхождение `"null"`, библиотека работает по правилу стенда из раздела «Адрес и рамка»: отправляет с `"*"`, принимает с `"null"` и `"file://"`;
- иначе `connect` отказывает (библиотека отклоняет обещание), ничего не отправляет и пишет причину в консоль. Тогда автор передаёт `opts.origin`.

Библиотека настройки не пишет. Всё, что меняет `properties`, идёт через `session.change` и «Применить» consolem.

**Образец** — тестовая страница стенда [`plugins/security_controller/setup/`](plugins/security_controller/setup/index.html) для вида `security_controller/KEYPAD`: `index.html`, `page.js`, `page.css`. Она подключает библиотеку как `../../../setup-bridge.js` и показывает четыре поля из пяти на двух своих вкладках. Ещё страница проверяет ввод (`invalid`), показывает ошибки `errors` у полей, делает поля неактивными при `readOnly` и берёт тему из `theme.tokens`. Запросов страница не делает. Если открыть её отдельно, без рамки consolem, страница пишет, что ждёт данные от консоли. `python3 tools/check_api.py` проверяет, что в разметке нет встроенного `<script>` и атрибутов `on…`, в коде нет `fetch` и `/api/`, а `ready.fields` совпадает с полями схемы вида, кроме `lock_after_tries`.
