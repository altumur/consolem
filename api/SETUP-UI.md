# Своя страница подсистемы: протокол `setup/1`

Этот документ описывает, как своя страница подсистемы работает внутри карточки consolem. Страницу объявляет вид: `UnitKind.setupUi` с `mode: iframe` ([openapi.json](openapi.json)). Страница и consolem обмениваются сообщениями `postMessage`. Точный вид каждого сообщения задаёт JSON Schema [`setup-ui.schema.json`](setup-ui.schema.json), а `python3 tools/check_api.py` сверяет схему с этим документом. Документ описывает два шага протокола. На шаге 1 страница показывает поля и отдаёт правку, а consolem записывает её. На шаге 2 страница просит consolem выполнить операцию контракта, переслать события потока, перейти к объекту или показать подтверждение (раздел «Шаг 2: мост к механизму»). Описание решения — [`docs/contract-layers/2026-11-18-setup-ui-iframe-design.md`](../docs/contract-layers/2026-11-18-setup-ui-iframe-design.md).

## Зачем и какой экран главнее

Подсистема лучше знает свой объект, поэтому она может дать свою страницу настроек. Тогда consolem не нужен ручной экран под каждый вид.

Какой экран видит человек, consolem решает по виду объекта, в три ступени:

1. У вида есть своя страница: `setupUi.mode: iframe`, версия `setupUi.protocol` знакома consolem (нет поля — `setup/1`), вид есть в `setupUi.kinds` (нет поля — только этот вид). Тогда consolem показывает страницу.
2. Страницы нет, но есть ручной экран consolem по профилю. Тогда consolem показывает ручной экран.
3. Нет ни страницы, ни ручного экрана. Тогда consolem показывает форму по схеме вида из `/kinds`.

Незнакомую версию протокола (`setup/9`) consolem не встраивает и показывает ступень 2 или 3. У `mode: tab` страница открывается ссылкой в новой вкладке и пишет сама, а в карточке consolem показывает ступень 2 или 3.

Страница заменяет только вкладки вида: те вкладки, которые ручной экран рисует под этот вид. Свои вкладки страница рисует внутри себя. Общее для любого объекта остаётся у consolem (вариант А описания решения):

- шапка карточки: имя, путь, состояние и меню «Ещё» (переименовать, перенести, удалить, папки, «Все параметры»);
- вкладки механизма, например «Доступ»;
- кнопки «Показать план» и «Применить» под страницей.

Ступень 1 не меняет тип объекта в consolem. Поэтому у вида с ручным экраном и страницей вкладки механизма остаются.

## Адрес и рамка

**Адрес.** У `mode: iframe` consolem всегда берёт адрес из `POST /units/{uid}/setup-ui`, даже если у вида есть `setupUi.url`. Бэкенд дописывает к адресу объект, язык и разовый ключ. Ключ бэкенд кладёт в запрос (`?t=`) или в путь адреса. consolem открывает адрес как есть и ничего к нему не дописывает. Относительный адрес consolem разрешает от адреса своей страницы. Когда consolem загружает рамку заново (после смены языка или по кнопке «Загрузить страницу снова»), consolem берёт новый адрес.

**Происхождение.** consolem принимает сообщения только от `iframe.contentWindow` и только с происхождения страницы. Отвечает consolem только на это происхождение и никогда на `"*"`. Происхождение страницы consolem берёт из `SetupUiLink.origin`. Если этого поля нет, consolem берёт `setupUi.origin`, а если нет и его, то происхождение выданного адреса. Поле `origin` нужно, когда дверь и прокси перенаправляют страницу на другое происхождение. Дверью этот документ называет шлюз системы, через который браузер получает страницу подсистемы и отправляет её запросы.

Страница проверяет, что сообщение пришло от `window.parent` и с происхождения consolem. Происхождение consolem страница берёт из `location.ancestorOrigins[0]`, а если его нет, из `document.referrer`. Страница обращается только к своему происхождению, относительными адресами.

**Правило: настоящая страница приходит с другого происхождения, чем consolem.** Бэкенд не отдаёт страницу подсистемы с происхождения consolem. Только так страница не получает доступа к consolem, хотя у рамки есть `allow-same-origin`. Правило не действует только на стенде (ниже, «Правило стенда — не протокол»).

**Рамка.** consolem создаёт рамку так:

```html
<iframe sandbox="allow-scripts allow-forms allow-same-origin" src="…"></iframe>
```

- `allow-same-origin` нужен, потому что без него страница не может обратиться к своей двери с кукой. Доступа к consolem страница с другого происхождения при этом не получает.
- `allow-top-navigation` и `allow-popups` consolem не даёт. Страница не уводит consolem со страницы и не открывает окна.

**Что настраивает система, а не consolem:**

- дверь отдаёт страницу с заголовком `Content-Security-Policy: frame-ancestors <происхождение consolem>`, поэтому чужой сайт не может встроить страницу. Этот заголовок и защищает страницу. Проверка происхождения в сообщениях не мешает чужому сайту встроить страницу и показать её человеку;
- политика CSP consolem разрешает `frame-src` для происхождений дверей;
- кука двери приходит в рамку, только если дверь на том же сайте, что consolem. Для двери на другом домене нужен `SameSite=None; Secure; Partitioned` или другой способ входа.

**Правило стенда — не протокол.** Встроенный сервер отдаёт тестовую страницу на том же происхождении, что consolem, или с диска (`file:`). consolem применяет правило стенда только к тестовой странице стенда: адрес относительный или лежит под `api/plugins/` рядом с consolem, на происхождении consolem (у consolem с диска — тоже на диске). Если бэкенд выдал другой адрес на происхождении consolem или подсказка `SetupUiLink.origin` или `setupUi.origin` равна происхождению consolem при чужом адресе, consolem не создаёт рамку. Тогда consolem пишет, что у страницы то же происхождение, что у консоли, и показывает экран из раздела «Страница не загрузилась». Рамку стенд создаёт так:

- consolem открыт по `http` или `https`, и адрес страницы на том же происхождении. Тогда consolem создаёт рамку без `allow-same-origin`. У страницы непрозрачное происхождение, поэтому страница не получает доступа к consolem;
- consolem и страница открыты с диска. Тогда consolem создаёт рамку с `allow-same-origin`. Без него Chrome не загружает скрипты страницы с диска. Chrome даёт каждому файлу своё непрозрачное происхождение, поэтому страница всё равно не получает доступа к consolem;
- ключ Chrome `--allow-file-access-from-files` открывает файлам доступ друг к другу. Этот ключ ставит `tools/check_ui.py`. Под этим ключом страница с диска получает доступ к consolem. Поэтому стенд с диска нужен только для проверок, и чужую страницу с диска открывать нельзя.

В обоих случаях стенд работает так:

- consolem отправляет сообщения с `"*"` и принимает их с происхождения `"null"`. Chrome называет происхождение рамки с диска `"null"`, даже если у рамки есть `allow-same-origin`;
- страница принимает сообщения consolem с происхождения `"null"` или `"file://"`. Chrome для страницы с диска называет происхождение родителя `"file://"`, а не `"null"`. Так бывает, когда consolem открыт с диска, например под `tools/check_ui.py`;
- проверку `source === window.parent` страница не снимает;
- правило стенда действует, только когда страница сама открыта с диска (`location.protocol` — `file:`) или её своё происхождение непрозрачно (`"null"`). Если настоящая страница не знает происхождения consolem (в Firefox нет `ancestorOrigins`, а `Referrer-Policy: no-referrer` убирает `referrer`), страница не переходит на правило стенда: автор передаёт происхождение явно, иначе страница не подключается и пишет причину в консоль.

Это правило нужно только стенду. Настоящая страница приходит с другого происхождения (правило выше), поэтому правило стенда к ней не относится.

## Сообщения

Каждое сообщение — объект `{proto: "setup/1", type, …}`. Получатель пропускает сообщение с незнакомым `type` и незнакомое поле. Другую версию `proto` получатель тоже пропускает. Схема описывает, что отправляет каждая сторона, поэтому в ней у каждого сообщения `additionalProperties: false`. Шаг сообщения схема называет в `x-step`. Хост шага 1 не отправляет сообщений и полей шага 2, а пришедшие сообщения шага 2 пропускает.

Указатель поля — JSON Pointer в `Unit`, как `Problem.errors[].field`: `/properties/<имя>`. Правка — JSON Merge Patch (RFC 7396) к `unit.properties`. Сторона всегда отправляет весь черновик, а не последнее изменение. `null` снимает значение, `{}` значит «изменений нет».

### consolem → страница

| `type` | Когда | Поля |
|---|---|---|
| `init` | consolem получил `ready` | `uid`, `kind`, `lang` (`ru`, `en`…), `theme`, `readOnly`, `unit {uid, kind, name, version, properties, status?}`, `draft` (черновик, `{}` — нет), `host {proto, apply, bridge?}`; `bridge` — шаг 2 |
| `draft` | черновик изменили вне страницы, например в «Все параметры» | `patch` — черновик целиком; `steps?` — шаг 2: шаги моста в черновике `[{step, op, label}]` |
| `applied` | своё «Применить» прошло; шаг 2 — операция с шагами моста кончилась или сервер отказал ей | `unit` — новый объект; черновик пуст, а при отказе операции с шагами моста черновик остаётся; `steps?` — шаг 2: итог шагов моста `[{step, state, code?, createdId?}]` |
| `errors` | бэкенд отверг правку в `POST /units/validate` | `problem` — `Problem` как есть: `code`, `message`, `field?`, `params?`, `current?`, `errors[]?` с указателем `field` |
| `revert` | объект у бэкенда изменился или черновик опустел по действию consolem; неудачное «Применить» без шагов моста | `unit`; черновик пуст; `steps?` — шаг 2: всегда `[]` |
| `theme` | тема consolem изменилась | `theme` |
| `flush` | consolem собирается применить правку | `seq` — целое число от 1 |
| `result` | шаг 2: ответ на `call`, `subscribe`, `navigate`, `confirm` | `id` — из вопроса, `ok`, `status` (HTTP-статус; `202` — consolem положил шаг в черновик; `0` — отказ моста без запроса), `body?`, `problem?` — `Problem`, `etag?` |
| `event` | шаг 2: сообщение потока по подписке страницы | `sub` — номер подписки, `message` — `StreamMessage` как есть |

### Страница → consolem

| `type` | Когда | Поля |
|---|---|---|
| `ready` | страница загрузилась | `fields?` — указатели полей, которые показывает страница |
| `change` | человек изменил поле на странице | `patch` — черновик целиком |
| `invalid` | страница нашла ошибку ввода | `fields` — указатели полей с ошибкой (пустой список снимает запрет), `message?` |
| `height` | высота содержимого изменилась | `px` — целое число от 0 |
| `flushed` | ответ на `flush` | `seq` — номер из `flush` |
| `call` | шаг 2: страница просит выполнить операцию | `id` — строка, `op` — `operationId` контракта, `params?` — параметры пути и запроса по именам, `body?` — тело запроса |
| `subscribe` | шаг 2: страница хочет события потока | `id` — он же номер подписки `sub`, `entityIds?` — `uid` объектов, `kinds?` — виды, `types?` — типы сообщений потока |
| `unsubscribe` | шаг 2: подписка больше не нужна | `sub` — номер подписки; ответа нет |
| `navigate` | шаг 2: страница просит перейти к объекту | `id`, `uid`, `tab?` — вкладка карточки |
| `confirm` | шаг 2: страница просит подтверждение consolem | `id`, `title`, `text`, `lose?` и `keep?` — списки строк, `count?` — число для ввода, `okLabel?` |

**Тема.** `theme = {mode: "dark" | "light", tokens: {"--one-…": "<значение CSS>"}}`. consolem передаёт токены оформления: `--one-canvas`, `--one-surface`, `--one-surface-muted`, `--one-fg`, `--one-fg-muted`, `--one-border`, `--one-border-strong`, `--one-accent`, `--one-accent-on`, `--one-danger`, `--one-focus-ring`, `--one-control-bg`, `--one-control-hover`, `--one-radius-control`. Страница ставит их своими переменными CSS.

**Язык.** Смена языка consolem перезагружает рамку с новым адресом и новым `lang`.

**Высота.** До первого `height` consolem даёт рамке 320 px. Значение `px` consolem ограничивает от 80 до 20 000 px. Это правило consolem, а не протокола.

## Как идёт «Применить»

1. Страница на каждую правку отправляет `change` с черновиком целиком. consolem кладёт черновик в свой черновик карточки, тот же, что у «Все параметры». У вида с ручным экраном consolem хранит правку по полям верхнего уровня, как черновик ручного экрана, и значение поля берёт из правки как есть. Поэтому поле-объект такая страница отдаёт целиком. Вложенную правку (`{"stream": {"fps": 10}}`) бэкенд сольёт по ключам, но ручной экран и план покажут её как всё значение поля.
2. consolem отбрасывает ключи правки вне схемы вида, поля `readOnly` и поля `x-transient`. О каждом таком ключе consolem один раз пишет предупреждение в консоль браузера.
3. Пока страница сообщает `invalid` с непустым списком, consolem не даёт нажать «Показать план». Пустой список `invalid` снимает запрет.
4. consolem пишет правку своим обычным путём карточки: «Показать план», проверка `POST /units/validate`, план, «Применить», `POST /operations` с `expectedVersions`. Журнал, уведомление с отсчётом и «Отменить», конфликт версий — общие для всех правок consolem. Это и есть «`PATCH` с `If-Match`» описания решения.
5. Перед записью consolem отправляет `flush {seq}` и ждёт `flushed` с тем же `seq` не дольше 2 секунд. Страница сначала отправляет `change` с вводом, который ещё не отправила, затем `flushed`. Если страница не ответила, consolem применяет то, что есть, и пишет об этом в уведомлении.
6. Если запись прошла, consolem отправляет `applied {unit}`. Только своё удачное «Применить» даёт `applied`. У черновика с шагами моста правило другое (раздел «Шаг 2: мост к механизму»).
7. Если бэкенд отверг правку в `POST /units/validate` (`422`), consolem отправляет `errors {problem}`. Страница подсвечивает свои поля. Поля, которых на странице нет, consolem показывает списком под рамкой со ссылкой «Все параметры». Конфликт версий (`412`) consolem показывает как у любой правки. Отказ `POST /operations` при «Применить» странице не приходит как `errors`: consolem показывает его, как у любой правки. Если в черновике нет шагов моста, consolem отправляет `revert` (п. 8). С шагами моста consolem отвечает иначе (раздел «Шаг 2: мост к механизму», «Применить» с шагами моста).
8. consolem отправляет `revert {unit}`, когда объект у бэкенда изменился или черновик опустел по действию consolem: «Сбросить», «Отменить» после записи, чужая правка при пустом черновике, неудачное «Применить» без шагов моста. При непустом черновике consolem не передаёт странице чужую правку: её найдёт конфликт версий при «Применить».

На шаге 1 consolem не проверяет черновик на ходу. Бэкенд проверяет правку один раз, по «Показать план».

## Режим `apply`

consolem называет режим применения в `init.host.apply`:

- `button` — человек нажимает «Применить» в consolem. Макет работает в этом режиме;
- `leave` — consolem применяет правку, когда человек уходит с карточки. Протокол для него готов (`flush` и `flushed`), но макет этот режим пока не делает.

Ни в одном режиме страница не рисует своих кнопок сохранения. Подсказку о режиме страница показать может.

## Страница не загрузилась

consolem ждёт `ready` 10 секунд. Если бэкенд не выдал адрес, дверь не ответила или `ready` не пришёл вовремя, consolem пишет, что страница подсистемы недоступна, и называет причину. Ниже consolem показывает форму по схеме вида, а у вида с ручным экраном — обычные вкладки ручного экрана. Поэтому объект можно настроить и без страницы. Кнопка «Загрузить страницу снова» берёт новый адрес и загружает страницу снова.

## Только просмотр

Страница `mode: iframe` ничего не пишет сама, поэтому бэкенд выдаёт её адрес по праву `view`. Бэкенд ставит `SetupUiLink.readOnly: true`, когда у человека право `view` без `edit`. Тогда consolem:

- отправляет странице `init` с `readOnly: true`;
- не показывает «Применить»;
- не принимает `change`.

Страница при `readOnly: true` делает поля неактивными. Человек с правом `view` видит ту же страницу, а не другой экран.

## Чего страница не делает

- Страница не пишет настройки объектов сама: ни через свою дверь, ни прямым запросом. Свой объект страница меняет через `change`, а другие объекты — шагами моста `draft` (шаг 2). Обе правки записывает «Применить» consolem.
- Страница не обращается к `/api/*` consolem и не получает куки и токен consolem.
- Страница не уводит consolem на другой адрес и не открывает окна.
- Страница не рисует кнопки «Сохранить» и «Отменить».

## Библиотека `setup-bridge.js`

Автор страницы может взять готовую библиотеку [`setup-bridge.js`](setup-bridge.js). Она отправляет `ready`, принимает `init`, проверяет `source` и происхождение, хранит черновик, отвечает на `flush` и сообщает высоту. Сообщения библиотеки точно повторяют схему: `python3 tools/check_api.py` прогоняет библиотеку в Node (`tools/check_setup_bridge.js`) и сверяет каждое её сообщение с `setup-ui.schema.json`.

**Как подключить.** Положить файл рядом со страницей и подключить обычным тегом, без сборки и зависимостей:

```html
<script src="setup-bridge.js"></script>
<script src="page.js"></script>
```

```js
SetupBridge.connect({
  fields: ["/properties/code_length", "/properties/beep"],
  onRevert: (unit) => show(unit.properties),
  onApplied: (unit) => show(unit.properties),
  onDraft: (patch) => show(SetupBridge.merge(session.unit.properties, patch)),
  onErrors: (problem) => mark(problem.errors || []),
  onTheme: (theme) => paintTheme(theme),
}).then((s) => {
  session = s;
  paintTheme(s.theme);
  show(SetupBridge.merge(s.unit.properties, s.draft));
});
// на каждый ввод — весь черновик
input.addEventListener("change", () => session.change(SetupBridge.diff(session.unit.properties, readForm())));
```

**`SetupBridge.connect(opts)` → `Promise<Session>`.** Библиотека сразу отправляет `ready` (с `opts.fields`, если они есть). Обещание сбывается, когда приходит `init`. Страница вызывает `connect` один раз: каждый вызов отправляет свой `ready` и добавляет свой обработчик сообщений. Поля `opts`, все необязательные:

- `fields` — указатели полей, которые показывает страница;
- `origin` — происхождение consolem, если автор знает его заранее. Оно главнее `ancestorOrigins` и `referrer`. Библиотека берёт от значения только происхождение (`new URL(origin).origin`), поэтому путь в адресе не мешает. Значение `"*"`, непрозрачное происхождение и не адрес библиотека не принимает: `connect` отказывает;
- `onDraft(patch, steps?)`, `onApplied(unit, steps?)`, `onErrors(problem)`, `onRevert(unit)`, `onTheme(theme)` — сообщения `draft`, `applied`, `errors`, `revert`, `theme`. Второй аргумент `steps` библиотека передаёт, если он есть в сообщении (шаг 2: шаги моста);
- `onFlush()` — consolem собирается применить правку. Страница отдаёт неотправленный ввод синхронно: вызывает `session.change(…)` или возвращает черновик. Если возвращённый черновик отличается от отправленного, библиотека отправляет `change`. Затем библиотека отправляет `flushed` с тем же `seq`, даже если `onFlush` бросил исключение: исключение библиотека пишет в консоль. Если `seq` не целое число от 1, библиотека пропускает `flush`;
- `autoHeight` — по умолчанию `true`: `ResizeObserver` на `document.body` отправляет `height` с высотой содержимого: низ `body` плюс его нижнее поле. Значение `documentElement.scrollHeight` не меньше высоты рамки, поэтому библиотека его не берёт: иначе рамка не становится ниже. Одно значение два раза подряд библиотека не отправляет. Если странице задать `body {height: 100%}`, низ `body` всегда равен высоте рамки, и рамка никогда не становится ниже. Поэтому высоту `body` страница не задаёт.

**`Session`** — объект после `init`:

- `init` — сообщение `init` целиком; `host`, `readOnly`, `theme` — его поля; `unit` — последний объект из `init`, `applied` или `revert`;
- `draft` — последний черновик, который страница отправила или получила. После `applied` и `revert` черновик становится `{}`, после `draft` черновик становится `patch`;
- `change(patch)` отправляет `change` с черновиком целиком и возвращает `true`. При `readOnly` библиотека ничего не отправляет и возвращает `false`;
- `invalid(fields, message?)` отправляет `invalid`. Пустой список снимает запрет;
- `height(px)` отправляет `height`: целое число от 0;
- шаг 2: `bridge` — `true`, если в `init.host` есть `bridge`;
- шаг 2: `can(op)` возвращает разметку операции из `init.host.bridge.ops` (`"read"`, `"act"`, `"draft"`) или `null`, если операции там нет;
- шаг 2: `call(op, {params?, body?})` отправляет `call` и возвращает `Promise` с ответом `{id, ok, status, body?, problem?, etag?}`. Обещание не отклоняется. Номер `id` выбирает библиотека, ответ она сопоставляет по `id`, а ответ с чужим `id` пропускает. Если consolem не ответил за 30 секунд, обещание сбывается с `ok: false`, `status: 0`, `problem.code: "UPSTREAM_UNAVAILABLE"`. У хоста шага 1 (`bridge` — `false`) библиотека ничего не отправляет и сразу отвечает `problem.code: "NOT_SUPPORTED"`;
- шаг 2: `subscribe({entityIds?, kinds?, types?}, onEvent)` отправляет `subscribe` и возвращает `Promise` с функцией отписки. Каждое `event` этой подписки библиотека передаёт в `onEvent(message)`. Функция отписки отправляет `unsubscribe` один раз, и события подписки больше не приходят в `onEvent`. Если consolem отказал (`BUSY`, `VALIDATION_FAILED`), обещание отклоняется, и у ошибки есть поле `problem`;
- шаг 2: `navigate(uid, tab?)` отправляет `navigate` и возвращает `Promise` с ответом `result`. После удачного перехода consolem закрывает рамку, поэтому обещание не сбывается. Если `uid` не строка или пустая строка, библиотека ничего не отправляет и сразу отвечает `VALIDATION_FAILED` с `field: "/uid"`;
- шаг 2: `confirm({title, text, lose?, keep?, count?, okLabel?})` отправляет `confirm` и возвращает `Promise<boolean>`: `true`, если пользователь подтвердил. Отказ consolem (`BUSY` и другие) даёт `false`. Если `title` не строка или пустая строка, библиотека сразу даёт `false`, пишет причину в консоль и сообщения не отправляет;
- у `navigate` и `confirm` срока ответа нет: отвечает пользователь. Если хост не называет сообщение в `init.host.bridge.messages`, библиотека ничего не отправляет: `subscribe` отклоняется, `navigate` сразу отвечает `NOT_SUPPORTED`, `confirm` даёт `false`.

**`SetupBridge.merge(base, patch)`** применяет JSON Merge Patch (RFC 7396) и возвращает новый объект: `null` снимает ключ, вложенный объект сливается, массив заменяется целиком. `base` не меняется. **`SetupBridge.diff(base, next)`** даёт правку от `base` к `next`: снятый ключ — `null`, вложенные объекты — рекурсивно, массивы — целиком. Если в `next` нет значений `null`, `merge(base, diff(base, next))` равно `next`. Значение `null` в правке снимает ключ, поэтому `null` из `next` после `merge` пропадает. Обе функции смотрят только на свои ключи объекта и пропускают ключ `__proto__`.

**Происхождение consolem** библиотека берёт из `opts.origin`, иначе из `location.ancestorOrigins[0]`, иначе из `document.referrer`. Библиотека принимает только сообщения от `window.parent` с `proto: "setup/1"`. Незнакомый `type` библиотека пропускает. Если происхождение известно, библиотека отправляет сообщения только на него и принимает только с него. Если происхождение непрозрачное (`"null"`, `"file://"`) или неизвестное, библиотека поступает так:

- если страница открыта с диска или её своё происхождение `"null"`, библиотека работает по правилу стенда из раздела «Адрес и рамка»: отправляет с `"*"`, принимает с `"null"` и `"file://"`;
- иначе `connect` отказывает (библиотека отклоняет обещание), ничего не отправляет и пишет причину в консоль. Тогда автор передаёт `opts.origin`.

Библиотека настройки не пишет. Всё, что меняет `properties`, идёт через `session.change` и «Применить» consolem.

**Образец** — тестовая страница стенда [`plugins/security_controller/setup/`](plugins/security_controller/setup/index.html) для вида `security_controller/KEYPAD`: `index.html`, `page.js`, `page.css`. Она подключает библиотеку как `../../../setup-bridge.js` и показывает четыре поля из пяти на двух своих вкладках. Ещё страница проверяет ввод (`invalid`), показывает ошибки `errors` у полей и отмечает кнопку вкладки с такой ошибкой, а ошибку поля не на странице называет подписью поля, делает поля неактивными при `readOnly` и берёт тему из `theme.tokens`. Запросов к своему серверу страница не делает. Если открыть её отдельно, без рамки consolem, страница пишет, что ждёт данные от консоли. `python3 tools/check_api.py` проверяет, что в разметке нет встроенного `<script>` и атрибутов `on…`, в коде нет `fetch` и `/api/`, а `ready.fields` совпадает с полями схемы вида, кроме `lock_after_tries`.

## Шаг 2: мост к механизму

На шаге 2 страница строит экран уровня карточки камеры или домена: объекты по ссылкам, найденное в сети, дочерние объекты, команды вида, переходы. Страница не обращается к `/api/*` сама. Она просит consolem, и consolem выполняет запрос своим токеном и с правами человека. Протокол остаётся `setup/1`: шаг 2 только добавляет сообщения (таблицы раздела «Сообщения», пометка «шаг 2»). Страница шага 1 на хосте шага 2 работает, и страница шага 2 на хосте шага 1 тоже работает.

### Что страница может вызывать

consolem называет мост в `init.host.bridge`:

```json
{"ops": {"getUnit": "read", "runUnitAction": "act", "createUnits": "draft"},
 "messages": ["call", "subscribe", "unsubscribe", "navigate", "confirm"],
 "limits": {"calls": 8, "subscriptions": 16, "watch": 199}}
```

- `ops` — операции, которые страница может вызывать, и их разметка `x-bridge`. В `ops` есть только операции с разметкой `x-bridge`, которые система объявила в `capabilities.operations`. При `readOnly: true` операций `draft` в `ops` нет.
- `messages` — сообщения шага 2, которые принимает consolem.
- `limits` — пределы моста (ниже, «Пределы»).

Если поля `bridge` нет, consolem — хост шага 1. Тогда страница показывает только шаг 1 и не отправляет сообщений шага 2. Чего нет в `ops`, страница не вызывает: она прячет эту часть экрана или показывает её по-своему.

### Разметка `x-bridge`

Что открыто мосту, говорит контракт. У каждой операции `api/openapi.json` есть расширение `x-bridge` или строка с причиной в списке закрытых (`BRIDGE_CLOSED` в `tools/check_api.py`). `python3 tools/check_api.py` не пропускает операцию без того и другого.

| `x-bridge` | Что делает consolem | Примеры |
|---|---|---|
| `read` | выполняет сразу | `getUnit`, `listUnits`, `getDiscovery`, `getTreeChildren`, `getCreatable` |
| `act` | выполняет сразу; команду видно в журнале, как из карточки. Если у команды `runUnitAction` или `runKindAction` есть `ActionDescriptor.confirm`, consolem сначала показывает свой диалог подтверждения (с вводом числа при `typeCount`) | `runUnitAction`, `runKindAction`, `startDiscovery`, `stopDiscovery` |
| `draft` | кладёт шаг в свой черновик и выполняет его по «Применить» | `patchUnit`, `createUnits`, `deleteUnit`, `moveUnit`, `deleteObjects`, `createOperation` |
| нет поля | отказывает: `NOT_SUPPORTED` | права и сеанс, запись вне склада, работа оператора, `/test/*` |

Мосту открыто то, что нужно экрану настройки объекта. Пути `/test/*` разметку не получают никогда.

### Вызов: `call` и `result`

Страница отправляет `call {id, op, params?, body?}`. Здесь `op` — `operationId` контракта, `params` — параметры пути и запроса по именам из описания операции, `body` — тело запроса. Номер `id` выбирает страница, и consolem повторяет его в `result`.

consolem отвечает `result {id, ok, status, body?, problem?, etag?}`:

- `read` и `act` consolem выполняет сразу. `status` — HTTP-статус ответа сервера, `body` — тело ответа как есть, `etag` — заголовок `ETag`, если сервер его дал;
- перед `runUnitAction` и `runKindAction` для команды с `ActionDescriptor.confirm` consolem показывает свой диалог подтверждения, как у той же команды в карточке: текст из `confirm.text`, ввод числа при `confirm.typeCount`. В шапке диалога consolem пишет строку «Спрашивает страница вида «<подпись вида>».», как у `confirm`. Если человек отказался, consolem не отправляет запрос и отвечает `ok: false`, `status: 0`, `problem.code: "CANCELLED"`. Сообщение страницы `confirm` этот диалог не заменяет: страница не может подтвердить команду сама. Чтобы узнать, есть ли у команды подтверждение, consolem читает вид объекта. Если объекта нет в кэше consolem, consolem сначала читает его (`GET /units/{uid}`), и этот запрос виден в журнале запросов. Если чтение не прошло, consolem не знает о подтверждении и не отправляет команду: он отвечает `ok: false`, `status: 0`, `problem.code: "UPSTREAM_UNAVAILABLE"`. Так же consolem отвечает, если вид объекта ему не знаком или если команды нет в описании вида из `/kinds` (у `runKindAction` — вид из `params.kind`; у `runUnitAction` — вид объекта из кэша consolem, даже если кэш устарел). Код здесь один, `UPSTREAM_UNAVAILABLE`: consolem не знает, нужно ли подтверждение. consolem читает описания видов заново по событию потока `kinds.changed` и после `stream.reset`. После этого новую команду вида страница может вызвать снова. Если сервер ответил на чтение отказом (например, `404`), consolem передаёт этот ответ странице как есть и тоже не отправляет команду;
- шаг `draft` consolem кладёт в черновик и отвечает `status: 202`, `body: {drafted: true, step}`. Номер `step` называет шаг в сообщениях `draft` и `applied`;
- если отказал сам мост, consolem не отправляет запрос и отвечает `ok: false`, `status: 0`, `problem {code, message, field?}`.

consolem права не пересчитывает. Отказ сервера (`403`, `404`, `422`) уходит странице как есть. Исключение — страница с `readOnly: true`: consolem не принимает от неё шаги `draft`. Значение параметра пути consolem кодирует (`encodeURIComponent`). Поэтому `params.uid = "../test/reset"` не ведёт на другой путь: сервер отвечает `404`.

**Коды отказа моста** (`status: 0`):

| `code` | Когда |
|---|---|
| `NOT_SUPPORTED` | у операции нет `x-bridge`; система не объявила операцию в `capabilities.operations`; шаг не выражается шагом операции |
| `VALIDATION_FAILED` | нет параметра пути или параметр незнакомый: `field: "/params/<имя>"`; тело шага `draft` не по схеме, например `UnitCreate` без `kind` или без `properties`: `field: "/body/…"`; поля `subscribe` за пределами или в `kinds` не вид объекта (раздел «Подписка на поток») |
| `PERMISSION_DENIED` | шаг `draft` у страницы с `readOnly: true`: `params: {readOnly: true}` |
| `NOT_SUPPORTED` (свой объект) | `deleteUnit` и `moveUnit` своего `uid` страницы, а также шаги `delete`, `move` и `folders` своего `uid` в `deleteObjects` и `createOperation`: страница не удаляет и не переносит свой объект и не меняет его папки шагом моста. `field` называет параметр или шаг |
| `BUSY` | вызовов или подписок больше предела; объектов во всех подписках больше `limits.watch`; второй `confirm`, пока первый открыт; открыт любой диалог consolem; второй `navigate`, пока первый не кончился; диалоги рамки на паузе после трёх отказов подряд в любых её диалогах (раздел «Подтверждение») |
| `CANCELLED` | человек отказался в диалоге consolem: подтверждение удаления, подтверждение команды с `ActionDescriptor.confirm`, переход с черновиком |
| `NOT_FOUND` | `navigate` к объекту, которого нет или которого человек не видит; `subscribe` с таким объектом в `entityIds` (`field: "/entityIds"`) |
| `UPSTREAM_UNAVAILABLE` | нет связи с сервером; перед командой `runUnitAction` или `runKindAction` consolem не прочитал вид объекта, вид ему не знаком или команды нет в описании вида (раздел «Вызов»): команда не уходит |

Код `CANCELLED` есть только в протоколе моста. В `ProblemCode` контракта его нет.

### Пределы

- В работе одновременно не больше 8 вызовов (`limits.calls`). Девятый вызов получает `BUSY`.
- Подписок не больше 16 (`limits.subscriptions`). Семнадцатая подписка получает `BUSY`.
- В одной подписке `entityIds` — не больше `limits.watch` объектов, `kinds` и `types` — не больше 32 строк, каждая строка — не длиннее 200 знаков. Иначе consolem отвечает `VALIDATION_FAILED` с полем. Схема `setup-ui.schema.json` задаёт те же пределы для `kinds`, `types` и длины строк. Число объектов в `entityIds` схема не задаёт: его называет `limits.watch`.
- В работе одновременно не больше одного `navigate` рамки. Второй `navigate` получает `BUSY`.
- Объектов во всех подписках не больше `limits.watch`. consolem даёт на одно место меньше предела наблюдения потока (`GET /reference` → `limits.watchMax`): это место занимает открытый объект. Подписка, после которой объектов стало бы больше `limits.watch`, получает `BUSY`, и consolem не добавляет её объекты в наблюдение.

### Как шаг `draft` ложится на шаг операции

consolem превращает вызов `draft` в шаг `OperationItemRequest` своего черновика:

| Операция | Шаг в черновике | Подтверждение consolem |
|---|---|---|
| `patchUnit {params: {uid}, body: UnitPatch}` | `{uid, patch: body}`; свой `uid` страницы — отказ `VALIDATION_FAILED`, `field: "/params/uid"`: свой объект страница меняет через `change` | — |
| `createUnits {body: {items}}` | на каждый `UnitCreate`: `{uid: item.parentId, createUnit: item}`; без `parentId` — `NOT_SUPPORTED`; тело consolem проверяет в момент вызова: `kind` — строка, `properties` — объект, `name` — строка, других ключей схемы `UnitCreate` нет, иначе `VALIDATION_FAILED` с `field: "/body/items/<i>/<поле>"` | — |
| `deleteUnit {params: {uid}}` | `{uid, delete: true}`; свой `uid` страницы — `NOT_SUPPORTED`, `field: "/params/uid"` | диалог удаления, число для ввода — 1 |
| `deleteObjects {body: {items: [{id, version}]}}` | на каждый: `{uid: id, delete: true}`; `id` не объекта склада — `NOT_SUPPORTED`; повтор `id` — один шаг | диалог удаления, число для ввода — `N`, число разных объектов |
| `moveUnit {params: {uid}, body: UnitMoveRequest}` | `{uid, move: body.parentId, params: остальное тело}`; свой `uid` страницы — `NOT_SUPPORTED`, `field: "/params/uid"` | — |
| `createOperation {body: OperationRequest}` | шаги `items` как есть; шаг `action` — `NOT_SUPPORTED`; `patch` своего `uid` — как у `patchUnit`; `delete`, `move` и `folders` своего `uid` — `NOT_SUPPORTED`; повтор шага `delete` того же `uid` — один шаг | если есть шаги `delete` — число разных объектов в них |

Удаление consolem подтверждает своим диалогом с вводом числа. В шапке диалога, как у `confirm`, стоит строка «Спрашивает страница вида «<подпись вида>».». Число объектов, которые пропадут, считает consolem, а не страница. Страница не может обойти диалог: если человек отказался, страница получает `CANCELLED`. Вложенные объекты сервер удаляет вместе с объектом. consolem считает в диалоге только прямых потомков (первый уровень) и так и пишет. Если объектов больше 20, consolem пишет о вложенных объектах без числа.

Страница не удаляет и не переносит свой объект: на нём держатся карточка и рамка. Папки своего объекта страница тоже не меняет шагом моста. Свой объект страница меняет только через `change`.

Версию объекта шага consolem берёт в момент вызова. Эта версия главнее версии, которую consolem узнал позже из потока. Поэтому чужая правка объекта между вызовом и «Применить» даёт конфликт версий (`412`), и consolem не затирает её.

Шаги моста лежат в черновике открытой карточки объекта страницы. Если человек открыл другую карточку, consolem закрыл рамку, и черновик карточки пропал вместе с шагами.

### «Применить» с шагами моста

- consolem показывает шаги моста в плане «Показать план» рядом с правкой страницы и отправляет странице `draft {patch, steps}`: `steps` — шаги моста в черновике `[{step, op, label}]`.
- «Применить» выполняет правку страницы и все шаги моста одной `POST /operations` с `expectedVersions`. После неё consolem показывает уведомление с «Отменить», как у любой правки карточки. «Отменить» откатывает всю операцию.
- Когда операция кончилась, consolem отправляет `applied {unit, steps}`, даже если свой объект страницы не изменился. `steps` — итог каждого шага моста по `OperationItem`: `[{step, state, code?, createdId?}]`. У шага `createUnit` в `createdId` стоит созданный объект.
- Если сервер отказал всей `POST /operations` (`412`, `422` и другие), consolem поступает так:
  1. consolem показывает отказ, как у любой правки карточки: `412` — как конфликт версий, другой код — уведомлением с причиной;
  2. consolem отправляет `applied {unit, steps}`: `unit` — объект, как он лежит у consolem, у каждого шага `state: "fail"` и `code` отказа;
  3. черновик и его шаги моста остаются, поэтому `revert` consolem не отправляет. Человек может исправить черновик или нажать «Сбросить».
  4. шаг, который вернулся в черновик, хранит прежнюю версию объекта. После `412` эта версия устарела, и следующее «Применить» снова даст `412`. Чтобы шаг прошёл, черновик нужно сбросить: человек нажимает «Сбросить», страница получает `revert {steps: []}` и вызывает свои шаги снова. Тогда consolem прочитает свежую версию.
- Если человек ушёл из карточки, пока шло «Применить», а сервер отказал операции, consolem не возвращает шаги в черновик: черновика этой карточки больше нет. Рамку consolem уже закрыл, поэтому `applied` страница не получает.
- Если consolem не смог прочитать итог операции (`GET /operations/{id}` не прошёл), у каждого шага моста `state: "fail"` и `code: "UPSTREAM_UNAVAILABLE"`. Сервер мог выполнить шаги, поэтому страница читает свои объекты заново.
- «Сбросить» и другие действия consolem, которые опустошают черновик, дают `revert {unit, steps: []}`.

### Подписка на поток: `subscribe`, `event`, `unsubscribe`

Страница отправляет `subscribe {id, entityIds?, kinds?, types?}`. consolem отвечает `result {id, ok: true, status: 200, body: {sub}}`. Номер подписки `sub` равен `id` из `subscribe`. Затем consolem пересылает странице каждое подходящее сообщение потока как `event {sub, message}`, где `message` — `StreamMessage` как есть.

- Сообщение подходит, если его `entityId` есть в `entityIds` или его `kind` есть в `kinds`. Если `types` задан, тип сообщения тоже должен быть в `types`.
- В `kinds` страница называет только виды объектов, которые consolem знает из `/kinds` (`UnitKind.kind`). Другое значение, например `discovery`, `rulePrompt`, `operation` или `exportJob` из поля `kind` сообщения потока, даёт `VALIDATION_FAILED` с `field: "/kinds"`, и consolem не открывает подписку. Такие сообщения страница получает по `entityIds`: например, события поиска в сети приходят подписке с `uid` домена.
- Подписка по `kinds` получает только те сообщения этих видов, которые и так приходят в поток consolem. Объекты этих видов consolem в наблюдение не добавляет. Сервер присылает события объекта только тому, кто его наблюдает, поэтому событие объекта, которого consolem не наблюдает, не придёт. Чтобы получать события объекта, страница называет его в `entityIds`.
- Объекты из `entityIds` пользователь должен видеть. consolem ищет их у сервера (`GET /units?ids=…`). Если объекта нет или пользователь не видит его, consolem отвечает `NOT_FOUND` с `field: "/entityIds"` и не открывает подписку.
- Сообщения `stream.reset` и `test.reset` consolem пересылает всем подпискам.
- Объекты из `entityIds` consolem добавляет в наблюдение потока, поэтому их события приходят.
- `unsubscribe {sub}` снимает подписку. Ответа на него нет.

### Переход: `navigate`

Страница отправляет `navigate {id, uid, tab?}`. consolem переходит к объекту по своему правилу перехода по ссылке: вспышка заголовка, вкладки и строки дерева. Если в черновике есть изменения, consolem сначала спрашивает человека. Если открыт другой диалог consolem или диалоги рамки на паузе (раздел «Подтверждение»), consolem не спрашивает и отвечает `BUSY`.

- После удачного перехода ответа нет: карточка другая, и consolem закрыл рамку.
- Если `uid` — объект самой страницы, consolem отвечает `ok: true`, и место моргает, даже если вкладка та же. Если `tab` — другая вкладка, consolem отвечает до смены вкладки: на другой вкладке рамки нет, и consolem её закрывает.
- Если человек остался на карточке, consolem отвечает `CANCELLED`.
- Если объекта нет или человек его не видит, consolem отвечает `NOT_FOUND`.

### Подтверждение: `confirm`

Страница отправляет `confirm {id, title, text, lose?, keep?, count?, okLabel?}`. consolem показывает свой стандартный диалог и отвечает `result {id, ok: true, status: 200, body: {confirmed}}`.

- В шапке диалога, над заголовком страницы, consolem пишет строку «Спрашивает страница вида «<подпись вида>».». Эту строку ставит consolem, а не страница, поэтому страница не может выдать свой вопрос за вопрос consolem.
- Все строки страницы consolem показывает текстом. HTML в них не работает.
- Списки «Пропадёт» (`lose`) и «Останется» (`keep`) consolem строит сам из строк страницы.
- Если задан `count`, человек вводит это число, как в диалоге удаления.
- Второй `confirm`, пока первый открыт, получает `BUSY`. Если consolem закрыл диалог страницы своим диалогом, страница получает `confirmed: false`.
- Если открыт любой диалог consolem (вопрос «Изменения не применены», удаление, подтверждение команды), consolem не открывает вопрос страницы поверх него и отвечает `BUSY`. Так же отвечают диалог удаления и подтверждение команды из моста.
- Если пользователь отказался три раза подряд, consolem 10 секунд отвечает `BUSY` на вопросы этой рамки. Счёт отказов у рамки один на все её диалоги: вопрос `confirm`, подтверждение команды `act`, диалог удаления шага `draft` и вопрос «Изменения не применены» перед `navigate`. Пауза тоже одна: на время паузы все эти диалоги получают `BUSY`, и consolem их не открывает. Пауза кончается раньше, если пользователь перешёл на страницу (фокус ушёл в рамку). Подтверждение в любом из этих диалогов обнуляет счёт отказов. Диалог, который закрыл другой диалог consolem, в счёт не идёт.

### Рамка закрылась

consolem отвечает только той рамке, которая спросила. Если рамка закрылась (человек открыл другой объект, рамку загрузили заново, страница не ответила), пока шёл вызов, подписка или диалог, consolem поступает так:

- ответ на вызов этой рамки consolem не отправляет никому;
- consolem снимает подписки рамки и убирает их объекты из наблюдения потока;
- consolem закрывает диалог `confirm` этой рамки без ответа.

### Видео

Живое видео (`startUnitLive`, `moveUnitLive`) мост не пропускает (решение владельца О5). Эти операции стоят в списке закрытых. Когда у API видео появится своё описание у системы, операциям этого описания нужна та же разметка `x-bridge`. До этого живой кадр страница берёт у своего сервера.

## Свои команды страницы

Своя логика плагина, которую платформа не знает, идёт от страницы прямо к её серверу через ту же дверь. Например, страница проверяет связь, калибрует датчик или запускает свой автодетектор. consolem в этом не участвует и о таких путях не знает.

| Что | Путь |
|---|---|
| Правка настроек объекта | черновик → «Применить» в consolem → бэкенд → плагин |
| Функция платформы: список, поиск, команда вида | страница → consolem (`call`) → бэкенд, с правами человека |
| Своя логика плагина | страница → свой сервер напрямую |

Две границы:

- **Своя команда не меняет настройки объекта.** Если итог команды — новые значения (калибровка подобрала порог), сервер возвращает их странице. Страница кладёт их в черновик (`change`), и человек нажимает «Применить».
- **Права на свои команды проверяет дверь.** Бэкенд выдаёт адрес страницы по праву человека (`view`, `edit`, `admin`). Дверь проверяет ранг на каждом маршруте. Человек с правом `view` открывает страницу, но дверь не выполняет его команду с маршрутом ранга `edit`.
