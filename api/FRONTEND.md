# Памятка для команды фронтенда

> **Для чего этот прототип.** Прототип API — основной макет `index.html`, переведённый на API. Это **спецификация поведения и эталон для проверки**, а не код продукта. По нему видно, что пользователь видит на каждом экране, что происходит при каждом действии и какие запросы при этом уходят на сервер. Он работает: его можно открыть, покликать и сравнить со своей реализацией.
>
> **Чем он не является.** Это **не готовое решение и не основа для кода**. Прототип — один HTML-файл на 1,5 МБ: глобальные функции, разметка, собранная строками, демо-данные, встроенный сервер и слой, который переводит ответы API в структуры старого макета. Так пишут макет, чтобы быстро проверять идеи, а не продукт. **Ни целиком, ни частями в продукт его не переносят** — интерфейс пишется заново на вашем стеке, с вашими компонентами, состоянием и тестами.
>
> **Что из него брать:**
> - **поведение** — [критерии приёмки](ACCEPTANCE.md);
> - **запросы** — [контракт](openapi.json);
> - **внешний вид** — сам прототип и дизайн-система ONE PSIM;
> - **решения сложных мест** — раздел «Что из прототипа — требование» ниже.
>
> Код прототипа читают, только чтобы понять, *как задумано* поведение. Копировать из него не нужно.

## Главное: у интерфейса нет своих данных

Всё, что в продукте хранит бэкенд, интерфейс получает и меняет только запросами контракта. Прототип так и сделан, и это проверяется: в его HTML не осталось ни одной константы с данными сервера.

- **При старте** интерфейс читает коллекции (`GET /domains`, `/servers`, `/devices`, `/folders`, `/archives`, `/volumes`, `/rules`, `/access`, `/settings`, …) и строит из них своё состояние. Рисует только после того, как всё пришло. `GET /rule-prompts` — сразу после старта, поток к этому моменту подключён: на большом домене старт уже на пределе 15 запросов (`tools/check_scale.py`).
- **Состояние меняется только ответом сервера или событием потока** — никогда до ответа. Оптимистичных обновлений в прототипе нет нигде. Если они понадобятся вам, это отдельное решение с откатом при ошибке.
- **Что остаётся у клиента** (на сервер не уходит): выбранный раздел и объект, раскрытие дерева, фильтры, ширина панели, тема, язык, избранное, черновики — карточки, групповой правки, прав.

## Что из прототипа — требование

Это решения, которые надо повторить по смыслу. Реализуйте их своими средствами. В скобках — где посмотреть поведение в прототипе (имена функций в `index.html`), чтобы понять задумку, а не чтобы скопировать.

| Решение | Как должно работать |
|---|---|
| **Черновик карточки** (`cardDiff`, `cardPlan`, `cardApply`) | Правки в карточке «Оборудования» копятся в черновике. Внизу — «Не применено: N», «Сбросить», «Показать план». План — строки «было → станет». «Применить» отправляет одну групповую операцию (`POST /operations`). При уходе с карточки с черновиком — вопрос «Сбросить и перейти / Остаться» |
| **Чужая правка при открытом черновике** (`hwFresh`) | Пришло изменение записи, у которой открыт черновик: поля, которые пользователь не трогал, берут новое значение; его правки остаются поверх. Чужое изменение не должно попасть в «было → станет» |
| **Очередь операции** (`apiQueue`, `opOnEvent`) | После «Применить» в шапке — очередь с ходом «N из M». Ход и итог по каждому шагу приходят событиями `operation.progress` и `operation.finished`, интерфейс сам ничего не отсчитывает. Пауза, «Отменить оставшееся», «Повторить неудачные» — запросы к операции. Есть отказы — открывается отчёт по шагам. Без отказов — тост с «Отменить», и «Отменить» — это `POST /operations/{id}/revert` |
| **Быстрые групповые действия** (`serversAssign`, `devicesMutate`) | Добавить серверы в домен, привязать к хранилищу на вкладке «Сеть», добавить устройства — один запрос с ответом `{done, failed}`. Не выполненное — тостом с причиной. «Отменить» — обратный запрос |
| **Удаление с отсчётом** (`askConfirm(…, {typeCount})`, `scheduleDelete`) | Подтверждение с вводом числа удаляемых объектов → отсчёт 10 с (15 с — больше трёх объектов) в тосте с «Отменить», отсчёт останавливается при наведении. Запрос уходит, только когда отсчёт кончился. Объекты на время отсчёта помечены в дереве и недоступны для правки |
| **Переименование в дереве** (`commitTreeRename`) | Enter или потеря фокуса → `PATCH`. Поле ввода остаётся открытым, пока нет ответа, чтобы старое имя не мелькнуло. Ошибка — тост, поле снова в фокусе |
| **Права — черновик целиком** (`accPlan`, `accSetSnapshot`) | Снимок прав (`GET /access`) — основа черновика. «Применить» — план, последствия для людей, затем `POST /access/apply` со всем черновиком и версией снимка. Защиту от самоблокировки интерфейс проверяет заранее как подсказку, но решает сервер (`409 SELF_LOCKOUT`). id новых ролей и пользователей — UUID, их создаёт клиент |
| **Поток событий** (`apiOnEvent`) | `entity.changed` → перечитать запись по id, если её версия новее известной. `entity.created` / `deleted` чужих записей → добавить или убрать. Своя запись могла прийти ответом раньше события — тогда событие ничего не делает. `stream.reset` или долгий обрыв → перечитать всё |
| **Поиск в сети** (`discStart`, `discOnEvent`) | «Обновить» запускает поиск на сервере. Находки приходят событиями по одной, с процентом хода. Мастер и вкладка «Сеть» одного домена слушают один и тот же поиск; если он уже идёт, второй экран к нему подключается |
| **План добавления устройств** (`planPush`, `planApply`, `planRetry`, `planRowIssues`) | Вкладки «В сети», «По адресу», «Из файла» ничего не создают: «В план» кладёт строки в план, в системе их нет до «Применить план». Производитель и модель проверяются по `reference.deviceModels`: регистр поправляется по списку, вне списка — ошибка в строке, правится в самом плане. Производитель `RTSP` — одно поле адреса потока вместо IP и порта. «Применить план» — один `POST /devices` на все строки с ключом идемпотентности; отказ остаётся в плане со своей причиной, «Повторить неудачные» шлёт только такие строки и с тем же ключом, пока состав не менялся. Сценарий — `tests/ui-plan.js`, приёмка — М-03…М-05 |
| **Экспорт** (`expFormUI`, `expMainHtml`, `expGroups`, `expBody`, `expCheckSoon`, `expOnEvent`; ADR-0117) | Состав — окно экспорта монитора one-psim-monitor: «Основное» (камеры, период с календарём дней записи, формат, «в один файл», имя файла, область кадра, супервизор, пароль, комментарий) и пять необязательных вкладок — «Качество видео», «Специальные опции» (кадру недоступна), «Выделение», «Конфиденциальность», «Титры»; вид — вкладки и карточки consolem. Сводка изменённого — в подсказке вкладки и счётчиком, вкладка с ошибкой — точкой. Раздел на рельсе: в выгрузке несколько камер. Из «Просмотра» камеры — «Экспорт…», «Кадр сейчас», «Выбрать область кадра» (рамка по видео), из «Отметок» — «Экспорт» у закладки. Списки — из `reference.export`, необязательное скрыто по `export*`. Каждая правка — `POST /exports/check`: ошибки у полей по `field`, внизу оценка и перекодирование. «Печать» — кадровое задание PDF, готовый файл открывается. Ход — `export.progress`, итог перечитывается по `export.finished` |
| **Ошибки по коду** (`problemText`) | Текст для пользователя — по `code` из ответа (`ProblemCode`), своими словами раздела. Поле `message` сервера — для журнала, не для экрана. Неизвестный код — «ошибка: КОД» |
| **Коды → подписи** | Сервер отдаёт коды и числа (`recordMode: "motion"`, `detectorKind: "linecross"`, `sizeBytes`, `usedPercent`). Подписи, единицы («4 ТБ») и переводы — на клиенте |
| **Время** | Всё время с сервера — в UTC. Показывается в часовом поясе системы (`GET /me` → `timezone`), а не браузера. Сроки («истекает через 3 дня») — от `serverTime`, а не от часов компьютера |
| **Без встроенного кода** (`onEv`) | Консоль VMS отдаёт страницу под CSP `script-src 'self'; object-src 'none'; base-uri 'none'`: код — только файлами со своего адреса, без встроенного `<script>`, без обработчиков в атрибутах (`onclick="…"`), без `eval` и `new Function`. Обработчики — `addEventListener`. Встроенные стили и картинки `data:` разрешены |
| **Моргание при переходе** (`accFlash`, `hwFlashLanding`) | Переход по ссылке подсвечивает место, куда пришли (критерий О-01) |
| **Возможности системы** (`capsLoad`, `can`, `data-needs`) | При старте — `GET /reference` → `capabilities`. Чего система не объявила, того нет на экране: пунктов меню, кнопок, вкладок, полей, видов в мастере; эти данные и не запрашиваются (нет `getDiscovery` — нет запросов поиска). Поведение поддержанного не меняется. В прототипе — `?fixture=one-domain` (критерий О-06) |
| **Черновик правила** (`ruleEdit`, `rulePlan`, `ruleApply`, `ruleSet`) | Правка правила копится в черновике, «Применить» — план «было → станет», затем правило целиком: новое — `POST /rules` (до этого его нет на сервере, id выдаёт сервер), прежнее — `PUT` с версией. Включённое с ошибкой не уходит: подсказка заранее, сервер тоже отвечает `422 RULE_INVALID`. Чужая правка при открытом черновике: нетронутые поля берут новое значение, правки пользователя остаются |
| **«Отменить» в «Автоматизации»** | Обратный запрос: новое правило — удалить, прежнее — `PUT` содержимого «до» с `historyNote: undo` (версия истории убирается, версия записи — новая); состояние и приглушение — `POST /rules/update` прежних значений; порядок — `POST /rules/reorder` прежнего |
| **Запуски правил** (`fireNode`, `ruleRunNow`, `ruleCheckRun`, `ruleTraceRetry`) | Трассу считает сервер: «Запустить», пробный запуск (на черновике, выбранных событиях, времени и исходах ветвлений), «Повторить невыполненное». Ответ — `RuleFire` кодами; подписи шагов, проверок и причин собирает интерфейс. Новые запуски других администраторов приходят событием `ruleFire` |
| **Вопросы операторам** (`promptsLoad`, `promptEvent`, `promptAnswer`, `promptTick`) | Колокольчик в шапке, на любом экране, если система объявила `listRulePrompts`; счётчик — только вопросы с `canAnswer`. Вопрос чужой роли виден без кнопок, со словом, кто отвечает. Панель открывается на месте, клик мимо её не закрывает, «Закрыть» и Esc закрывают, с панелью ассистента открыта одна из двух. Список — `GET /rule-prompts` сразу после старта и после `stream.reset`; потом только поток: `prompt.opened` — перечитать список (в событии нет текста), `prompt.closed` — снять строку. Опроса нет. Таймер — счёт до `until` по часам сервера: поправка берётся из `at` событий потока и `serverTime` в `GET /me`, наибольшая разница. Срок вышел — строка уходит словами. Ответ не ждёт итога: `202` оставляет строку с «Ответ отправлен», снимает её `prompt.closed`. `409 BUSY`, `409 NOT_RUNNABLE`, `404` — строка снимается со своим словом. Звук — только новый уровень `escalate` с `canAnswer`, Web Audio; отказ браузера работе не мешает, выключение — рядом с колокольчиком, настройка в `localStorage` |
| **Правка принята, не применена** (`problemKept`, `keptNote`) | `SERVER_OFFLINE` с `params.kept` — не отказ: «Принято, применится», в групповых строкой элемента, без «Отменить»: откатить нельзя. Вторая правка до применения первой — `412`, форма говорит это словами |
| **Панель ассистента** (`asstRender`, `asstFromSearch`, `asstSendText`, `asstEnd`) | Панель — верх окна поиска, под ней обычные секции: «В дереве», «Не в дереве», «Недавние», «Разделы». Под ответом — поле и «Отправить» (при плане — «Уточнить»), Enter отправляет: ответ на вопрос и уточнение плана идут тем же разговором с `context`. Просьба из строки поиска (Enter с набранным, что бы ни нашёл поиск, или «Новый диалог с ассистентом» над окном) — всегда новый разговор: `context`, план и секреты забыты, идущий ход снят. Строка, выбранная стрелками, — Enter выбирает её. Без ассистента Enter — фильтр, как раньше. Над ответом — последние пять просьб, старые сверху, длинная — одной строкой с многоточием, целиком в подсказке. «Закрыть» и «Нового разговора» нет: клик мимо, Esc, колокольчик скрывают панель, разговор, идущий ход, секреты и набранное в поле живут; клик или фокус в строке возвращает её как была. Ход ассистента курсор не забирает ни из карточки, ни из строки поиска, даже пустой |
| **План настройки в дереве** (`asstPlanToTree`, `asstPlanDraft`, `ASST_DRAFT`, `bulkDraft.plan`, `bulkDraft.planVer`, `asstPlanOpen`) | План с `items` в панели — текст; «Применить» и «Отказаться» нет, «Открыть в дереве» — только когда план в дереве не виден (тег снят, другой раздел или срез). Дерево показывает объекты плана тем же тегом отбора «Ассистент: N», все отмечены, открыта групповая карточка (и для одного объекта). Значения плана — слой черновика по объектам: поле `DevicePatch` → ключ карточки (`recordMode` → «Режим», `enabled`, `preRecordSec`, `login`, `password`, `archiveId`, `res`, `fps`), одно у всех — стоит в поле, разные — «— разные —» и раскладка «по плану ассистента» под полем; поле подсвечено. `bulkChanges` строит шаг на значение, каждому объекту своё. Поле, заданное человеком, заменяет значения плана; «Сбросить» снимает всё. «Применить» — обычный план карточки, одна операция с откатом, `expectedVersions` — версии плана. Поля вне карточки названы словами в панели, обхода нет. Уточнение снимает слой плана, правки человека остаются |
| **Отбор ассистента над деревом** (`asstPick`, `asstPickSet`, `asstPickClear`, `pickWave`, `asstFoundToTree`, `asstFoundPick`) | Общий механизм для `found` и, дальше, для плана настройки. Дерево показывает только отобранное: тег над деревом «Ассистент: N из total» и условия словами, крестик снимает его, срез возвращается как был, выбор остаётся. Механизм — волны поиска (`fs`): у `ids` записи и цепочки `/tree/paths` дочитываются кусками до `idsMax`, до `idsMax` — дерево, больше — плоский список страницами; у `filter` — `GET /devices` с фильтрами отбора, как обычный фильтр дерева. `truncated` — словами в подсказке. В панели текст, число, условия, «Выбрать всё» и «Показать в дереве» — только когда отобранное в дереве не видно (тег снят, другой раздел или срез); — отобранное в выбор для групповой правки, до `selectMax` |
| **План правил от ассистента** (`asstRulesLoad`, `asstRuleView`, `asstRulesApply`) | Поля `kind` в запросе нет ни в каком разделе: что за реплика, решает сервер или служба по каждой реплике; тип не показан и не выбирается. План читает записи `update` при показе, разницу считает `ruleDiffOf` из строк плана, сводка модели подписана отдельно. «Применить» — двери контракта по порядку, новое правило `asstNewRule` делает наблюдающим, итог — по строке на запись |
| **План выгрузки от ассистента** (`asstExportHtml`, `expFromAssist`, `expDraftOf`) | `AssistEvent.export` открывает раздел «Экспорт» с этим заказом — тем же путём, что «Повторить» (`expDraftOf`), и зовёт `/exports/check`: ошибки у своих полей. Пароль и супервизора вводит человек, заказ создаёт кнопка «Экспорт» окна. В панели — камеры, вид, время, формат и «Открыть выгрузку» |
| **Режим объекта** (`ruleModeSwitch`, `modeCurLoad`) | Текущий режим считает сервер (`GET /modes/current`), меняется событием `objectMode`. «Включить вручную» — `POST /modes/current` до следующей смены по расписанию (обслуживание — до отмены); «Отменить» — прежнее состояние. Режимы правятся списком целиком (`PUT /modes`), id нового — UUID клиента |
| **Расписания, особые дни, окна** (`schSave`, `grpEdit`, `maintEdit`) | Расписание правится в редакторе черновиком, «Сохранить» — `POST`/`PUT`. ## Что ещё за вами

Этого в прототипе нет вовсе или есть только обозначено:

- **Вход и сессия.** В прототипе администратор уже вошёл. Ответ `401 UNAUTHORIZED` должен вести на вход: прототип переходит по адресу из `<meta name="consolem-login">` (в сборке для консоли — `../`), а если его нет — показывает «Сессия истекла». Поток событий при обрыве спрашивает `GET /me`: `401` — тоже на вход, иначе переподключается.
- **Права администратора.** В прототипе все кнопки доступны всем. В продукте кнопки и разделы зависят от функций роли (`DEVICES_SETUP`, `USERS_RIGHTS_SETUP` и т. д.), а `403 PERMISSION_DENIED` и `404` для невидимого объекта надо показывать. Модель прав администратора ещё не согласована — [BACKEND.md, «Что ещё не решено»](BACKEND.md#что-ещё-не-решено).
- **Каталог строк и переводы.** Подписи сейчас разбросаны по коду прототипа и `assets/i18n-en.js`; нужен свой каталог.
- **Большие инсталляции.** Прототип читает всё целиком, на демо-объёме это работает. На тысячах объектов нужна постраничная загрузка и серверный поиск — тоже открытый вопрос.
- **Доступность, клавиатура, поддерживаемые браузеры** — по вашим стандартам. Прототип проверялся в Chrome.
- **Видео, карты, живые кадры** в прототипе нарисованы.

## Как говорить с бэкендом

- **Адрес API** — настройка сборки или окружения; в прототипе — `?api=…` или `<meta name="consolem-api">`, адрес можно дать относительно страницы (`api`). Все запросы — с `credentials: "include"`, тело — JSON.
- **Версии.** Запомните `version` (или `ETag`) каждой прочитанной записи. Это непрозрачная строка: сравнивайте её только на равенство, не разбирайте и не вычисляйте следующую. Изменение отправляйте с `If-Match: "<version>"`, групповую операцию — с `expectedVersions` всех объектов. `412` — запись изменилась: перечитать и показать пользователю. `428` — ошибка вашего кода: версию не передали.
- **`idempotencyKey`** создавайте один раз на действие пользователя и повторяйте его при повторе после сетевой ошибки — тогда сервер не выполнит действие дважды.
- **Поток.** `new EventSource(адрес + "/stream", { withCredentials: true })`; сообщения без `event:`, тип — в `data.type`. После переподключения браузер сам пошлёт `Last-Event-ID`. Пришёл `stream.reset` — перечитайте всё.
- **Частичный успех** — норма, а не ошибка: в ответах `{done, failed}` и в шагах операции у каждого объекта свой итог.
- **Разрабатывать можно уже сейчас**, не дожидаясь бэкенда: `node tools/serve_api.mjs` поднимает стенд на эталонных данных с тем же контрактом. `POST /test/reset` возвращает данные в исходное состояние.

## Когда готово

1. Все критерии [`ACCEPTANCE.md`](ACCEPTANCE.md) выполняются против стенда (`tools/serve_api.mjs`, затем стенд бэкенда), и при задержке ответа 300 мс тоже.
2. Экраны выглядят как в прототипе: в светлой и тёмной теме, по-русски и по-английски (критерий О-05).
