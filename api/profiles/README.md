# Профили

В этой папке лежат профили видов. Файл `<имя>.json` — источник истины. Таблицу `<имя>.md` собирает `tools/build_api.py`, руками её не правят.

## Что такое профиль

Профиль — договорённость об именах полей особого экрана. В него входят все поля, которые экран показывает. Профиль называет свойства (`properties`), наблюдаемое состояние (`status.observed`) и предметные пути (`apis`). Для каждого имени профиль фиксирует тип и смысл.

Вид объявляет профиль в `implements`. Такой вид несёт свойство под тем же именем, того же типа и с тем же смыслом. Тогда ручной экран консоли работает с видом без правки. Поля вида сверх профиля живут под своими именами. Поля, которого нет на особом экране, в профиле нет: оно есть только в схеме вида и в «Все параметры».

Профили публикует сервер: `GET /kinds` отдаёт их в разделе `profiles` (схема `Profile` в `api/openapi.json`). Раздел `profiles` в `api/fixtures/demo.json` собирает `tools/build_api.py` из этих файлов.

## Файл профиля

Имя файла — имя профиля без `/<старшая версия>`: `vms.camera/1` лежит в `vms.camera.json`.

| Поле | Что значит |
|---|---|
| `id` | имя и старшая версия: `vms.camera/1` |
| `version` | младшая версия вместе со старшей: `1.5`. Старшая версия равна номеру в `id` |
| `label` | название профиля для людей |
| `owner` | кто ведёт профиль |
| `reviewers` | кто смотрит правку: команды бэкендов, которые объявили профиль |
| `uses` | от каких профилей и каких версий зависит профиль: список `{id, version}` |
| `properties`, `status` | поля: у каждого `schema` (кусок JSON Schema), `meaning` (смысл) и `since` (версия, с которой поле есть) |
| `apis` | предметные пути объекта, например `recording-days` |
| `changes` | что менялось по версиям, новые сверху. У строки есть `version`, `what` и необязательный список `removed` (снятые поля) |

## Версии

- Новое поле — новая младшая версия: поднять `version`, поставить полю `since` этой версии, добавить строку в начало `changes`.
- Поле снято, переименовано или сменило тип — новая старшая версия. Создать профиль `<имя>/<N+1>` рядом со старым. Для контракта это добавление. Старый профиль снимает его owner после ответа reviewers.
- Вид пишет в `implements` только старшую версию: `vms.camera/1`. Младшую версию сервер отдаёт в `GET /kinds`.

Клиент читает версию так:

1. Сервер прислал младшую версию выше, чем знает клиент (`1.7` при известной `1.5`). Особый экран работает. Новые поля клиент показывает в «Все параметры».
2. Сервер прислал младшую версию ниже (`1.4` при известной `1.5`). Особый экран не показывает поля, которых в `1.4` нет.
3. Сервер прислал незнакомую старшую версию (`vms.camera/2` без `vms.camera/1`). Клиент пропускает профиль и открывает объект формой по схеме.

## Зависимости

Профиль называет в `uses` каждый профиль, на который ссылается. Если в схеме поля есть `x-ref` на другой профиль, этот профиль должен быть в `uses`. Версия в `uses` — самая младшая, с которой профиль работает. Профиль не использует сам себя. Взаимные зависимости разрешены.

Если у зависимости появилась новая старшая версия, проверка показывает, какие профили это задело. Например, ломающая правка камеры (`vms.camera/2`) сразу задевает кассу.

## Как собрать и проверить

1. Правка файла профиля. Если правка меняет вид, правка схемы вида в `api/fixtures/demo.json`.
2. `python3 tools/build_api.py` собирает раздел `profiles` в `demo.json`, наборы, таблицы `<имя>.md`, `api/openapi.js` и `api/fixture.js`.
3. `python3 tools/check_api.py` проверяет профили пятью строками «Профили …»:
   - файлы устроены по формату;
   - раздел `profiles` наборов собран из файлов;
   - виды несут поля профиля того же типа, а `status` объектов совпадает со схемой профиля;
   - версия профиля выросла вместе с правкой, а снятых полей нет (сверка с `origin/main`);
   - зависимости из `uses` есть, и их версия не ниже указанной.

`python3 tools/build_api.py --check` проверяет, что собранные файлы не отстали от файлов профилей.
