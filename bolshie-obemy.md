# Миллион камер в конфигураторе: почему интерфейс не тормозит

Записка для разработчиков фронтенда и бэкенда. 2026-11-07.

## Коротко

- **Задача решена на стороне интерфейса.** Макет (`index.html`) работает с системой на **1 000 000 камер, 2 000 серверов и 1 200 папок в четырёх доменах** (стенд `xl`). Он открывается сразу, дерево раскрывается, поиск ищет, карточки открываются, и вкладка не зависает.
- **Клиент не скачивает систему целиком.** Он читает только то, что пользователь видит: дерево — по веткам и страницами по 200 строк, поиск — порциями. Всё остальное остаётся на сервере.
- **Объём лежит на сервере, и сервер отдаёт его страницами.** Для этого нужны индексы, страницы с курсором и поиск, который проходит склад кусками. Всё это описано в контракте `api/openapi.json` и проверяется тестами.
- **Бэкенду не нужно изобретать.** Достаточно сделать по контракту то, что уже делает тестовый сервер в репозитории. Тесты API (361 проверка) покажут, где реализация расходится.

## Что можно проверить самому

Тестовый сервер — это тот же код, что встроен в страницу (`api/server.js`), только за настоящим HTTP:

```
node tools/serve_api.mjs 8787 --fixture xl
```

Затем откройте `index.html?api=http://127.0.0.1:8787`. Набор `xl` сервер строит при запуске, это несколько секунд. После этого интерфейс открывается сразу.

Скорость меряет `python3 tools/check_perf.py`. Инструмент открывает страницу в настоящем Chrome, нажимает клавиши и мышь и считает, сколько ждёт оператор (подробно — `api/TESTS.md`, раздел 9).

## Сервер в странице и отдельный сервер

Тестовый сервер можно запустить двумя способами. Код у них один, отличается только то, где сервер работает.

- **Сервер встроен в страницу** (`index.html` без `?api=`, так открывается сайт на GitHub Pages). Сервер работает в той же вкладке, что и интерфейс. Он строит набор данных прямо в браузере и делит с интерфейсом один поток. На демо-наборе этого не видно. На миллионе камер старт занимает около 3 с: столько вкладка строит миллион объектов. Это работа тестового сервера, а не интерфейса, но со стороны её не отличить. Поэтому в таком режиме трудно увидеть, как быстро на самом деле работает интерфейс.
- **Сервер запущен отдельно** (`node tools/serve_api.mjs 8787 --fixture xl` и `index.html?api=http://127.0.0.1:8787`). Набор данных один раз строит процесс сервера при своём запуске. Вкладка только задаёт вопросы по HTTP и получает страницы ответов. **Интерфейс открывается сразу, без задержки, даже на миллионе камер.** Так он будет работать с настоящим бэкендом.

Чтобы увидеть настоящую скорость интерфейса, запустите сервер отдельно.

## Почему старт быстрый

На старте клиент делает около 18 запросов и не читает ни одной камеры из сотен тысяч:

1. Виды объектов: `GET /kinds`.
2. Домены и серверы: `GET /units?implements=vms.domain/1,vms.server/1`.
3. Корень дерева: `GET /tree/children`.

Большой домен на старте свёрнут, кроме домена открытого объекта. Что в нём, клиент прочитает, когда пользователь раскроет ветку.

Числа у доменов и в срезах («Камеры», «Хранилища»…) клиент не считает сам. Он берёт итог сервера и помечает, насколько число точное:

- «≈» — оценка сервера;
- «+» — консоль прочитала ещё не всё.

## Дерево: по веткам и страницами

- Раскрыли сервер или папку — клиент запрашивает `GET /tree/children?parentId=…&layout=…`. Сервер отдаёт до 200 строк и курсор `nextCursor`, если строк больше.
- Внизу длинной ветки стоит «Показать ещё»: следующая страница по курсору.
- Курсор хранит ключ последней строки, а не номер. Если кто-то добавил объект, уже показанные строки не съезжают и не повторяются.
- Клиент держит в памяти только прочитанное. Его объём растёт от действий пользователя, а не от размера системы.
- Браузер не раскладывает строки за пределами экрана (`content-visibility`), а свёрнутые ветки вообще не строятся. Тысячи строк в дереве не тормозят.
- Дерево перерисовывается не чаще одного раза за кадр.

## Поиск: порциями, «волнами»

- Поиск начинается через 200 мс после последней буквы. Сама буква видна в поле сразу, а Enter, Esc и крестик тоже срабатывают сразу.
- Запрос: `GET /units?q=…`. Сервер идёт по складу **ограниченным проходом**: одну страницу он набирает до `limit` найденных или до бюджета времени. Затем отдаёт найденное и курсор продолжения.
- Клиент сразу показывает первые результаты и запрашивает следующие порции («Ищем дальше»). Поиск редкого слова на 250 000 камер — около шести порций, примерно полсекунды.
- Очистка поиска возвращает дерево к прежнему виду. Открытое и отмеченное остаётся на месте.

## Выбор и групповые действия

- **Отметки.** Галочками за один раз отмечается не больше 500 объектов (`selectMax` в `/reference`). Больше — следующей операцией, и у каждой операции свой откат.
- **Ассистент.** Если пользователь просит отобрать большое множество, ассистент отвечает фильтром и числом, а не списком id: «Отобрано: 975 000. Листается фильтром». На миллионе камер такой ответ приходит за 0,4 с.
- **Долгие операции.** Они идут через `POST /operations`: шаги выполняются по одному, ход приходит в поток событий, у каждого шага свой итог.

## Изменения на лету

Клиент не перечитывает систему, чтобы узнать об изменениях. Сервер сам присылает события в поток `GET /stream` (SSE): создан, изменён, удалён, сменился статус. Клиент обновляет только затронутые строки.

На стенде 100 событий связи камер подряд обрабатываются примерно за 0,1–0,4 с и не мешают работе.

## Что это требует от бэкенда

То же, что уже делает тестовый сервер. Подробно — `api/BACKEND.md` и `api/README.md`, «Договорённости».

1. **Индексы.** Дети узла, объекты вида, домена, папки и ссылки сервер берёт из индекса, без перебора всего склада.
2. **Страница по курсору.** Ответ — не больше `limit` строк и `nextCursor`. Ключ курсора не сдвигается от вставок. Сортировать все строки ради одной страницы не нужно: достаточно отобрать первые `limit` после курсора.
3. **Ограниченный проход для отбора и поиска.** Сервер проходит склад по разделам и дописывает страницу до `limit` или до бюджета времени. Рекомендация бэкенду — около 100–200 мс на страницу. Пустая страница с `nextCursor` допустима: клиент её выдерживает.
4. **Итоги вместо перечислений.** Числа для доменов и срезов сервер считает сам и отдаёт готовыми, при необходимости как оценку.
5. **Поток событий.** Изменения сервер присылает событиями. Клиент не опрашивает систему целиком.
6. **Групповые действия — операциями.** Сервер выполняет шаги, клиент показывает ход.

Готовность проверяется тестами API: откройте `tests/api.html?api=<адрес вашего стенда>` или запустите `python3 tools/run_api_tests.py`. Сейчас тестовый сервер проходит все 361 проверку.

## Цифры

Время ожидания оператора — `tools/check_perf.py`, настоящий Chrome, сервер в той же вкладке, замер 2026-11-07.

| Действие | Стенд `large`, 250 000 камер | Стенд `xl`, 1 000 000 камер |
|---|---|---|
| Раскрыть сервер, открыть камеру, сервер, домен | в пределах 0,3 с | в пределах 0,3 с |
| Вкладка домена «Папки» | — | 40 мс |
| Группировка «Серверы» | ~0,15 с | — |
| Поиск «Камера» | ~0,3 с | — |
| Поиск редкого слова («Кластер») | ~0,5 с | ~1,4–1,8 с |
| Ассистент: отбор камер без папки | — | 0,4 с |
| 100 событий потока подряд | ~0,1 с | ~0,4 с |

На `large` в пределе 37 шагов из 38. На `xl` выше предела старт, поиск редкого слова и два шага «Хранилищ» (0,2–0,25 с при пределе 0,2 с, ниже). Старт на `xl` около 3 с только у сервера, встроенного в страницу (раздел «Сервер в странице и отдельный сервер»). С отдельным сервером интерфейс открывается сразу.

## Что ещё не идеально

- **Поиск редкого слова на миллионе** — 1,4–1,8 с. Это порции прохода тестового сервера. Настоящий бэкенд с индексом по словам найдёт быстрее.
- **На `xl` у предела 0,2 с** срез «Хранилища» и открытие хранилища: 0,2–0,25 с. Основное время там уходит на сборку мусора браузера при миллионе объектов в той же вкладке. С отдельным сервером этой нагрузки во вкладке нет.

Это ограничения тестового сервера, а не устройства интерфейса.
