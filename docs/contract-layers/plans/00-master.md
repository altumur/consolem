# Контракт по слоям — общий план работ

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Этот файл — оглавление и порядок: задачи лежат в планах частей 01–07, исполняются по очереди, часть за частью.

**Goal:** провести переделку контракта consolem по слоям целиком: общий механизм без слов VMS, описания подсистем в профилях со своей версией и хозяином, тесты по слоям, экран по профилю и своя страница подсистемы в iframe с мостом к механизму.

**Architecture:** механизм (`/kinds`, `/units`, дерево, операции, права, журнал, правила, `capabilities`) — один для любой системы; виды, поля, команды, раскладки VMS — данные подсистем и профилей (`api/profiles/*.json`). Граница видна в контракте (`x-layer`) и закреплена проверками `tools/check_api.py`. Интерфейс выбирает экран по трём ступеням: своя страница подсистемы → ручной экран по профилю → форма по схеме.

**Tech Stack:** `api/openapi.json`, встроенный сервер `api/*.js`, наборы `api/fixtures/`, тесты `tests/api-*.js` и `tests/ui-*.js`, инструменты `tools/*.py`, макет `index.html` и прототипы.

**Spec:** [предложение о слоях](../2026-11-16-kontrakt-i-podsistemy-predlozhenie.md), [своя страница подсистемы](../2026-11-18-setup-ui-iframe-design.md), [«всё — плагин»](../2026-11-18-everything-is-a-plugin.md); позиция w2c — [запрос](../../../api/requests/2026-11-18-114831Z-w2c-contract-layers-request.md) и [ответ](../../../api/requests/2026-11-18-114831Z-w2c-contract-layers-response.md); запрос к w2c — [своя страница в iframe](../../../api/requests/2026-11-18-120707Z-owner-setup-ui-iframe-request.md).

## Сверка частей

Планы частей писались параллельно. Где они расходились, решение ниже, и оно главнее текста части.

- **С1. Слой: два словаря, одно соответствие.** В контракте (часть 01) `x-layer` — `<id профиля>`, `video` или `vms`; нет пометки — механизм. У теста (часть 03) `layer` — `mechanism`, `video` или `profile:<id>`. Соответствие: `x-layer: <id>` = `layer: profile:<id>`; `video` = `video`; `vms` (часть VMS, ещё не вынесенная из механизма) = `mechanism`, пока часть 04 не перенесёт её в профиль, — тогда тест получает слой этого профиля. Проверка части 03 «слой у каждого теста» может брать слой пути из `layer_of_path` части 01, но не обязана.
- **С2. Незнакомая старшая версия профиля — только в части 07.** Задача 7 части 02 (прототип `index_NN_profil-starshaya-versiya.html`, `screenProfile`, `PROFILE_SCREEN_CODES`) **снята**: ту же ошибку `screenType` чинит задача 1 части 07 (`handScreenOf`, `vms.camera/2` → форма по схеме) тем же тестом. Часть 02 кончается задачей 6.
- **С3. Ступень 1 — через `screenPageStep` части 07.** Часть 05 не заводит свой выбор экрана: она заменяет тело `screenPageStep(kind)` (часть 07) — `"page"` у `setupUi.mode: iframe` с поддержанным `protocol` и видом в `setupUi.kinds`, `null` у `mode: tab`. `suiKindOf(n)` и `suiOn(n)` части 05 строятся на `screenPageStep(nodeKind(n)) === "page"` плюс отметка `setupUi` в `n._caps` и полная запись (`!n._row`).
- **С4. Страница не меняет тип узла.** В части 07 сказано «узел вида со страницей — узел формы по схеме». Заменяется так: ступень 1 тип узла не меняет, тип даёт ступень 2 или 3. У вида с ручным экраном и страницей узел остаётся ручным, поэтому вкладки механизма (`SUI_MECH_TABS`: «Доступ») остаются, как требует вариант А описания решения, раздел 4. Так уже написан `tabsFor` части 05 (`isSchemaNode(n) ? [] : tabsForHand(n).filter(…SUI_MECH_TABS…)`).
- **С5. Разметка `x-bridge` — по контракту на момент части 06.** Таблица части 06 снята с контракта 0.23.0. Часть 04 переносит пути поиска, сценариев и ретрансляторов (`operationId` те же) и добавляет `getExportReference`. Исполнитель части 06 размечает операции контракта, каким он стал, а `check_bridge` не пропустит неразмеченную.
- **С6. «Применить» у страницы — путь карточки.** Часть 05 пишет правку обычным путём карточки (план → `/units/validate` → `POST /operations` с `expectedVersions`), а не прямым `PATCH` с `If-Match`. Это и есть «обычный путь» раздела 6 описания решения; описание поправит задача 2 части 05 (`api/SETUP-UI.md`).
- **С7. Проверяющие профиля.** Часть 01 ставит по умолчанию `reviewers: ["w2c"]`, часть 02 — `["w2c", "NGP"]`. До решения владельца (вопрос О1) — `["w2c"]`: адресата NGP в таблице «Кому» нет, уведомлять некого.
- **С8. Правила процесса последними в части 01.** Задача 4 части 01 (правила в скилле `api-contract`, `CLAUDE.md`) идёт после `tools/layers.py` и таблицы версий, чтобы правила не ссылались на то, чего нет. Оговорку «пока файла профиля нет» снимает часть 02 (задача 5).
- **С9. Прототипы по одному на часть.** Прототипы заводят части 07, 04, 05 и 06 — по одному, каждый копией `index.html` после переноса прошлого. Прототип части не переносится, пока не прошли проверки прототипа (`--page`, `?selftest`, `check_perf --page`, если часть трогает дерево, поиск, выбор или поток: 04, 06).

## Как исполнять

**Решено владельцем 2026-11-18: subagent-driven** (`superpowers:subagent-driven-development`), в отдельной сессии Claude Code. На каждую задачу — свежий исполнитель, после неё — свежий проверяющий, в конце каждой части — проверка всей части. Причина: 59 задач в 7 частях, задачи одной части опираются на имена соседних (Interfaces), а ошибка в контракте уходит к w2c.

- Части — строго по очереди (01 → 02 → 03 → 07 → 04 → 05 → 06), внутри части — по порядку задач. Параллельно идут только задачи, которые план части прямо называет независимыми.
- **Push в `main` — один раз, в конце всей работы** (решение владельца 2026-11-18; заменяет правило `CLAUDE.md` «сразу push» на эту работу). После каждой части — `git fetch origin && git rebase origin/main`, чтобы правки коллег приходили сразу; хеши коммитов в запросах к w2c — после финального push.
- После каждой части — короткий отчёт владельцу: что сделано, коммиты, версия контракта, прототип, что подготовлено для w2c, что принёс rebase. Затем — следующая часть без ожидания, если владелец не сказал иначе.
- Остановиться и спросить владельца: проверка падает и причину не найти; при rebase чужая правка несовместима с планом; решение не покрыто ни планом, ни «Сверкой частей», ни умолчаниями.
