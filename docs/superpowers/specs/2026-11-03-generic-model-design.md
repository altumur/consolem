2026-11-03 · основа: запрос [`2026-11-03-065231Z-mockup-generic-model-request.md`](../../../api/requests/2026-11-03-065231Z-mockup-generic-model-request.md),

сценарии — Е) и ответ altumur [`…-response.md`](../../../api/requests/2026-11-03-065231Z-mockup-generic-model-response.md).
Состояние репозитория — `0c8f18e`.

## 1. Зачем

WebUI конфигуратора должен настраивать объекты **расширяемых** VMS: виды объектов появляются после выпуска WebUI (плагины psim
в NGP, подсистемы w2c, новые `Unit` NGP). Сейчас контракт `api/openapi.json` строго типизирован: путь и схема на каждый вид,
закрытые `DeviceType` и `TreeNode.kind`. Новый вид — это правка контракта, сервера, интерфейса и тестов, а вид плагина так не
добавить вообще.

Переводим макет на универсальное ядро: сервер отдаёт описания видов (`GET /kinds`) и объекты (`/units`). Интерфейс строит
дерево, мастер, фильтры, подписи и форму по описаниям. У хорошо известных видов остаются ручные экраны, но привязанные к
**профилю** (`vms.camera/1`…), а не к виду. Направление согласовано с altumur, его поправки — в разделе 6.

Результат — рабочий образец: контракт, тестовый сервер, набор, тесты, документы и интерфейс. altumur заберёт его в форк и
доведёт бэкенд w2c; он ждёт нас и параллельно ядро не делает.

## 2. Цели, не-цели, анти-цели

**Цели**
- Все этапы 0–5 из ответа altumur сразу: ядро на чтение и запись, профили, права и правила по описаниям видов, без старых
  CRUD-путей по видам.
- Объект **незнакомого** вида показывается, создаётся, правится, удаляется, получает команды, участвует в правилах и правах
  без кода интерфейса под вид. Проверяется на настоящем виде psim `security_controller` (контроллер и датчик) и на
  синтетическом `test.unknown`.
- Всё, что умеет `index.html` сейчас, умеет и новая страница, на тех же данных и с тем же видом экранов у известных видов.
- **Поиск — не уже, чем в базе, и по всем видам.** Каждое место и каждый способ поиска `index.html` работает так же: строка в
  шапке, фильтр дерева, выбор полей, точный ID, теги, отбор по домену и видам, поиск фразой и ассистент, поиск в списках
  (папка, сеть, права, журнал). Разница одна: искать можно объекты любых видов, в том числе незнакомых, по их полям `x-search`.

**Не-цели**
- Бэкенд w2c и NGP, адаптеры систем.
- Страница плагина в рамке (`setupUi.mode: iframe`) — только описание в контракте и ссылка во вкладке (`mode: tab`).
- Схема на объект (`schemaPerUnit`, сценарий NGP 5) — путь `GET /units/{uid}/schema` есть в контракте и сервере, но в наборе
  такого вида нет, кроме одного примера для теста.
- Изменения базового `index.html`, `api/`, `tests/`.

**Анти-цели** (сделано формально, но провал)
- Ручные экраны пропали или обеднели: у камеры, хранилища, сервера, домена, папки, плана добавления — то же, что в `index.html`.
- Универсальность «на словах»: топология, подписи, родители, обязательность полей остались таблицами в коде сервера или
  интерфейса, а не пришли из `/kinds`.
- Незнакомый вид требует правки интерфейса, чтобы его создать или изменить.
- Базовый `index.html` сломан или изменён.

## 3. Ограничения и решения пользователя

- **Где лежит работа.** `index.html`, `api/`, `tests/` не трогаем: это база для сверки.
  - Новая страница — `index_generic.html` в корне (копия `index.html`, затем переделка). Имя без номера — решение
    пользователя.
  - Контракт, сервер, клиент, набор, документы — `api-generic/` (копия `api/`, затем переделка).
  - Тесты — `tests-generic/` (копия `tests/`, затем переделка).
  - Инструменты `tools/*.py` получают параметр папки (`--api api-generic`, `--tests tests-generic`); без параметра работают
    как сейчас с `api/` и `tests/`. Новых копий инструментов не делаем.
- **Правило CLAUDE.md «контракт правит altumur».** Пользователь разрешил делать контракт и сервер здесь; altumur ждёт и заберёт.
  Старый `api/` при этом не меняется.
- **Коммитов нет**, пока пользователь не скажет. Строку о странице в `protos.html` добавляем без коммита.
- Правила интерфейса из CLAUDE.md действуют на новой странице: без кода в атрибутах (`onEv`), удаление с вводом числа,
  моргание при переходе.

## 4. Варианты

1. **Фасад.** Сервер хранит как сейчас, `/units` — перевод поверх таблиц; интерфейс меняет только переходник. Быстро, но
   топология и проверки остаются в коде по видам, а образец не похож на то, что строит altumur.
2. **Единое хранилище `Unit` и профили — выбран.** Один склад объектов, всё «данное» о виде — из описаний; код остаётся только
   для смысла профилей. Интерфейс берёт каталоги видов из `/kinds`, ручные экраны — по профилю, незнакомое — форма по схеме.
3. **Интерфейс целиком по схемам, без ручных экранов.** Отброшен: пропали бы карточки камеры, хранилища, домена, план
   добавления — то, что делает макет ценным.

Выбран 2: пользователь хочет полный переход и сохранить ручные экраны.

## 5. Что решено

### 5.1. Контракт `api-generic/openapi.json`

Берём наброски приложения Д.1–Д.2 с поправками altumur (раздел 6). Конечное состояние — **после этапа 5**: старых путей
`/domains`, `/servers`, `/devices`, `/folders`, `/archives`, `/volumes`, `/devices/{id}/streams` (CRUD) в нём нет. Этапы 0–5
— порядок нашей работы и порядок, в котором altumur сможет закреплять части у себя; промежуточные состояния отдельно не
сохраняем.

Ядро:
- `GET /kinds` (ETag, `If-None-Match` → 304), `GET /kinds/{kind}`;
- `GET /units` (`kind`, `parentId`, `domainId`, `implements`, `ref`, `folderId`, `q`, `ids`, `cursor`, плюс нынешние отборы
  `/devices`: `noFolder`, `noRecord`, `serverId`, `archiveId`…), `POST /units` (группой, `idempotencyKey`, вложенные дети,
  частичный успех `done/failed` — как `POST /devices`), `GET`, `PATCH` (JSON Merge Patch, `If-Match`), `DELETE /units/{uid}`;
- `POST /units/{uid}/move`, `POST /units/{uid}/actions/{action}` (`instant` → 200 `result`, `longRunning` → 202 с операцией),
  `GET /units/{uid}/creatable`, `GET /units/{uid}/schema`, `POST /units/validate`;
- шаги `/operations`: `set {uid, patch}`, `action {uid, action, params}`, `create`, `delete {uid}`, `folders`;
  `POST /objects/delete` — по `uid`.

Схемы: `UnitKind`, `Unit`, `Text {key, text, lang}`, `ActionDescriptor`, `EventDescriptor`, `Profile`; `Problem.field` —
JSON Pointer в теле, `Problem.errors[]` необязателен; `TreeNode.kind` и `StreamMessage.kind` — открытые строки,
`TreeNode` получает `icon`, `implements`; `StreamMessage.type` += `kinds.changed`.

Предметные API остаются типизированными, адрес — по `uid`, доступность — профилем: `/units/{uid}/live`, `talk`, `timeline`,
`playback`, `holds`, `bookmarks`, `archive-fetch`, `ptz`, `presets/{n}`, `recording-target`. Остаются как есть: `/operations*`,
`/stream*`, `/access*`, `/rules*`, `/rule-prompts*`, `/schedules`, `/day-groups`, `/modes*`, `/maintenance-windows*`,
`/domains/{id}/scenarios*`, `/domains/{id}/discovery`, `/domains/{id}/relays*`, `/settings`, `/licenses`, `/journal`,
`/assist/*`, `/stream-accounts*`, `archive-watches`, `archive-scans`, `/test/*`.
Становятся действиями: `POST /devices/probe`, `POST /archives/check`, `POST /volumes/{id}/format`,
`POST /devices/{id}/operations/{op}`, `/servers/probe`. `/servers/assign` — групповой `move`.
Потоки камеры — дочерние объекты вида `stream`.

Из `Reference` уходят в описания видов: `deviceKinds`, `deviceParams`, `ipServerSubtypes`, `detectorKinds`, `archiveKinds`,
`storageTypes`, `volumeStates`, `unitOptions`. Из `Capabilities` — `deviceTypes`, `foundDeviceTypes`, `unitTypes`,
`writableFields` (замена — `UnitKind.capabilities`, `Unit.capabilities`, `readOnly` в схеме). `DeviceType`, `Device`,
`DeviceCreate`, `DevicePatch`, `DeviceRow`, `UnitOption`, `UnitProperty` и `*Patch` других видов уходят.

**Дерево** остаётся отдельным API: `GET /tree/children` (раскладки `folders`, `servers`, `archives`, `detectors`, страницы) и
`GET /tree/paths` — как сейчас; `TreeNode.kind` — открытая строка (вид объекта), у узла `icon`, `implements`, вместо `row` —
краткий `Unit`. События `tree.changed` — как сейчас. *Моё решение: дерево уже универсально (приложение А.3), а раскладки и
страницы на 250 000 камер клиент из `/units` не соберёт.*

**Поиск — по всем видам.**
- `GET /units?q=` ищет по объектам любых видов: имя, короткое имя, `uid` и свойства, помеченные в схеме вида `x-search: true`
  (у камеры — адрес, производитель, модель, номер; у `security_controller` — `ip_address`; у незнакомого вида — что объявил вид).
  Параметр `fields=` сужает поиск до перечисленных свойств; отборы — `kind`, `implements`, `status` (связь), `domainId`,
  `noFolder`, `noRecord`, `noDetector`. В ответе у объекта — `match {field}`: в каком поле нашлось.
- Строка поиска в шапке, фильтр дерева по полям (`SEARCH_FIELDS`) и чипы видов (`TYPE_FILTERS`) строятся из `/kinds`: поля
  поиска — объединение `x-search` всех видов с подписями из схем; чипы — виды и профили.
- **Ассистент и поиск фразой** (`/assist/turns`): мир `AssistWorld` — `kinds` + `units` вместо `devices`, `servers`,
  `folders`; найденное `AssistFoundFilter` — `{q, kinds, implements, status, domainId, fields, noFolder, noRecord, noDetector}`;
  шаг плана `AssistPlanItem` — `{uid, version, patch, name, changes[] {field: JSON Pointer, before, after, why}}`. Значит,
  ассистент может предлагать правки и объектам незнакомых видов — в пределах их схемы. Заглушка ассистента в сервере и служба
  ассистента демо-страницы переводятся так же.

**Права.** Уровни не беднеют. `UnitKind.access {class, levels[]}`: класс доступа объединяет виды с общим набором уровней —
нынешние категории роли (`cam` с FORBID…FULL, `tel`, `acfa`…) становятся классами, их виды объявляют класс. Вид без класса
получает общий набор `view < edit < admin` и класс, равный своему коду. `Role.kindAccess {класс: уровень}` заменяет поля
категорий и умолчания `dCam`, `dSens`…; `folderAccess` и `objectAccess` остаются картами, ключ — `uid`, значение — уровень
класса объекта. Право на действие — `ActionDescriptor.right` (уровень класса). Логика `RoleGlobal` (`bm`, `alert`,
`DEVICES_SETUP`) — как сейчас. *Моё решение: сохраняет экран прав и правила видимости архива.*

**Правила — полный перевод.** Все события и действия объектов — из `events`/`actions` описаний видов, в том числе у камер,
детекторов, датчиков, реле, СКУД. Триггер `{source: "unit", kinds[] | implements[], event, match}` (вид события — `event`,
а не `kind`), действие `{type: "unitAction", action, params}` с целью по `uid`; цели `target.include[]` — `{uid}` или область
`{area: folder | server | domain, uid}`. Из `Reference` уходят `ruleTriggers`/`ruleActions`/`eventKinds` по устройствам и
`deviceTypes` в движке; остаются триггеры и действия не про объекты (расписание, режимы, сценарии, вопросы оператору).
Движок правил, правила набора, `fixture_fires.js` переводятся. *Моё решение: «сразу всё»; вариант «старые рядом с новыми»
оставил бы две модели событий.*

### 5.2. Виды и профили в наборе

- **Вид = нынешний вид записи**, по одному на каждое значение `DeviceType` (17), плюс `domain`, `server`, `folder`, `volume`,
  `stream`. Хранилища — **вид на каждый вид хранилища** из `reference.archiveKinds` (`archive.disk`, `archive.nas`…): у них
  разные схемы адреса и режимы. Подвиды `ipsrv` — как сейчас, свойством. *Моё решение; совпадает с выбором altumur «каждый
  `type` — свой вид».*
- **Профили** (публикует контракт, список в `api-generic/README.md`): `vms.domain/1`, `vms.server/1`, `vms.folder/1`,
  `vms.camera/1`, `vms.archive/1`, `vms.volume/1`, `vms.stream/1`, `vms.detector/1`, `vms.acs/1` (единицы СКУД с командами),
  плюс возможности предметных API `vms.live/1`, `vms.ptz/1`, `vms.talk/1`, `vms.timeline/1`. Точный состав свойств профиля —
  за исполнителем, по полям, которые читают ручные экраны.
- **Незнакомые виды:** `security_controller/CONTROLLER` и `security_controller/SENSOR` — переводом настоящего
  `psim-sdk/psim_plugins/cmd/security_controller/manifest/plugin.json` и `langs/` (ссылки на камеры `source: platform_objects`
  → `x-ref {implements: [vms.camera/1]}`, команды → `actions`, события → `events`, `setup_ui` → `setupUi {mode: tab}`);
  `test.unknown` — синтетический вид со всеми видами полей и виджетов `x-ui-*` для приёмки. Объектов этих видов в наборе —
  несколько, в одном домене.
- **Набор** `api-generic/fixtures/demo.json`: разделы `kinds` и `units` вместо `domains`, `servers`, `devices`, `folders`,
  `archives`, `volumes`; остальные разделы — как есть, ссылки в них по `uid`. `uid` = нынешний `id` (UUID с цифрой вида не
  меняем). Перевод — скриптом `tools/generic_fixture.py` из `api/fixtures/demo.json`, потом набор правится как обычно.
  `one-domain.json` и `large.json` собирает `tools/profile_fixture.py --api api-generic` (отбор по видам и возможностям
  вместо `deviceTypes`).

### 5.3. Сервер `api-generic/server.js`

- Один склад `Unit` с индексами по `uid`, `parentId`, `kind`, `domainId`, ссылкам (`x-ref`) и папкам — `large` (250 000
  камер) должен проходить `check_scale.py`.
- Из описаний видов, а не из кода: родители и `creatable`, проверка тела по JSON Schema вида (с указателем на поле),
  `readOnly`/`writeOnly`, `x-immutable`, ссылки `x-ref`, подписи, действия и события, права уровня вида.
- Кодом, по профилю (хуки «перед записью / после / при удалении / кто исполнитель»): запись камеры и хранилища, каскады
  удаления, детекторы и конфликт шаблонов, потоки и основной поток, PTZ и аренда, живое видео, тома и форматирование,
  NAT-камеры, СКУД и реле двери, сервер-исполнитель шага, нумерация устройств. Поведение и коды ошибок — как в `api/server.js`.
- Действия незнакомых видов исполняются сервером одинаково: `instant` — ответ сразу (для `security_controller` — смена
  `status.observed.armed` и событие), `longRunning` — операция.
- `PATCH` на путях ядра отвечает сразу; «ещё не применилось» — `status.observedVersion` ≠ `version` и условие `Applied`
  (предложение altumur).
- Поток: `entity.*` с `kind` = вид объекта; `kinds.changed` — через `POST /test/kinds` (служебная операция стенда: добавить
  или поменять описание вида на ходу, сценарий 2).

### 5.4. Интерфейс `index_generic.html`

- **Шов** — вход и выход кэша (отчёт разведки, раздел 6): `unitNode(u, kind)` вместо `devNode/srvNode/archNode/volNode/
  folderNode`, `nodeToUnit` вместо `nodeCreate/keyToApi/fldToApi`, `RENAME_API` → `PATCH /units/{uid}`; загрузка
  (`hwRead`, `treeRead`, `hwEnsure`, `hwFull`, `hwReload`, события `HW_EVENT`) — на `/units`. Внутренние узлы `{type,…}`
  остаются: `type` узла = имя ручного экрана, выбирается по профилю вида; у незнакомого вида `type` = код вида.
- **Из `/kinds` при старте:** `LB` (подписи), `TYPE_FILTERS`, `WIZ` и `canAdd`, `needsParent/parentOpts` (по `parents` и
  `creatable`), иконки, `DEV_WITH_KIDS`, `CAPS.found/units/writable`, `*_PATCH` (сейчас читаются из схем контракта на
  старте), `CARD_PROP/CARD_FLD_PROP` для незнакомых полей.
- **Форма по схеме** для вида без ручного экрана: карточка (`tabsFor` → вкладки из `x-ui-tab`, `formBase` → поля по схеме с
  группами, порядком, единицами, виджетами), мастер добавления (`POST /units`), кнопки действий с параметрами по схеме,
  «Страница плагина» по `setupUi`. Правка идёт через тот же черновик карточки и «Показать план» → `/operations`.
- **Свойства сверх профиля** у известного вида — вкладка «Дополнительно» формой по схеме.
- Права (роль: уровни по видам из `/kinds`) и правила (события и действия из описаний видов) — в нынешних экранах прав и
  автоматизации.
- Подписи: сначала ключ в словаре интерфейса, затем `text` с сервера (раздел 6).

### 5.5. Тесты и проверки

- `tests-generic/api-*.js`: каждый нынешний тест переписан на ядро и проходит; плюс `api-units.js` — ядро на незнакомых
  видах (описания, создание, правка с ошибкой по указателю, действия, события, `kinds.changed`, `creatable`, `validate`,
  удаление, групповая операция по разным видам). `harness.js`: `needs` вида `kind:<вид>` и `implements:<профиль>` вместо
  `type:<вид>`.
- `tests-generic/ui-*.js`: каждый нынешний сценарий проходит на новой странице; плюс `ui-unknown.js` — незнакомый вид
  целиком через интерфейс (дерево, карточка, мастер, команда, удаление с вводом числа, правило, права).
- Инструменты: `check_api.py` (набор по `kinds/units`, описания видов — по мета-схеме, примеры проходят схему, ссылки
  разрешаются), `check_ui.py`, `run_api_tests.py`, `check_scale.py`, `check_webui.py`, `build_api.py` — с параметрами папок.
- **Сверка с базой:** `compare_screens.py` в режиме «две страницы» — `index.html` на `api/` и `index_generic.html`
  на `api-generic/`, те же экраны; для известных видов разницы нет.

## 6. Поправки altumur, которые входят в решение

- Подпись — `{key, text, lang}`; интерфейс сначала ищет `key` в своём словаре. `labelCount` — необязательный.
- `field` на путях ядра — всегда JSON Pointer; `errors[]` необязателен, минимум одна ошибка.
- `kinds.changed` — подсказка; после `stream.reset` клиент перечитывает `/kinds` с `If-None-Match`. ETag `/kinds` — хэш описаний.
- Описание поля: `x-bound-to` (смена поля сбрасывает секрет), `x-rights {scope: group | cluster}`, `readOnly` у полей,
  которые заполняет сервер, `x-inherit {merge}`; `Unit.inherited[имя].from` — `unit | domain | default`.
- `accessLevels` вида необязателен, у системы общий набор (`view`, `edit`, `admin`); `kindAccess` — объявляемая возможность.
- Действия: контракт знает `instant` и `longRunning`; система может объявить только `longRunning` (как w2c).
- `move` и `validate` — объявляемые возможности (`capabilities.operations`).
- `setupUi {url, kinds, mode}`: `mode: tab` сейчас, `iframe` — потом; параметры страницы `?type=&id=&lang=`.
- `version` — непрозрачная строка; у сборных объектов — склейка версий частей (у нас — как сейчас у камеры-кластера).
- Строки таблиц w2c — виды `<sub>/<таблица>` с хозяином; документ (`shape: document`) — только для общих настроек домена.
  В наборе — по одному примеру каждого, для тестов.

## 7. Как работаем

1. Копии: `index.html` → `index_generic.html`, `api/` → `api-generic/`, `tests/` → `tests-generic/`; страница
   подключает `api-generic/*.js`; все проверки проходят на копии до правок — это точка отсчёта.
2. Контракт ядра (этапы 0–1) пишет ведущий, сам.
3. Дальше параллельно агенты, каждый на своём: набор и сервер; тесты API; интерфейс. Этапы 1 → 2 → 3 → 4 → 5; к следующему —
   когда все проверки на текущем проходят.
4. **Догнать базу** (решение пользователя): перед сдачей одним проходом перенести в `index_generic.html`,
   `api-generic/` и `tests-generic/` всё, что пришло в `index.html`, `api/`, `tests/` после `0c8f18e`
   (`git diff 0c8f18e HEAD -- index.html api tests`), в терминах ядра. Сверка экранов — с базой на момент сдачи.
5. В конце: проверки из раздела 5.5, сверка экранов, документы, строка в `protos.html`. Коммит — по слову пользователя.
