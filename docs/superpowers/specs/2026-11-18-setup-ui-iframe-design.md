# Своя страница настроек подсистемы в consolem — описание решения

2026-11-18 · автор — владелец контракта (joynickray) · статус: на обсуждении

Основа: предложение [«Отделить общий контракт конфигуратора от описаний подсистем»](../../2026-11-16-kontrakt-i-podsistemy-predlozhenie.md),
запрос w2c [«Плагины psim на 0.2.0»](../../../api/requests/2026-11-05-110504Z-w2c-psim-plugins-request.md) и
[ответ](../../../api/requests/2026-11-05-110504Z-w2c-psim-plugins-response.md) (контракт 0.16.0). Состояние: контракт 0.23.0,
consolem `b18aeed`, psim-sdk `3a35850`, w2c `altumur/server-vms-course` `7b0dcef73`.

**Что заменяет.** Это решение меняет п. 11 нашего запроса [«Универсальная модель»](../../../api/requests/2026-11-03-065231Z-mockup-generic-model-request.md)
(2026-11-03) и этап 2 w2c ADR-0115 §4.3, который на этом пункте основан. Раньше было так: по умолчанию форма по схеме, страница
плагина открывается переключателем, страница сама пишет настройки своим сервером, сообщений четыре (`ready`, `height`, `dirty`,
`saved`), `sandbox` без `allow-same-origin`. Что меняется — раздел 10, таблица для w2c.

## 1. Зачем

Конфигуратор consolem общий: он не знает, что такое камера, касса или датчик. Подсистема описывает свои поля сама (`GET /kinds`),
и consolem строит по ним форму. Но форма по схеме удобна не всегда. У сложных объектов нужен продуманный экран: что важно, в каком
порядке, что рисуется на кадре. Сейчас такие экраны пишет только mockup, руками в `index.html`, под профиль (`vms.camera/1`…).

Нужно, чтобы свой экран могла поставить сама подсистема:

- автор плагина psim (psim-sdk) пишет плагин и к нему страницу настроек;
- подсистема w2c (`cam`, `rec`, `det`…) или NGP тоже может поставить свою страницу;
- страницу отдаёт веб-сервер плагина или подсистемы, на чём бы он ни был написан;
- consolem показывает эту страницу внутри карточки объекта, а кнопки «Применить» и «Отменить» остаются в consolem.

Так конфигуратор остаётся общим, а свой экран у объекта появляется без правки consolem. Это прямо продолжает предложение о слоях:
описание подсистемы и её экран принадлежат подсистеме, а consolem даёт только механизм.

## 2. Цели, не-цели, анти-цели

**Цели**

- Любая подсистема (плагин psim, подсистема w2c, NGP) может поставить свою страницу настроек вида. consolem показывает её внутри
  карточки, в iframe.
- Правка настроек объекта всегда проходит через «Применить» в consolem, с журналом, откатом, правами и `If-Match`, как у любого
  объекта.
- Страница может быть сложной, уровня нашей карточки камеры или домена: читать объекты, запускать поиск в сети и команды вида,
  переходить к другим объектам, просить подтверждение.
- Если своей страницы нет, consolem показывает ручной экран по профилю, а если нет и его, форму по схеме из `/kinds`.
- На время прототипа можно переключиться между своим экраном и общими настройками и увидеть, какие поля свой экран не показывает.

**Не-цели**

- consolem не знает, какой путь проходит страница от плагина до браузера: прокси, другая машина, дверь w2c. Он знает только адрес.
- consolem не разбирает манифесты: ни `plugin.json` psim, ни `*.subsystem.yaml` w2c. Он видит только `/kinds`. Перевод манифеста в
  описание вида делает бэкенд.
- Видео, архив и выгрузка этим решением не переносятся. Для них — отдельный API (п. 7 предложения о слоях).
- Единый вид чужих страниц с consolem не гарантируется. Мы даём тему, токены оформления и образец, а автор страницы решает сам.

**Анти-цели** (если так вышло, решение провалено, даже если всё работает)

- Страница получила токен или куки consolem, или обратилась к `/api/*` consolem сама.
- Страница изменила настройки объекта мимо «Применить»: журнал consolem этого не видит, а черновик расходится с системой.
- В consolem появился код под конкретный плагин или подсистему.
- У psim и у w2c получились разные протоколы встраивания.
- Человек без права видит через страницу то, что consolem ему не показал бы.

## 3. Как сейчас

**consolem.**

- В контракте есть `UnitKind.setupUi {url?, kinds?, mode: tab | iframe}`. Про `iframe` сказано «потом» (`api/openapi.json`,
  схема `UnitKind`). Есть путь `POST /units/{uid}/setup-ui` → `SetupUiLink {url, expiresAt}`: адрес на одно открытие с разовым
  ключом. Отметка `setupUi` в `Unit.capabilities` ставится, когда у человека есть право `edit`. Страница живёт на другом
  происхождении, куки и токен консоли не получает, к `/api/*` консоли не обращается.
- `index.html` показывает кнопку «Страница плагина», и та открывает страницу в новой вкладке (`schemaPluginLink`,
  `schemaPluginOpen`).
- Из прототипа 77 в `index.html` уже есть «Все параметры» в меню «Ещё»: форма по схеме у объекта с ручным экраном, общий черновик
  двух форм, отметка «сверх профиля» (`hasBaseForm`, `formAllSet`, `kindExtraProps`). Выбор формы consolem помнит у вида.
- Форма по схеме уже умеет вкладки и блоки: `x-ui-tab`, `x-ui-group`, `x-ui-order` (`api/README.md`, раздел о `schema`).

**psim-sdk.**

- В манифесте `plugin.json` плагин объявляет ресурс `PROXY` с `role: "setup_ui"` и `object_types`. Страницу отдаёт встроенный
  веб-сервер плагина через прокси платформы.
- Эмулятор платформы (`psim_platform_emulator/webui/webui.html:628–705`) встраивает страницу в карточку Details через iframe:
  `publicUrl?type=&id=&lang=`. По умолчанию там общая таблица параметров, страница включается галочкой «Use plugin setup UI».
  При смене языка эмулятор перезагружает iframe (ADR-006).
- Протокола сообщений между карточкой платформы и страницей (`postMessage`) нет. А прямой обмен страницы со своим плагином по
  HTTP есть: плагин публикует произвольные ресурсы `PROXY` (`/ui`, `/api`, `/setup`), его веб-сервер отвечает на свои пути
  (`railway_detector`: `/values`, `/cameras`, `/frame`, `/state`, `/send-command`) и шлёт изменения по WebSocket (`/ws`).
- У `railway_detector` на странице своя кнопка Apply: `POST ./values` самому плагину. Это тестовый вариант, в продакшне его не
  будет.
- Плагин запросы не проверяет, он только отсекает чужие страницы по `Origin` (`railway_detector/webui/guard.go`).
- ADR-005 (предложено) добавляет `Platform.UpdateObject`: правка объекта через платформу.

**w2c.**

- Своя страница есть у любой подсистемы: ключ манифеста `setup_ui: [{route, tables, mode}]` (P/02.1 N1.2, строка 167). Страницу
  отдаёт дверь подсистемы по маршруту `door.routes`. `mode` — только `tab`. Маршрут — с рангом `edit` или `admin`, потому что
  «страница пишет настройки сервером подсистемы».
- Токен страницы — в `?t=` первого адреса. Дверь ставит свою куку (`HttpOnly`, `SameSite=Strict`, путь маршрута) и перенаправляет
  на адрес без `t` (ADR-0115, доп. 2, п. 8). Перед пересылкой плагину дверь снимает `Cookie` и `Authorization` запроса (доп. 16).
- Описание вида плагина psim и новых таблиц бэкенд строит прямо из манифеста (V/11.14 N1.5). У видов VMS (камера, хранилище…)
  бэкенд берёт копию нашего `kinds.json` и `mapping.tsv`. Убрать эту копию предлагает документ о слоях.
- В манифесте w2c есть `display.form`: блоки формы с заголовками и пояснениями.

## 3а. Подходы

Рассмотрены три способа дать странице сложную логику.

| | Подход | Что даёт | Чем плох |
|---|---|---|---|
| 1 | **Узкий мост.** consolem даёт странице только начальные данные и принимает правку. Всё остальное страница берёт у своего сервера | быстро, протокол маленький | чужие объекты страница читает правами плагина, а не человека (так сейчас у `railway_detector`: `./cameras`); команды идут мимо журнала и прав. Экран уровня камеры или домена честно не построить |
| 2 | **Мост к механизму consolem** (выбран). Страница просит consolem выполнить операцию контракта, consolem выполняет её с правами человека и возвращает ответ | сложный экран возможен; права, журнал и откат одни для всех | протокол больше; нужна разметка операций в контракте |
| 3 | **Дать странице токен consolem** | страница делает что хочет | отброшен: запрещают контракт и w2c ADR-0115 доп. 1 Б1 |

Запуск по шагам: **шаг 1** — начальные данные, правка, проверка, высота, «Применить» в consolem; **шаг 2** — вызовы операций,
подписка на события, переход, подтверждение. Страницы шага 1 на шаге 2 не ломаются.

Где описан протокол. Рассматривали psim-sdk: на него опирается w2c, и автор плагина читает его документацию. Выбран **контракт
consolem**: страницы ставят не только плагины psim, но и подсистемы w2c и NGP, а встраивает их всегда consolem. psim-sdk даёт
по этому описанию библиотеку для авторов и сторону consolem в эмуляторе.

Какой экран главнее. Рассматривали ручной экран consolem выше страницы подсистемы. Выбрано наоборот: подсистема точнее знает свою
систему.

## 4. Какой экран видит человек

Правило из трёх ступеней, по виду объекта:

1. **У вида есть своя страница** (`setupUi`, `mode: iframe`, вид в `setupUi.kinds`) — показывается она. Ручной экран consolem
   при этом не показывается совсем.
2. **Страницы нет, есть ручной экран consolem по профилю** — показывается ручной экран.
3. **Нет ни того, ни другого** — форма по схеме из `/kinds`, с вкладками и блоками по `x-ui-tab`, `x-ui-group`, `x-ui-order`.

**Что заменяет страница.** Страница заменяет вкладки вида — те, что у ручного экрана рисуются под вид (у камеры «Подключение»,
«Видео», «Архив», «Детекторы», «Периферия»; у домена «Папки», «Устройства», «Серверы», «Лицензии», «Топология»). Свои вкладки
страница рисует внутри себя. За consolem остаётся общее для любого объекта:

- шапка карточки: имя, путь, состояние, меню «Ещё» (переименовать, перенести, удалить, папки, «Все параметры»);
- вкладки, которые есть у любого объекта: «Доступ» (права на объект) и другие вкладки механизма;
- кнопки «Применить» и «Отменить» под страницей.

Так права, переименование и удаление работают у всех объектов одинаково, а шаг 1 запускается без шага 2. Решено с владельцем
(вариант А против «страница заменяет всю карточку»). Какие вкладки ручного экрана относятся к виду, а какие к механизму, строитель
определяет по `tabsForHand`; спорные называет в плане.

Дополнительно:

- **«Все параметры»** — пункт меню «Ещё» у любого объекта со своим экраном (ступень 1 или 2). Он открывает форму по схеме со всеми
  полями вида. Так уже работает для ручного экрана (прототип 77). Черновик у страницы и у формы общий.
- **Страница не загрузилась.** Дверь не ответила, адрес не выдан или страница не прислала `ready` за 10 секунд. Тогда consolem
  пишет, что страница недоступна, с причиной, и показывает форму по схеме. Объект остаётся настраиваемым, пока плагин не работает.
- **Только право просмотра.** Страница `mode: iframe` ничего не пишет, поэтому её адрес выдаётся и по праву `view`. consolem
  передаёт странице `readOnly: true` и не показывает «Применить». Тот, кто только смотрит, видит ту же страницу, а не другой экран.
  Страница `mode: tab` по-прежнему пишет сама (этап 1 w2c), поэтому у неё остаётся право `edit`. Решение автора документа.
- **`mode: tab`** остаётся: такую страницу consolem открывает ссылкой в новой вкладке, как сейчас, а в карточке — ступень 2 или 3.

## 5. Откуда страница и как она встраивается

**Откуда.** Страницу объявляет манифест подсистемы: `plugin.json` psim (`role: setup_ui`) или `*.subsystem.yaml` w2c (`setup_ui`).
Бэкенд превращает это в `UnitKind.setupUi`. consolem не знает, через какие прокси и с какой машины страница придёт. Ему нужны
только две вещи: описание вида с `setupUi` и адрес, по которому страница доходит до браузера.

**Адрес.** Постоянный `setupUi.url` (consolem дописывает `?type=&id=&lang=`) или адрес на одно открытие из
`POST /units/{uid}/setup-ui`. Разовый ключ нужен только для первой загрузки. Перезагрузка iframe (смена языка, повтор после
ошибки) берёт новый адрес.

**Происхождение страницы.** consolem принимает сообщения только от `iframe.contentWindow` и только с ожидаемого происхождения, и
отвечает только на него (никогда не `"*"`). Ожидаемое происхождение — это происхождение выданного адреса. Если прокси перенаправляют
на другое происхождение, бэкенд называет итоговое явно: новое необязательное поле `origin` у `setupUi` и у `SetupUiLink`.

**Рамка.** `<iframe sandbox="allow-scripts allow-forms allow-same-origin">`.

- `allow-same-origin` нужен. Без него у страницы непрозрачное происхождение, и её `fetch` к своей двери с кукой не работает. w2c
  отметил это сам (ADR-0115, доп. 2, п. 8). Для страницы с другого происхождения это безопасно: доступа к consolem она не получает.
- Без `allow-top-navigation` и `allow-popups`: страница не уводит consolem со страницы и не открывает окна. Переход к объекту — через
  сообщение (шаг 2).

**Что нужно со стороны системы** (не consolem):

- дверь отдаёт страницу с `Content-Security-Policy: frame-ancestors <происхождение consolem>`, чтобы чужой сайт её не встроил;
- CSP оболочки consolem получает `frame-src` на происхождения дверей;
- кука двери внутри iframe приходит, только если дверь на том же сайте, что consolem (тот же хост, порт может быть другим). Если
  дверь на другом домене, нужен `SameSite=None; Secure; Partitioned` или другой способ входа. Это проверяет система.

**Страница обращается только к своему происхождению**, относительными адресами. Так цепочка прокси за адресом её не ломает. Страница
проверяет, что сообщения пришли от `window.parent` и с происхождения consolem. Его страница берёт из `location.ancestorOrigins` или
из `document.referrer`. Встроить её чужому сайту не даёт `frame-ancestors`.

## 6. Протокол, шаг 1: правка и «Применить»

Каждое сообщение — объект `{proto: "setup/1", type, …}`. Незнакомый `type` обе стороны пропускают. Ниже — смысл сообщений. Точные
имена полей и JSON Schema сообщений — работа строителя (раздел 11).

**consolem → страница**

| `type` | Когда | Что внутри |
|---|---|---|
| `init` | после `ready` | `uid`, `kind`, `lang`, `theme` (`dark` / `light` и токены оформления), `readOnly`, `unit` (как `GET /units/{uid}`: `properties`, `status`, `version`), `draft` (правка, если она уже есть: человек правил в «Все параметры»), `host` (что умеет consolem: версия протокола, операции шага 2) |
| `draft` | черновик изменили вне страницы, например в «Все параметры» | правка целиком |
| `applied` | «Применить» прошло | новый `unit`; черновик пуст |
| `errors` | сервер отверг правку | `Problem` как есть: `errors[]` с `field` (JSON Pointer) и текстом |
| `revert` | человек нажал «Отменить» | `unit`; черновик пуст |
| `theme` | сменилась тема | как в `init` |

Смена языка перезагружает iframe с новым `lang`, как в эмуляторе psim (ADR-006).

**страница → consolem**

| `type` | Когда | Что внутри |
|---|---|---|
| `ready` | страница загрузилась | `proto`; необязательно `fields` — список JSON Pointer полей, которые страница показывает (для строки покрытия, раздел 8, и для «Все параметры») |
| `change` | каждая правка на странице | правка целиком, JSON Merge Patch к `properties` (`null` — снять значение). Пустая правка — изменений нет |
| `invalid` | страница сама нашла ошибку ввода | `fields[]` и текст; пока список не пуст, «Применить» неактивна. Пустой список снимает запрет |
| `height` | меняется высота содержимого | высота в пикселях; consolem задаёт высоту рамки |

**Как идёт «Применить»**

1. «Применить» активна, когда черновик не пуст и страница не сообщила `invalid`.
2. consolem пишет правку обычным путём: `PATCH /units/{uid}` с `If-Match`, на шаге 2 — операцией по нескольким объектам. Журнал,
   тост с отсчётом и «Отменить», конфликт версий — как у любой правки в consolem.
3. Успех — `applied` странице. `422` — `errors` странице: страница подсвечивает свои поля, а поля, которых на странице нет, consolem
   показывает списком под рамкой со ссылкой «Все параметры». `412` — стандартный конфликт версий consolem.
4. Уход с карточки с непустым черновиком — стандартное предупреждение consolem о несохранённых изменениях.
5. Пока черновик не пуст, consolem может проверять его на ходу (`POST /units/validate`) и присылать `errors`. Нужно ли это на шаге 1
   — решает строитель по скорости.

**Чего страница не делает.** Не пишет настройки объекта ни через consolem, ни через свой сервер. Всё, что меняет `properties`,
идёт через `change` и «Применить».

## 7. Протокол, шаг 2: страница просит consolem

На шаге 2 страница может сделать экран уровня нашей карточки камеры или домена: найденное в сети (`GET /domains/{id}/discovery`),
лицензии, дерево, объекты по ссылкам, команды вида, переходы.

**Вызов операции.** Страница шлёт `call {id, op, params, body}`, где `op` — `operationId` контракта (`getDiscovery`,
`listLicenses`, `listUnits`, `runUnitAction`…). consolem выполняет запрос сам, со своим токеном и правами человека, и отвечает
`result {id, ok, status, body | problem}`. Отдельное сообщение под каждую функцию не нужно: всё, что есть в контракте и разрешено
мосту, страница вызывает одинаково.

**Что мост разрешает — разметка в контракте.** У каждой операции `api/openapi.json` новое расширение `x-bridge`:

| Значение | Что делает consolem | Примеры |
|---|---|---|
| `read` | выполняет сразу | `listUnits`, `getUnit`, `getDiscovery`, `listLicenses`, `getTreeChildren`, `getCreatable` |
| `act` | выполняет сразу; команда видна в журнале, как из карточки | `runUnitAction`, `startDiscovery`, `stopDiscovery` |
| `draft` | не выполняет, а кладёт в черновик; выполнит по «Применить» | `patchUnit`, `createUnits`, `deleteUnit`, `moveUnit`, `deleteObjects` |
| нет поля | отказ `NOT_SUPPORTED` | `/test/*`, `/access/apply`, `/assist/*` и всё, что не размечено |

Удаление (`deleteUnit`, `deleteObjects`) в черновике consolem подтверждает своим стандартным диалогом с вводом числа. Страница
обойти его не может. Черновик из нескольких объектов «Применить» выполняет одной операцией (`POST /operations`), с откатом.

**Функции платформы, которых нет в контракте.** Сначала их добавляют в контракт, это правка механизма. Есть путь проще: подсистема
объявляет функцию командой вида в своём манифесте (`ActionDescriptor`), и страница вызывает её общим `runUnitAction`. Контракт
consolem тогда не меняется, это слой подсистемы.

**Другие сообщения шага 2**

| `type` | Направление | Что делает |
|---|---|---|
| `subscribe` | страница → consolem | события `/stream` по названным объектам или видам consolem пересылает странице (`event`). Нужно для долгих работ: поиск в сети, операции |
| `navigate` | страница → consolem | перейти к объекту (`uid`, `tab`). consolem переходит со вспышкой по своему правилу. Если в черновике есть изменения, consolem сначала предупреждает |
| `confirm` | страница → consolem | показать стандартное подтверждение consolem (текст, что пропадёт, число для ввода); ответ — `result` |

Что страница может вызывать, она узнаёт из `init.host`. Чего там нет, она не вызывает, а показывает по-своему или прячет.

## 8. Свои команды страницы — напрямую к своему серверу

Своя логика плагина, которую платформа не знает (проверить связь, откалибровать, свой график, запустить автодетектор внутри
плагина), идёт от страницы прямо к её серверу, через ту же дверь и те же прокси. consolem в этом не участвует и о таких путях не
знает. Так уже работает в psim-sdk: плагин сам решает, какие пути HTTP выставить, а о ходе своей работы сообщает той странице,
которая её запустила, например по WebSocket (`railway_detector`: `/ws`). Это решение не отнимает этот путь, а только задаёт его
границу.

| Что | Путь |
|---|---|
| Правка настроек объекта | черновик → «Применить» в consolem → бэкенд → плагин |
| Функция платформы: список, поиск, команда вида, лицензии | страница → consolem (`call`) → бэкенд, права человека |
| Своя логика плагина | страница → свой сервер напрямую |

Две границы:

- **Своя команда не меняет настройки объекта сама.** Если её итог — новые значения (калибровка подобрала порог), сервер возвращает их
  странице, страница кладёт их в черновик (`change`), человек нажимает «Применить».
- **Права на свои команды проверяет дверь.** Адрес страницы выдаётся по настоящему праву человека (`view`, `edit`, `admin`). Дверь
  w2c уже проверяет ранг на каждом маршруте (`door.routes: [{name, rank}]`). Человек с `view` откроет страницу, но команду с
  маршрутом `rank: edit` дверь отвергнет.

## 9. Режим сравнения (только прототип)

Зачем: увидеть глазами и проверить, что свой экран показывает все нужные поля. Например, в схеме камеры 50 полей, а на своём экране 48.

```text
┌ Камера «Вход 1» ───────────────────── Свой ◉━○ Общие ── Ещё ▾ ┐
│  Свой экран: 48 полей из 50 · не показаны: noiseReduction, wdr ▸ │
│ ┌──────────────────────────────────────────────────────────────┐ │
│ │  страница подсистемы (iframe) или ручной экран consolem      │ │
│ └──────────────────────────────────────────────────────────────┘ │
│                                       [ Отменить ]  [ Применить ] │
└───────────────────────────────────────────────────────────────────┘
```

- **Переключатель «Свой / Общие»** в шапке карточки, справа, рядом с «Ещё». Он виден только у объектов со своим экраном (ступень 1
  или 2). «Общие» — форма по схеме.
- **Один на все объекты.** Выбрал «Общие» — все карточки открываются в общих настройках, пока не переключишь обратно. Выбор consolem
  помнит и после перезагрузки (`localStorage`). Выбор формы у вида из прототипа 77 (`formAllByKind`) переключатель перекрывает,
  пока он включён.
- **Строка покрытия** видна в обоих положениях. Сколько полей схемы вида на своём экране, каких нет — списком, раскрывается по ▸.
  Обратная проверка: поля, которые свой экран называет, а в схеме вида их нет, — это ошибка описания, строка показывает их отдельно.
- **Откуда список полей своего экрана.** У ручного экрана — по профилям вида: объединение `Profile.properties` всех `implements`
  (то же, что считает `kindExtraProps`; профиль включает все поля особого экрана, п. 6 предложения о слоях). У страницы — из
  `ready.fields`. Не прислала — строка пишет «Страница не сообщила свои поля».
- **Черновик.** У страницы подсистемы черновик с формой по схеме один: оба работают с `properties`, consolem шлёт странице `draft`,
  переключение правку не теряет. У ручного экрана consolem черновика два (модель экрана `cardDiff` и `n.xprops` формы по схеме), и
  сводить их в один — переделка каждого ручного экрана. Поэтому у ручного экрана переключатель ведёт себя как «Все параметры»
  сейчас: пока есть неприменённая правка, переключиться нельзя, и consolem называет причину (`FORM_BACK_WHY`). Сравнению это не
  мешает: смотрят, а не правят в двух формах сразу. Решение автора документа.

Нужен ли переключатель в основном макете, решают при переносе.

## 10. Что меняется и где

**Контракт consolem** (механизм, делает владелец; младшая версия после 0.23.0):

- `setupUi.mode: iframe` получает смысл из разделов 4–6, слово «потом» уходит;
- новое `setupUi.protocol` — версия протокола страницы (`setup/1`); без поля у `mode: iframe` — `setup/1`;
- новое необязательное `origin` у `setupUi` и у `SetupUiLink` (раздел 5);
- отметка `setupUi` в `Unit.capabilities` и `POST /units/{uid}/setup-ui` у вида с `mode: iframe` — по праву `view`; у `mode: tab`
  — по-прежнему `edit` (раздел 4). Поведение существующих видов с `tab` не меняется;
- описание протокола — отдельный файл `api/SETUP-UI.md` и JSON Schema сообщений рядом (`api/setup-ui.schema.json`); ссылка из
  описания `setupUi`;
- шаг 2: расширение `x-bridge` у операций (раздел 7) и проверка в `tools/check_api.py`: у каждой операции либо `x-bridge`, либо её
  нет в списке исключений;
- `api/fixtures/demo.json`: страница `mode: iframe` — у нового вида или объекта, существующие `CONTROLLER` и `SENSOR` с `mode: tab`
  не трогаем. Тогда `index.html` до переноса ведёт себя как сейчас: незнакомый ему `mode: iframe` он не показывает ссылкой, объект
  открывается формой по схеме, а его тесты (`tests/ui-unknown.js`, `tests/api-units.js`) не меняются. Какой вид взять — решает
  строитель, лишь бы проверки `index.html` проходили без правки самого `index.html`. Решение автора документа;
- стенд: тестовая страница плагина в репозитории (например, `api/plugins/security_controller/setup/index.html`), которую
  встроенный сервер выдаёт в `SetupUiLink.url`. На Pages она на том же происхождении. Чтобы стенд проверял границу, рамка тестовой
  страницы — `sandbox` без `allow-same-origin`, а страница работает без `fetch` к своему серверу (данные — из `init`). Так она
  не достаёт до consolem, как настоящая страница с другого происхождения. У такой рамки происхождение `"null"`, и ответить ей с
  конкретным `targetOrigin` нельзя. Поэтому только на стенде, только рамке, чей адрес — тестовая страница с происхождения
  consolem, consolem отправляет сообщения с `"*"`. Правило выбора без кода под плагин: адрес на происхождении consolem — рамка без
  `allow-same-origin` и `"*"`; иначе — как в разделе 5. В протокол `setup/1` это не входит. Решение автора документа;
- библиотека для автора страницы (`setup-bridge.js`) пишется здесь, в consolem (`api/setup-bridge.js`), по протоколу; тестовая
  страница стенда работает на ней же, своего кода протокола у неё нет. psim-sdk получает её готовой, вместе с предложением
  (ниже). Так протокол и его эталонная реализация одни. Решение автора документа;
- тесты `tests/api-*.js`: адрес страницы по праву `view`, `origin`, разметка `x-bridge`.

**consolem, интерфейс** — в новом прототипе (копия `index.html`), потом перенос в основной:

- правило выбора экрана (раздел 4), iframe и обработка сообщений шага 1;
- «Все параметры» и общий черновик со страницей;
- режим сравнения (раздел 9);
- шаг 2 — тем же прототипом или следующим;
- тестовая страница шага 2 — образец «сложного» экрана на данных стенда, например найденное в сети домена и команда вида.

**Предложение о слоях** (`docs/2026-11-16-kontrakt-i-podsistemy-predlozhenie.md`), п. 6: особый экран бывает ручным (по профилю) или
от подсистемы (`setupUi`); порядок — раздел 4 этого документа.

**psim-sdk** (по согласованию с его авторами):

Работу в psim-sdk этот план не делает: репозиторий чужой. План готовит для его авторов предложение и готовую библиотеку, а
делают они:

- ADR «Встраивание панели настроек» со ссылкой на протокол consolem;
- библиотека `setup-bridge.js` из consolem, раздаётся как `/static/i18n.js`;
- эмулятор: сторона consolem в карточке Details — страница по умолчанию, кнопки «Применить» и «Отменить» снаружи; галочка
  «Use plugin setup UI» остаётся как переключатель сравнения;
- шаблон генератора (`psim_plugin_gen/.../setup.html`) — на библиотеке, без своей кнопки сохранения;
- страница `railway_detector` — без тестовой кнопки Apply, правка через `change`.

**w2c** — запрос от consolem (`api/requests/`, адресат w2c). Что меняется против ADR-0115 §4.3 и норм:

| Пункт | Было (ADR-0115, P/02.1 N1.2) | Становится |
|---|---|---|
| Вид по умолчанию | форма по схеме, страница — добавка | есть страница — она; форма — «Все параметры» |
| Запись | страница пишет сервером подсистемы | страница не пишет; пишет consolem через `PATCH`, бэкенд передаёт плагину (`Platform.UpdateObject`, psim ADR-005) |
| `setup_ui[].mode` | только `tab` | `tab` или `iframe` |
| Ранг маршрута страницы | `edit` или `admin` | любой, токен — по настоящему праву человека; команды страницы проверяет ранг их маршрутов |
| Сообщения | `ready`, `height`, `dirty`, `saved` | протокол `setup/1` (разделы 6–7) |
| `sandbox` | без `allow-same-origin` | с `allow-same-origin` (как в доп. 2, п. 8) |
| Встраивание | — | дверь: `frame-ancestors` на consolem; оболочка: `frame-src` на двери; кука двери в iframe (раздел 5) |
| Прямой обмен страницы с плагином | HTTP через дверь | так же; дверь пропускает и WebSocket страницы (как `/ws` у `railway_detector`), с той же кукой |
| Блоки формы | `display.form` не доходит до consolem | бэкенд переводит `display.form` в `x-ui-tab`, `x-ui-group`, `x-ui-order` |

## 11. Порядок работ

1. **Контракт шага 1 и прототип.** Правки контракта из раздела 10 без `x-bridge`; тестовая страница; прототип: правило экрана,
   iframe, шаг 1, режим сравнения. Проверки — `api/TESTS.md` для `api/`, прототип — по правилам `CLAUDE.md`.
2. **Запрос к w2c и разговор с авторами psim-sdk** — параллельно с п. 1, как только описан протокол шага 1.
3. **Шаг 2.** `x-bridge` в контракте, `call`, `subscribe`, `navigate`, `confirm` в прототипе, тестовая страница «сложного» экрана.
4. **Перенос в `index.html`** по просьбе (скилл `proto-promote`).
